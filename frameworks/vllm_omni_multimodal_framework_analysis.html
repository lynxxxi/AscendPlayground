vLLM-Omni
多模态执行图

从“高效生成文本”走向“调度异构模型流水线”：用 Stage Graph 表达 AR、DiT、编解码器与跨模态连接，用解耦部署把不同计算形态放到合适的设备与批处理域。

01 / VERDICT
Executive readout

真正的新抽象不是“更多模态”，而是可部署的阶段图

vLLM-Omni 不是给原版 vLLM 增加几个图像输入插件，而是把 any-to-any 模型拆成具有独立执行策略、资源所有权与指标的 Stage。它复用 vLLM 的 AR 调度与 KV Cache，同时引入 Diffusion runtime、跨阶段 Orchestrator、StageRuntime、OmniConnector 与异构输出协议。

核心价值

复杂模型结构可服务化

Thinker、Talker、Code2Wav、DiT、VAE 等组件不再必须塞进同一进程与同一批处理循环。

工程壁垒

控制流与数据流分离

Orchestrator 决定请求状态与顺序；Connector 只搬运 tensor、KV 与元数据；部署位置由 StageRuntime 管理。

采用边界

兼容矩阵是逐模型、逐平台的

“框架支持 NPU”不代表每个模型、量化格式、Kernel 与分布式连接器都已在 NPU 上等价可用。

结论：若目标是语音对话、文生图/视频、具身动作或 AR→DiT 组合模型的生产服务，vLLM-Omni 的抽象方向完整；若只是视觉理解后输出文本，原版 vLLM 的多模态输入路径通常更简单。
02 / POSITION
System boundary

三类“多模态”必须先分清

多模态输入、非文本输出和 any-to-any 多阶段模型不是同一个问题。vLLM-Omni 主要解决后两者，并兼容第一类。

INPUT MM

理解型多模态

  • 文本 + 图像/音频/视频输入
  • 主干仍是 AR，输出通常为文本
  • 很多场景原版 vLLM 已覆盖
→
HETEROGENEOUS OUTPUT

生成型多模态

  • 输出文本、图像、音频、视频或动作
  • 存在 DiT、vocoder、VAE 等非 AR 组件
  • 指标从 TPOT 扩展到 TTFP、RTF、E2EL
→
ANY-TO-ANY

多阶段组合

  • 多个 AR / DiT / CNN 组件相互连接
  • 阶段间传 hidden state、latent、KV 或媒体 chunk
  • 需要独立扩缩容、批处理与故障生命周期
03 / ARCH
Control plane × execution plane

配置、编排、执行与传输各自有明确所有者

模型拓扑由 PipelineConfig 描述，部署位置由 DeployConfig 描述；解析后由 StageRuntime 物化副本，AR 与 Diffusion 使用各自引擎。Stage 是逻辑单元，不强制等于单独进程。

PipelineConfig

定义阶段、执行类型、能力和关系，是模型拓扑的事实源。

DeployConfig

定义设备、进程、副本、连接器与部署默认值，不改写模型图。

Stage policy

每阶段独立选择 batching、attention、parallelism 与 quantization。

Typed payload

张量与元数据分离，输出模态可组合，并保留请求关联与顺序。

04 / RUNTIME
Request lifecycle

一条请求穿过多个独立调度域

以 Qwen3-Omni 类语音链路为例，Thinker 产生文本与隐藏状态，Talker 产生音频 codec token，Code2Wav 合成波形；异步 chunk hand-off 使后级不必等待前级全部完成。

03 / TRANSFERStage edgetransfer function 整理 hidden state 与元数据。

05 / OPT
Stage-local optimization

不要给异构阶段套同一套优化参数

AR decode 是内存与 KV 管理问题，DiT denoise 是大算子、多步迭代与序列并行问题，VAE/codec 又有不同的吞吐和内存曲线。vLLM-Omni 的关键是把优化作用域降到 Stage。

AR

vLLM 原生能力

  • 连续批处理与高效 KV Cache
  • TP / PP / DP / EP 等并行
  • 前缀缓存与流式 token 输出
DiT

扩散执行能力

  • step-wise 执行与请求级 batching
  • 扩散注意力、量化与并行后端
  • 异步输出物化，减少关键路径阻塞
PIPELINE

跨阶段能力

  • 阶段级副本与动态资源配置
  • 共享内存、多节点 Connector
  • 异步 chunk、取消传播与输出排序
性能口径：论文报告 Qwen3-Omni 相对基线的 JCT 最多降低 91.4%，这是特定模型、硬件、并发和基线下的系统结果，不等价于“任意模型提升 10×”，也不能直接外推到 NPU。

07 / ASCEND
NPU readiness

昇腾不是从零移植，但必须按模型逐项验收

官方安装文档将 NPU 列为支持平台，模型矩阵也明确标记多条 Ascend 路径。这意味着平台接入已经存在；真正的工程工作集中在模型覆盖、阶段间传输、并行/量化组合与性能回归。

REUSE

可直接复用的上层资产

  • PipelineConfig / DeployConfig 分层
  • Orchestrator 请求状态和输出顺序
  • OpenAI-compatible API 与结构化输出
  • 阶段级指标、生命周期和错误归因

需要重新验证的执行面

  • 每个模型的 torch_npu 算子与 dtype 覆盖
  • DiT attention、量化、compile 与动态 shape
  • Connector 在单机/多机 NPU 的零拷贝或 RDMA 路径
  • TP/DP/EP 与阶段副本的 HCCL 拓扑
  • 显存预算、流并发、异步输出和故障恢复

08 / ROADMAP
Adoption plan

先打通单模型，再证明“解耦”真的值得

PHASE 0 / 1 周

冻结版本与口径

锁定 vLLM-Omni 与 vLLM 同 major/minor 版本；选择官方 NPU 已标记模型和固定请求集。

EXIT → 安装、离线推理、输出可复现
PHASE 1 / 1–2 周

单体服务基线

先用共置 Stage 跑通 API、流式、取消、异常与质量门，并采集各阶段时间。

EXIT → E2E 稳定且瓶颈可定位
PHASE 2 / 2–4 周

阶段级调优

只针对热点阶段调整并行、批处理、精度和内存；分别记录 AR 与 DiT 指标。

EXIT → 单 Stage 收益可解释
PHASE 3 / 3–6 周

解耦与扩缩容

拆分瓶颈阶段，验证 Connector 成本、背压、故障恢复和副本比例。

EXIT → JCT / 吞吐收益覆盖复杂度
09 / RISKS
Decision ledger

采用前需要接受的六个事实

01

项目演进很快

文档已要求 vLLM-Omni 与上游 vLLM major/minor 对齐；升级不是普通依赖漂移，而可能涉及 runtime 与配置边界变化。

02

支持是矩阵，不是布尔值

框架、平台、模型、任务、量化、并行与连接器必须作为一个部署组合验收。

03

拆分可能更慢

中间 tensor 很大、请求量不足或阶段耗时接近时，传输与同步可能抵消解耦收益。

04

指标必须随模态变化

只看 token/s 会掩盖媒体首包、实时因子、VAE 尾延迟与最终 artifact 质量。

05

故障跨阶段传播

取消、超时、worker 重启和部分流式输出需要全链路语义，不能只看单引擎健康。

06

质量门是生产能力

视觉、音频和动作输出的数值差异不能仅靠文本回归测试覆盖。
