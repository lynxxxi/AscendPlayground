01 / VERDICT
Executive readout

不是“缺 CI”，而是 PR 门禁之后出现断层

MindIE-SD 已具备一个企业主导型开源项目的基本骨架：3 条公开 GitCode workflow、x86/ARM 多 ABI 构建、CPU 友好 UT、pre-commit、增量测试、覆盖率门禁、双语 Sphinx/ReadTheDocs、OWNERS 与治理文档。真正拉开它与第一梯队差距的，是 merge 后、nightly、release 三段没有形成公开且可量化的持续看护。

已观察事实

PR 基础门禁有真实工程深度

文档变更可跳过构建；非文档变更并行执行 x86 ABI1、ARM ABI1、ARM ABI0 构建和 ARM UT；新增 Python 文件设 60% 行覆盖、30% 分支覆盖门槛。

公开缺口

没有 E2E / nightly / release workflow

当前树中未观察到公开的 E2E 目录、定时 workflow、性能回归门禁或发布流水线。NPU 精度与模型兼容性更多体现为文档/示例能力，而不是持续回归资产。

运营推断

“微信群快答”可能制造隐性支持债

README 将微信群作为快速交流入口，但关键决策、FAQ 与故障经验若不回流公开 Issue/文档，会让搜索者重复提问，也让维护者承担不可复用的私域答疑。

一句话策略：先不追求复制 vLLM/SGLang 的全部规模；优先把现有 PR 构建/UT 资产接成 PR → merge → nightly → release 四段闭环，再用分目录 OWNERS、贡献者阶梯和 CHAOSS 指标把“谁负责、多久响应、何时升级”公开化。

02 / METHOD
Evidence before score

事实、样本、推断和目标，四种证据不混写

技术事实来自各项目 2026-08-24 当前默认分支的仓库树、官方文档与公开 workflow；仓库规模来自 GitHub/GitCode 公开页面/API；治理效率采用最近关闭项的滚动样本。所有评分都是分析判断，不是社区官方评级。

事实 仓库/官方文档可直接验证样本 有窗口和样本量限制推断 从事实推导的分析目标 建议 SLO，不是现状

对标集：两类社区，不能只排一个榜

  • 通用推理/后端：vLLM、vllm-ascend、SGLang、TensorRT-LLM。
  • 多模态生成：vLLM-Omni、Cache-DiT、LightX2V、FastVideo、DiffSynth-Studio。
  • 审计对象：MindIE-SD，既是 NPU 加速套件，又向多个上层社区提供后端能力。

滚动效率样本的正确读法

  • GitHub Issue：最近更新的 30 个已关闭 Issue，其“创建→关闭”年龄中位数。
  • GitHub PR：最近 30 个 closed PR 中已合入项的“创建→合入”中位数。
  • GitCode：最近 10 个公开关闭 Issue / 合入 PR。
  • 它不测首次响应；高值可能代表主动清理旧债，小时级低值也可能代表维护者自合并或机器人。
评分规则（0–5）
0 未观察到资产；1 手工/零散；2 有基础入口但未形成门禁；3 PR 级可重复且有文档；4 PR/merge/nightly/release 多层闭环并可观测；5 元数据驱动、跨硬件、成本治理、自动恢复和公开运营机制均成熟。总分是 11 维简单平均，用于定位差距，不用于替代逐项证据。

03 / LANDSCAPE
Scale is context, not health

先看规模与节奏，再看机制

05 / TESTING
UT → E2E → nightly → release

MindIE-SD 的 UT 已经像一层，E2E/nightly 还不像系统

当前测试文档明确区分 CPU 兼容与 NPU 依赖测试，提供 --cpu_only / --npu_only / --all，还具备增量 test finder。但公开 PR workflow 实际只调用 CPU 友好的 run_UT_test.sh；NPU 用例、模型 E2E、精度、性能和长稳没有公开触发时机与硬件归属。

L0 / CPU逻辑 UT配置、工具、编译逻辑；硬件 mock；每 PR 必跑。
L1 / 1 NPU算子/组件真实 NPU 算子，小输入，不起完整模型服务。
L2 / 1 NPU模型 E2E减层/随机权重；单模型基本推理、API、输出结构。
L3 / 2–8 NPU集成/兼容并行、量化、缓存、编译、框架组合，merge 后运行。
L4 / POOL精度/性能/长稳真实权重，nightly/weekly/release；基线与方差带。

P0：先把“跑什么”显式化

为每个测试文件补 level、est_time、runner、framework、model、disabled_issue。SGLang 的注册制是当前性价比最高的参考。

P0：把性能与正确性分开

模型能生成不代表精度对齐，sanity 也不代表性能稳定。nightly 至少拆功能、精度、性能三条历史曲线，阈值使用相对基线和方差带。

P1：禁止无债主 skip

所有跳过/豁免必须带原因、Issue、责任人和到期日；机器人每周巡检。目标不是“全绿”，而是“红得准、有人管、可恢复”。

06 / BUILD & CI
Build time is a product metric

三条构建 lane 已有，构建时间却仍是黑箱

MindIE-SD 的构建并非普通 Python wheel：setup.py::CustomBuildPy 会串联 AscendC/TIK custom OPP、PyTorch plugin、compile_commands 合并与 wheel 打包。PR 流水线并行构建 x86 ABI1、ARM ABI1、ARM ABI0，是正确方向；但公开 workflow 没有 step duration 归档、timeout、缓存命中率或历史趋势，因此无法回答“冷构建多久、哪段最慢、改动后退化多少”。

07 / OPERATIONS
Docs · quality · release · bots · compatibility

文档与质量领先于发布和机器人

MindIE-SD 的用户入口已经比很多同规模多模态项目完整：中英文 Sphinx、ReadTheDocs、开发镜像、测试/构建/性能指南、支持矩阵、PyPI 包和 vLLM-Omni 镜像说明。薄弱点在于这些资产尚未被 release 与机器人持续验证。

08 / GOVERNANCE
Ownership is not yet a ladder

角色名单清楚，但权力如何获得仍不清楚

根目录 OWNERS 已列出 5 位 branch keeper、5 位 approver、18 位 reviewer；治理文档也说明 reviewer→approver→branch keeper 的合入链。这比许多同规模多模态项目成熟。但文档没有回答晋升标准、提名/投票、任期、emeritus、罢免、厂商多样性和非代码贡献路径。

可见的责任链

PR 模板要求 Issue、Purpose、Test Plan、Test Report；治理要求 reviewer 评审、approver 确认、branch keeper 合入。角色与受保护分支责任相匹配。

root OWNERS 会成为漏斗

仓库跨 ops、compilation、quantization、cache、docs、release 多个专业域，却只有根级名单。所有通知和审批容易集中到同一批人，无法显示实际模块所有权。

公开沟通存在“双轨”

Issue 是正式入口，微信群是快速入口。若 RFC、故障决策和路线优先发生在群内，外部贡献者无法检索上下文，也难以靠公开贡献积累 merit。

09 / CLASSICS
Books are operating lenses

经典框架不是口号，而是检查表

把经典书籍和成熟基金会经验放进同一张审计表，可以看出 MindIE-SD 的主要挑战不是技术资产不足，而是“公开、可复用、可晋升、可量化”四个社区机制尚未跟上代码演进速度。

01 / FOGEL
Producing OSS

降低贡献者的“首次成功成本”

透明入口发布节奏可咀嚼任务

MindIE-SD 已有贡献指南、PR 模板、devcontainer、测试与构建文档；下一步不是再写一份概述，而是让一个外部开发者在无 NPU 环境完成“fork→CPU UT→PR→自动 reviewer→首次反馈”。发布日历、good first issue、已知限制和版本兼容窗口也应公开。

02 / EGHBAL
Working in Public

这是一个正在“stadium 化”的企业项目

用户≫贡献者维护者压力私域债务

随着 vLLM-Omni、Cache-DiT、LightX2V 等生态入口增多，旁观用户会比深度贡献者增长更快。微信群能降低单次答疑延迟，却可能扩大维护者重复劳动。应设“群聊→Issue/FAQ 回流”制度、支持边界、问题模板和轮值 triage，避免核心工程师成为永远在线的客服。

03 / ASF
Apache Way

单厂商起步不是问题，权力只在雇佣关系中才是问题

Community over Code公开沟通Merit厂商中立

现有角色名单显示清楚的公司维护结构，但未说明外部个体如何凭公开贡献获得 reviewer/approver 权限。建议发布晋升证据、公开提名与决策记录；所有技术决策从私域回写公共渠道，并定期披露组织/公司多样性，而非只统计 commit 数。

04 / K8S
Community

从根 OWNERS 走向模块 ownership 和 reviewer/approver 双阶段

Contributor LadderOWNERSSIGRelease Team

MindIE-SD 已有 reviewer、approver、branch keeper 三类角色，适合直接映射 Kubernetes 的两阶段评审。按 ops / compilation / quantization / cache / docs / release 建分目录 OWNERS，并让机器人自动建议 reviewer；建立轻量 SIG/working group 和 Release Team shadow，降低根级名单的通知过载。

05 / CNCF
Contributor Strategy

治理文档必须告诉贡献者“领导位置可达到”

角色晋升非代码贡献连续性

当前治理文件描述“谁在做什么”，还没有“怎样成为他们”。采用 CNCF Maintainer Council + Contributor Ladder 的轻量模板，补晋升、移除、emeritus、投票和非代码贡献路径；不要复制一个听起来漂亮但不符合实际的章程。

06 / CHAOSS
Health Metrics

从产出计数转向响应、风险和可持续性

首次响应变更请求Bus factor留存

Star、commit、closed issue 都是活动量，不等于健康。首期看板只需 8 项：Issue 首次人工响应、PR 首次 review、合入周期、未关闭年龄 p90、flaky、reviewer 负载、首次贡献成功率、90 天贡献者留存。按内部/外部作者拆分，才看得见社区摩擦。

07 / TODO Group
OSPO

衡量“上游影响”，而不只衡量下游代码量

Outbound OSSUpstream first维护成本

MindIE-SD 的生态价值应包括：向 vLLM-Omni、Cache-DiT、LightX2V 等上游合入的 NPU 能力、被接受的接口设计、减少的 downstream patch、版本同步时延和跨社区维护者数量。OSPO 应帮助团队获得跨项目贡献时间和晋升认可，而不是只要求仓库内 commit。

10 / ROADMAP
90-day operating system

先闭环，再扩张；先观测，再优化

路线图刻意不从“再加更多测试”开始，而从资产盘点、责任归属和时间数据开始。没有注册表和 owner，测试越多只会让 CI 更慢、失败更吵。

WEEK 0–2 / INVENTORY

把存量变成资产

  • 所有测试标 L0–L4、硬件、模型、框架、预计耗时
  • 输出 build/UT 分阶段 duration
  • 建立 skipped/flaky/compatibility 债务表
  • 为 ops/compile/quant/cache/docs 划 owner
EXIT → 可回答“跑什么、在哪跑、多久、谁负责”
WEEK 3–5 / CLOSE THE LOOP

接通 merge 与 nightly

  • merge smoke：单 NPU + 减层模型
  • nightly：功能、精度、性能三条流
  • artifact 复用与 diff-aware 路由
  • 失败自动建/关联 Issue，禁止裸 skip
EXIT → 每个支持矩阵 ✅ 有 last-green
WEEK 6–8 / RELEASE

版本成为可重复事件

  • 发布 checklist、RC 窗口与 release team
  • 同一 artifact 提升到 PyPI/镜像
  • SBOM、签名、provenance、回滚演练
  • 兼容窗口与弃用政策
EXIT → 从 tag 到可验证产物 ≤ 60m
WEEK 9–12 / COMMUNITY

把维护者从人工路由中释放

  • labeler、welcome、retest、stale、backport
  • Contributor Ladder + 分目录 OWNERS
  • 每周 triage + 月度公开健康报告
  • 微信群决策/FAQ 回流公共渠道
EXIT → 外部 PR 首 review p90 ≤ 2 工作日
