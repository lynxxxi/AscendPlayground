01 / VERDICT
Executive readout

不是“缺 CI”，而是 PR 门禁之后出现断层

MindIE-SD 已具备一个企业主导型开源项目的基本骨架：3 条公开 GitCode workflow、x86/ARM 多 ABI 构建、CPU 友好 UT、pre-commit、增量测试、覆盖率门禁、双语 Sphinx/ReadTheDocs、OWNERS 与治理文档。真正拉开它与第一梯队差距的，是 merge 后、nightly、release 三段没有形成公开且可量化的持续看护。

已观察事实

PR 基础门禁有真实工程深度

文档变更可跳过构建；非文档变更并行执行 x86 ABI1、ARM ABI1、ARM ABI0 构建和 ARM UT；新增 Python 文件设 60% 行覆盖、30% 分支覆盖门槛。

公开缺口

没有 E2E / nightly / release workflow

当前树中未观察到公开的 E2E 目录、定时 workflow、性能回归门禁或发布流水线。NPU 精度与模型兼容性更多体现为文档/示例能力，而不是持续回归资产。

运营推断

“微信群快答”可能制造隐性支持债

README 将微信群作为快速交流入口，但关键决策、FAQ 与故障经验若不回流公开 Issue/文档，会让搜索者重复提问，也让维护者承担不可复用的私域答疑。

一句话策略：先不追求复制 vLLM/SGLang 的全部规模；优先把现有 PR 构建/UT 资产接成 PR → merge → nightly → release 四段闭环，再用分目录 OWNERS、贡献者阶梯和 CHAOSS 指标把“谁负责、多久响应、何时升级”公开化。

02 / METHOD
Evidence before score

事实、样本、推断和目标，四种证据不混写

技术事实来自各项目 2026-08-24 当前默认分支的仓库树、官方文档与公开 workflow；仓库规模来自 GitHub/GitCode 公开页面/API；治理效率采用最近关闭项的滚动样本。所有评分都是分析判断，不是社区官方评级。

事实 仓库/官方文档可直接验证样本 有窗口和样本量限制推断 从事实推导的分析目标 建议 SLO，不是现状

对标集：两类社区，不能只排一个榜

  • 通用推理/后端：vLLM、vllm-ascend、SGLang、TensorRT-LLM。
  • 多模态生成：vLLM-Omni、Cache-DiT、LightX2V、FastVideo、DiffSynth-Studio。
  • 审计对象：MindIE-SD，既是 NPU 加速套件，又向多个上层社区提供后端能力。

滚动效率样本的正确读法

  • GitHub Issue：最近更新的 30 个已关闭 Issue，其“创建→关闭”年龄中位数。
  • GitHub PR：最近 30 个 closed PR 中已合入项的“创建→合入”中位数。
  • GitCode：最近 10 个公开关闭 Issue / 合入 PR。
  • 它不测首次响应；高值可能代表主动清理旧债，小时级低值也可能代表维护者自合并或机器人。
评分规则（0–5）
0 未观察到资产；1 手工/零散；2 有基础入口但未形成门禁；3 PR 级可重复且有文档；4 PR/merge/nightly/release 多层闭环并可观测；5 元数据驱动、跨硬件、成本治理、自动恢复和公开运营机制均成熟。总分是 11 维简单平均，用于定位差距，不用于替代逐项证据。

03 / LANDSCAPE
Scale is context, not health

先看规模与节奏，再看机制

05 / TESTING
UT → E2E → nightly → release

MindIE-SD 的 UT 已经像一层，E2E/nightly 还不像系统

当前测试文档明确区分 CPU 兼容与 NPU 依赖测试，提供 --cpu_only / --npu_only / --all，还具备增量 test finder。但公开 PR workflow 实际只调用 CPU 友好的 run_UT_test.sh；NPU 用例、模型 E2E、精度、性能和长稳没有公开触发时机与硬件归属。

L0 / CPU逻辑 UT配置、工具、编译逻辑；硬件 mock；每 PR 必跑。
L1 / 1 NPU算子/组件真实 NPU 算子，小输入，不起完整模型服务。
L2 / 1 NPU模型 E2E减层/随机权重；单模型基本推理、API、输出结构。
L3 / 2–8 NPU集成/兼容并行、量化、缓存、编译、框架组合，merge 后运行。
L4 / POOL精度/性能/长稳真实权重，nightly/weekly/release；基线与方差带。

P0：先把“跑什么”显式化

为每个测试文件补 level、est_time、runner、framework、model、disabled_issue。SGLang 的注册制是当前性价比最高的参考。

P0：把性能与正确性分开

模型能生成不代表精度对齐，sanity 也不代表性能稳定。nightly 至少拆功能、精度、性能三条历史曲线，阈值使用相对基线和方差带。

P1：禁止无债主 skip

所有跳过/豁免必须带原因、Issue、责任人和到期日；机器人每周巡检。目标不是“全绿”，而是“红得准、有人管、可恢复”。

06 / BUILD & CI
Build time is a product metric

三条构建 lane 已有，构建时间却仍是黑箱

MindIE-SD 的构建并非普通 Python wheel：setup.py::CustomBuildPy 会串联 AscendC/TIK custom OPP、PyTorch plugin、compile_commands 合并与 wheel 打包。PR 流水线并行构建 x86 ABI1、ARM ABI1、ARM ABI0，是正确方向；但公开 workflow 没有 step duration 归档、timeout、缓存命中率或历史趋势，因此无法回答“冷构建多久、哪段最慢、改动后退化多少”。

07 / OPERATIONS
Docs · quality · release · bots · compatibility

文档与质量领先于发布和机器人

08 / GOVERNANCE
Ownership is not yet a ladder

角色名单清楚，但权力如何获得仍不清楚

根目录 OWNERS 已列出 5 位 branch keeper、5 位 approver、18 位 reviewer；治理文档也说明 reviewer→approver→branch keeper 的合入链。这比许多同规模多模态项目成熟。但文档没有回答晋升标准、提名/投票、任期、emeritus、罢免、厂商多样性和非代码贡献路径。

可见的责任链

PR 模板要求 Issue、Purpose、Test Plan、Test Report；治理要求 reviewer 评审、approver 确认、branch keeper 合入。角色与受保护分支责任相匹配。

root OWNERS 会成为漏斗

仓库跨 ops、compilation、quantization、cache、docs、release 多个专业域，却只有根级名单。所有通知和审批容易集中到同一批人，无法显示实际模块所有权。

公开沟通存在“双轨”

Issue 是正式入口，微信群是快速入口。若 RFC、故障决策和路线优先发生在群内，外部贡献者无法检索上下文，也难以靠公开贡献积累 merit。

09 / CONTRIBUTION GATES
Small PR · closed review · green CI

把外部贡献要求写成可验证的合入契约

MindIE-SD 当前最直接的流程问题不是缺少行为准则，而是贡献指南、PR 模板、CI 触发方式和真实分支策略没有形成同一套门禁。规则应进入贡献指南和 PR 模板，由平台与 CI 强制；CODE_OF_CONDUCT.md 继续只负责社区行为边界。

分支错配

main 与仓库事实冲突

中英文贡献指南要求从 main 创建分支，但当前远端长期分支是 dev/master，PR workflow 也监听 dev/master。文档会直接引导外部开发者选错基线或目标分支。

规模缺口

1000 行只约束 commit，不约束 PR

现有本地治理规则提到历史整理时单个 commit diff 控制在 1000 行以内，但多个小 commit 仍可组成超大 PR，无法降低一次评审的认知负担。

闭环缺口

角色链不等于意见已闭环

治理文档定义了 reviewer→approver→branch keeper，却没有要求所有评论得到答复、所有 conversation 已解决，以及新提交后重新确认批准。

门禁缺口

评论触发不等于 CI 必须通过

当前公开 PR 流水线依赖评论 compile 触发。仓库文件能证明存在 CodeCheck、构建和 UT，不能证明这些状态已被配置为服务端合入必需项。

vLLM 与 SGLang：共同点是把“可评审、可验证、有人负责”串成链

维度vLLMSGLangMindIE-SD 应吸收什么
目标分支围绕默认开发主线提交 PR。禁止直接向 main 提交，要求创建独立主题分支后发 PR。外部贡献必须基于最新 upstream/dev 创建 topic branch，PR base 只能是 dev；master 仅接收维护者发布/热修复或 dev→master。
变更规模重大架构变更超过 500 LOC（排除 kernel/data/config/test）应先有 RFC，否则可标记 rfc-required 并拒绝进入常规评审。没有统一 LOC 硬上限，但要求避免大幅改造；跨 kernel 发布链拆成多个 PR，超时测试和 CI job 也按边界拆分。采用更容易执行的单 PR 有效变更量 ≤1000 行，并保留“批准的 RFC + maintainer 例外标签”处理不可拆分变更。
评审闭环需要修改时加 action-required；作者处理意见并请求复审，合理时间内响应所有评论。Merge Oncall 协调评审，Codeowners 和其他 reviewer 完成批准。要求所有意见明确回复、需要修改的意见完成复审、不采纳意见说明理由并获 reviewer 确认，未解决会话数必须为 0。
CI 与合入lint、测试、文档是质量要求；受限硬件 CI 由授权命令触发，最新提交必须获得所需信号。run-ci 标签启动 CI；理想合入条件是每个修改文件获得 Codeowner 批准且 required CI 全绿。自动运行基础检查，昂贵 NPU 测试可授权触发，但所有适用 required checks 必须针对最新 head/预合并结果通过后才能合入。
PR 模板强制填写 Purpose、Test Plan、Test Result 和文档影响。显式列出 Motivation、Modifications、准确性、性能以及格式/测试/文档 checklist。在现有四段模板上增加目标分支、有效行数、评审闭环、CI 状态和文档影响的勾选项。
推荐规范原文：外部贡献者必须基于最新 upstream/dev 创建独立主题分支，并将 PR 的目标分支设置为 dev。单个 PR 的有效变更量原则上不得超过 1000 行；所有评审意见必须形成“已修改并复审”或“说明理由并获确认”的闭环；所有适用的必需 CI 必须在最新提交上通过。任何一项不满足，PR 不得合入。

四道门必须机器可判，不能只靠贡献者自觉

GATE 01 / BASE只进 devCI 校验 PR base；外部 PR 指向 master 时直接失败并给出重开指引。发布与紧急热修复使用受控例外路径。
GATE 02 / SIZE≤1000 有效行按整个 PR 的 additions + deletions 计算，而不是逐 commit；生成物、锁文件、vendored code 和测试数据通过白名单排除。
GATE 03 / REVIEW未解决会话为 0所有评论有结论；最后一次代码更新后仍保有有效 Approver 批准。新 push 应使旧批准失效或触发重新确认。
GATE 04 / CI必需检查全绿CodeCheck、适用构建和 UT 针对最新 head/merge ref 成功；失败、取消、未运行均不可合入，文档 PR 由路径规则自动选择专用检查。

第一层：贡献指南

解释为什么以 dev 为集成分支、怎样同步 upstream/dev、如何拆分 PR、怎样处理 review，以及本地最小验证命令。中英文必须同步。

第二层：PR 模板与 policy job

模板收集 Issue、目的、测试证据和 checklist；轻量 policy job 自动检查 base、有效行数与必要字段，并提供明确修复信息。

第三层：服务端分支保护

dev/master 禁止直接 push，配置 required approvals、最新代码批准、全部会话解决和 required status checks。仓库内 workflow 不能替代这层配置。

建议加入 PR 模板的最小 checklist
  • 本 PR 以 dev 为目标分支，并基于最新 upstream/dev。
  • 本 PR 只解决一个主题，有效变更量不超过 1000 行；若超限，已关联批准的 RFC 和例外标签。
  • 已执行适用的 pre-commit、构建、单元测试、准确性或性能测试，并在 Test Report 提供结果。
  • 所有评审意见均已回复；需要修改的意见已完成修改并请求复审，未解决会话为 0。
  • 用户可见变更已同步中英文文档；不适用时已说明原因。
统计口径建议：“有效变更量”定义为整个 PR 相对目标分支的新增行与删除行之和；不要按 commit 分别计算，以免用多个小 commit 绕过门禁。二进制文件、自动生成文件、依赖锁文件、第三方镜像代码和大体量测试数据应维护显式排除清单。若团队坚持绝对硬上限，可删除 RFC 例外，但要接受大型重命名、生成物更新和迁移类变更无法正常提交的代价。

90-day operating system

先闭环，再扩张；先观测，再优化

路线图刻意不从“再加更多测试”开始，而从资产盘点、责任归属和时间数据开始。没有注册表和 owner，测试越多只会让 CI 更慢、失败更吵。
