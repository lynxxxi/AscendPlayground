Working in Public
把维护工作变成公共资产		设置轮值支持和群聊回流规则；问题归档到 Issue/FAQ；技术取舍进入 RFC/ADR，避免核心维护者重复答疑。建议起步线接口、发布、治理决定 100% 有公共记录；高频问题每月回写 FAQ；每周有明确 triage 值班人。双轨入口Issue 是正式入口，微信群提供快速支持；未观察到私域决策回流规则和公开支持轮值。私域知识债、维护者隐形负载和重复支持无法测量。
Apache Way
公开、共识、Merit、厂商中立		公开讨论重大决策；用可验证贡献晋升 reviewer/approver；披露提名、投票和任职依据；按项目利益而非雇佣关系授权。建议起步线重大决定公共留痕率 100%；每半年公开评审晋升候选；晋升证据、异议和结果可检索。角色已明确SIG 与组织合入责任链、晋升/投票/退出规则已公开；厂商多样性和执行历史待统计。晋升入口已可见；需统计外部贡献者实际获得角色的案例和周期。
Kubernetes Community
OWNERS、SIG、KEP、Release Team		分目录设置 reviewer/approver；自动路由 PR；用 RFC/KEP 管理重大变更；Release Team 设 shadow 培养接班人。建议起步线活跃模块 100% 至少 2 名 owner；≥80% PR 自动匹配 reviewer；Top3 review 份额 <60%；每次发布至少 1 名 shadow。组织职责配置已有 MindIE-SD SIG 和组织审批规则；模块路由、RFC 索引与 Release Team shadow 覆盖待核验。需验证不同专业域的检视负载和接班覆盖，不能仅从本仓无 OWNERS 推断。

重点对标：vLLM-Omni 的 L1–L5 是什么，每层有哪些用例？

L 是测试层级（Level）。Omni 把不同验证深度和算力成本的用例放到不同交付阶段：L1 组件逻辑 → L2 基本链路 → L3 真实模型关键验证 → L4 扩展回归 → L5 长稳与可靠性。这不是五个质量分数，也不是五套互不重叠的测试目录；同一测试函数可以在不同层使用不同权重和断言。

L1 / UNIT & LOGIC组件算得对吗？函数、配置、边界和异常；CPU 快速反馈，不启动完整模型服务。
L2 / BASIC E2E请求链路通了吗？启动服务或离线引擎，发请求、检查输出；允许 dummy 或轻量权重。
L3 / CORE VALIDATION真实模型结果对吗？关键模型与部署组合，真实权重、内容与尺寸等更深断言。
L4 / FULL REGRESSION扩展场景退化了吗？功能组合、独立精度基线、性能负载、用户文档示例。
L5 / STABILITY久跑和故障能应对吗？持续负载、显存压力、进程退出、错误响应与恢复行为。
证据口径：2026-09-20 核对分层总览、测试编写指南及下列具体源码。表中是代表性已存在用例，不是全仓用例穷举；执行次数会随参数化、硬件、筛选和 skip 变化。时间为规范预算，不是本次实测；L4/L5 也不意味着对全部模型与全部硬件做笛卡尔积覆盖。

能力官方依据对 nightly 可感知性的意义
运行结果三入口查看流水线运行结果：入口一 Actions 标签页；入口二 提交记录页每条提交右侧的状态徽标，点击跳运行详情；入口三 PR 页 Checks 标签页汇总该 PR 触发的全部运行。开发者默认就能看见——前提是运行属于本仓库。独立调度可以通过 PR 回传或运行关联提供入口；原生 Actions 入口是否展示该任务需要实测，不能断言全部为空。

定时触发触发事件 1.9：on.schedule 使用 POSIX cron，按 UTC 解释、最短 5 分钟。平台级定时可用。“几点跑”必须实测：本报告前述 op-plugin 仓内注释与官方 UTC 说明存在冲突，先用无 NPU 的最小任务记录实际触发时刻。
可被外部定向触发手动运行流水线 API：POST /api/v8/repos/:owner/:repo/actions/workflows/:workflow_id/dispatches，body 带 ref 与 inputs；同组还有停止、重试、重新运行。调度系统或机器人可以“在 MindIE-SD 仓库里”发起一次运行并指定 ref：不需要把用例搬进被测仓，也能让运行归属被测仓。这是当前拓扑最低成本的缝合点。
结果可被读回OpenAPI 目录的 Actions 分组提供：流水线列表、运行记录、运行详情、jobs 列表、job 详情、Step 级日志、下载 job 日志、Artifacts 列表与下载。机器人能轮询结果并生成摘要：把“跑了什么、哪几条挂了、报告在哪”回写成 commit 评论或 Issue，开发者不必登录调度网站。

必须写清的平台边界：本次未核验到与 GitHub commit status/check-runs 等价的公开写入接口，不能直接照搬 GitHub 的事件名、API 与权限模型，也不能把“未查到接口”写成平台绝对没有能力。SD 的组织配置已通过 ci-pipeline-passed 等受控标签参与合入判断，PR 也已有外部结果回传，这是当前优先复用的路径。实际 SD 合入配置比仅检查本仓 workflow 更能说明接线。定时可保留在现有平台，跨仓触发可利用现有 webhook/调度服务；仅在确有需求时适配 Actions dispatch，并验证运行 SHA、授权、失败回传与旧状态失效。上述配置仍不证明所有边界已正确强制，需在实施阶段用受控失败验收。

其他社区怎么做：nightly 的结果怎么到达开发者

下面六个项目的机制都能用公开文件与官方文档核对。它们的共同点不是“有 CI”，而是结果入口公开、结论绑定到具体提交或修订区间、失败有固定去处（面板 / 模板 / 标签 / 值班人）。

社区 / 项目运行绑定与公开入口失败怎样到达开发者MindIE-SD 可借鉴的点
PyTorchHUD（hud.pytorch.org）：按 PR hud.pytorch.org/pr/<n>、按提交 hud.pytorch.org/commit/<sha> 把该提交上的全部 job 聚合到一页；主页展示 main 分支所有 job，便于识别持续性失败；日志分类器标注可能的失败原因。另有为“仓外后端”设计的 CRCR（Cross-Repo CI Relay）：上游按 allowlist 把 PR 事件派发给下游仓，下游跑完用 OIDC 回调把结果写回 HUD 与 PR check run（等级：L2 只上 HUD、L3 打非阻塞 check run、L4 才阻塞）。PR 上的 Dr. CI 机器人评论直接给出 HUD 链接；开发者先在 HUD 上判断“是我改坏的，还是主干本来就红”。仓外后端的结果则通过 CRCR 出现在 hud.pytorch.org/crcr 与对应 PR 的 check run 上。①“一个提交一页”的聚合视图；②机器人把链接送到 PR 现场；③主干视图把“我的 PR 挂了”与“主干本来就挂”分开；④同一份 allowlist 的 L3（npu）里已经写着 Ascend/pytorch——Ascend 生态内部就有一个“外部 CI 绑定上游 PR 并回写 check run”的现成先例，值得直接问对接人抄流程。
vLLMCI Failures 文档：Buildkite 日志公开且无需登录，仓内 ci-fetch-log.sh 一条命令取回失败 job 日志；Buildkite 的 test reliability 分析按用例给出 main 分支可靠性（2 天窗口）。先查 CI Failures Dashboard（GitHub Project）：已收录即大概率与本 PR 无关，可补日志链接并点 👍；未收录则按 450-ci-failure.yml 模板开单，标题格式固定、环境字段要求写 “Still failing on main as of commit <sha>”，并打 ci-failure 标签进入面板；文档给出每日 triage 步骤。①失败清单是公开面板，还能反映“多少人受影响”；②开单模板强制带上提交号；③把“每天看一眼”写成有步骤的例行动作。
SGLangNightly Test (Nvidia)：schedule: 0 14 */2 * * 加 workflow_dispatch，按 1/2/4/8 卡与 H100/B200/H200/GB300 显式拆矩阵；夜间任务生成 dashboard.md 并发布到独立数据仓 sgl-project/ci-data-diffusion（workflow 里的步骤名仍写作 “Publish to sglang-ci-data”，是过时残留，容易误导读者），各分片上传指标后合并 consolidated metrics。汇总 job “Check if any job failed” 统一收口；失败的 job 与 metrics 一起进入数据仓与看板，而不是留在某台 runner 上。①代码仓与结果数据仓分离，报告可长期保留；②卡数/型号显式拆矩阵；③“所有分片都上传指标”才允许合并，缺分片可判定为不完整。
TensorRT-LLM夜间与 periodic 测试不在公开 Actions，而在内部 Jenkins（公开 workflow 里只有 3 个 schedule，全是仓库维护类）。公开侧只保留“触发 + 回写”两件事：l0-test.yml 用 workflow_dispatch 接收 sha、test_result、test_results_url，再用 github-script 调 createCommitStatus({context:'blossom-ci', sha: inputs.sha, description:'N passed, M failed, K skipped'})，把内部结果写回 PR 上的 commit status；测试清单 tests/integration/test_lists/test-db/*.yml 版本化，条目带 stage: pre_merge / post_merge 与后端。开发者在本仓 PR 上就能看到 blossom-ci 状态与“通过/失败/跳过”计数，点进去是具体运行；要复现时用 /bot run --stage-list "<stage>" 跑 post-merge 的确切子集；waive 必须带 bug 链接或说明；完整 post-merge 运行需要 ci: post-merge approved 标签。最接近 MindIE-SD 现状的形态：执行体在公开仓库之外，但公开侧保留“SHA 入参 + 状态回写 + 显式测试清单”三件套。差别在于它用的是 GitHub 的 commit status API；本次未核验 GitCode 对应公开写入接口，所以 MindIE-SD 只能用“运行放进本仓”或“commit 评论 + Issue 自动开单”替代（见上文平台边界）。
OpenVINOnightly 就是 GitHub Actions 里的 ubuntu_22.yml 等 workflow：schedule 配两条 cron（0 0 * * 3,6 与 0 0 * * 2,4），并用 run-name 把定时运行渲染成 “… - Nightly (with / without latest OneDNN)”，在 Actions 列表中一眼可辨。官方 CI 文档直接告诉开发者：定时运行请到 Actions 页把 Event 过滤为 schedule（“For scheduled runs: Filter the runs by clicking on Event and selecting schedule”）。①nightly 运行自带标记，开发者不需要额外文档就能在列表里找到；②“怎么看夜间结果”被写进官方文档，而不是靠口口相传；③定时与 PR 运行共用同一套 Actions 界面，减少第二个入口。
LLVM（Buildbot）llvm-zorg 的 getReporters() 一次注册四类上报：GitHub PR 评论机器人、自动打标签、commit status 推送、以及带 Blamelist 的邮件通知（MailNotifier 可显示可疑提交列表）。失败评论模板固定为 “LLVM Buildbot has detected a new failure on builder … at step …”；关键在于 is_wrong_issue() 会拉取 PR 事件逐页比对 event['commit_id'] 与出错 revision，不匹配就打印 “Given commit {sha} is not related to PR#{issue}. Do not comment this PR.” —— 只评论引入失败的那个 PR，而不是给所有相关 PR 发噪音。①“归因到 PR”是可以写成代码的判定，不必依赖人肉；②同一套失败同时进评论、标签、状态与邮件，覆盖不同习惯的人；③邮件附 blamelist，把“谁可能改坏的”直接摆出来。
KubernetesTestGrid（testgrid.k8s.io）：每个 tab 依据最近若干次运行判定 PASSING / FAILING / FLAKY，支持排序、筛选、图表、分组与摘要；提供可嵌入的汇总徽章 https://testgrid.k8s.io/q/summary/<dashboard>/<tab>/tests_status?style=svg。状态页本身就是入口：点开即可看到是哪一天、哪个提交开始变红、是否持续。①用“最近 N 次”判定而不是单次结论；②徽章直接指向状态页而非裸日志；③flaky 与 failing 分开表达，避免“一红全红”。
Rustperf.rust-lang.org 性能回归看板可按 revision 区间对比；仓内 triage 目录保存每周日志（如 2026-08-09）：修订区间、回归/改进统计、每条回归的对比链接与责任人。每周由公开名册上的值班人生成 triage 日志，先复查上周承诺的动作（“nag people”），再在周会与 This Week in Rust 中复查。①把“每周看一次夜间结果”写成有名字的轮值与固定产出；②日志进仓、可搜索可引用，而不是聊天记录；③先复查上周动作，形成闭环。
提炼成四个必要条件：（1）可归属——运行或产物必须带 SHA（路径/文件名内嵌 SHA，或像 LLVM 那样比对 commit_id 找到引入失败的 PR）；（2）可看见——至少有一个公开或半公开的查看面（Actions 的 schedule 列表、HUD、TestGrid tab、Buildkite Analytics）；（3）会主动找人——邮件、IM、PR 评论、check run 至少占其一，并且归因是有条件的（只在引入失败处发声）；（4）有 owner 与升级——Issue + 标签 + 指派或轮值、连续 N 次失败才升级。
两个反面提醒：vLLM 与 SGLang 的日常夜间运行都不自动建 Issue（vLLM 依赖人工按模板开单，SGLang 连仪表盘都是数据仓里的 Markdown）——说明“跑起来”不等于“看得见”，强如这两个社区也在靠制度补位。而 TensorRT-LLM 与 OpenVINO 把执行体放在内部 Jenkins 里，公开侧只留 SHA 入参 + 状态回写 + 显式测试清单——这是“测试仓分离”最值得抄的合规形态。回头看 MindIE-SD 当前拓扑：部分 PR 运行已按提交回传，nightly 的版本绑定、报告访问、责任归属与历史索引尚待逐项核验。应补足已有链路，不能说四个条件均未满足。

从“跑起来”到“被看见”：nightly 感知的五段链路

01 / BIND运行绑定提交记录被测仓、分支、SHA 与触发方式（定时/手动/API），标题里就带 SHA 前 8 位。
02 / REPORT结果回到仓库在 Commit 页、PR Checks 或 commit 评论上留下可点击的结果，而不是只活在调度网站里。
03 / ASSIGN失败有主自动开单/去重，带失败用例、日志与机器信息，指派到 owner 或值班人，并打 ci/nightly 标签。
04 / SURFACE公开看板与 last-green一页状态：最近一次结论、通过率、按模型/硬件分组、上次全绿时间；README 徽章指向它。
05 / RITUAL固定仪式每周汇总红灯 TOP 与 flaky 名单，纳入版本发布验收；红超过 N 天升级到维护者会议。
方案 A / 优先复用

保留调度、机器与测试仓，补结果契约

在现有平台任务开始时固定 SD、pytest-infra、MindIE-CI 的精确 SHA；完成后利用已有 PR/报告服务发布批次摘要、测试覆盖和详情链接。nightly 报告记录时间与基线，失败关联 Issue 并去重。先核验现有实现，缺什么补什么，不要求迁移到 Actions。

方案 B / 可选原生入口

有需求时在 SD 仓增加调用入口

若团队希望从仓内手动触发或查看统一运行，可添加 workflow_dispatch 或 schedule，调用经过授权的现有测试服务。先确认平台支持、资源访问、测试 SHA 与结果回传；主干 nightly 不会自动成为每个 PR 的检查，不能承诺新增一个 YAML 就让三个界面都出现完整结果。

方案 C / 今天就能做

先把“入口”写进仓库

不管用哪种接法，MindIE-SD 的 test.md 都应该有独立一段：nightly 覆盖什么、什么时候跑、结果在哪看、挂了找谁。这是从 SD 仓发现 nightly 的低成本入口，可链接现有平台，无需先迁移调度。附带一条：pytest-infra 已有 testcase/mindie/sd，把这份用例清单与实际运行记录对应到支持矩阵，才能让测试资产与文档口径一致。

结论：感知问题不是“再加一个看板”，而是把运行从“调度网站里的任务”变成“仓库里的记录”。顺序建议是：先把 MindIE-SD 的 nightly 入口写进文档（今天）→ 在现有任务记录精确被测 SHA，并复用结果回传（一周内）→ 再为现有外部调度补可审查配置和失败关联（一个月内）→ 最后才谈聚合看板与趋势。同步核验已有 owner 和通知规则，避免展示与处理脱节。

GitCode ≠ GitHub：逐项迁移检查

能力GitCode 文档 / Ascend 源码证据MindIE-SD 应如何落地
PR 与合入后触发触发事件参考使用 open/reopen/update/merge；不是 GitHub 的 opened/synchronize。PR 评论有独立的 pull_request_comment 和正则过滤。轻量检查接 PR open/reopen/update；主干验证优先用目标分支 push，覆盖合入及直接推送。昂贵 E2E 可保留授权评论入口；同一提交避免 push 与 merge 双重触发。

三条曲线必须分开

功能（能不能跑）、精度（跑得对不对）、性能（跑得多快）是三条独立曲线，失败归因和责任人也不同。混在一条“nightly 红了”里，最终没人看得懂。

阈值用相对基线与方差带

先冻结一个基线版本与硬件组合，再定义“超过 2σ 或相对基线退化 >5% 报警”。绝对数字在不同机器上没有可比性。

权限第一

命令必须绑定 actor 角色：外部用户只能触发只读/诊断类命令，昂贵 NPU 任务需要 collaborator 以上权限。SGLang 在 fork PR 上按权限决定是否 checkout PR 代码，是必须抄的安全姿势——命令处理器本身跑在提权上下文里。

幂等与限流

同一条命令重复出现只能产生一个 active run；用 concurrency 的 IGNORE/QUEUE 策略代替“谁手快谁先跑”。机器人对重复命令应先回复已有运行链接，而不是再排一次队。

可审计、可回退

命令处理脚本要进仓、走 PR 评审、留评论与标签痕迹，并支持“谁在什么时候让机器人做了什么”的回溯。外部服务可继续承载巡检，但应提供可审计配置、结果入口与责任人。

建议加入 PR 模板的最小 checklist
  • 本 PR 以 dev 为目标分支，并基于最新 upstream/dev。
  • 本 PR 只解决一个主题，有效变更量不超过 1000 行；若超限，已关联批准的 RFC 和例外标签。
  • 已执行适用的 pre-commit、构建、单元测试、准确性或性能测试，并在 Test Report 提供结果。
  • 所有评审意见均已回复；需要修改的意见已完成修改并请求复审，未解决会话为 0。
  • 用户可见变更已同步中英文文档；不适用时已说明原因。
统计口径建议：“有效变更量”定义为整个 PR 相对目标分支的新增行与删除行之和；不要按 commit 分别计算，以免用多个小 commit 绕过门禁。二进制文件、自动生成文件、依赖锁文件、第三方镜像代码和大体量测试数据应维护显式排除清单。若团队坚持绝对硬上限，可删除 RFC 例外，但要接受大型重命名、生成物更新和迁移类变更无法正常提交的代价。
