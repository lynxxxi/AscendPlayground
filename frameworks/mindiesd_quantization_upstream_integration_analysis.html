01 / VERDICT
Executive decision

只复用 runtime layer：MindIE 作为 Ascend 加速库 provider

本方案只分析并复用 MindIE 的运行时量化 layer、kernel wrapper、布局处理与能力探测。上层 quantize(model)、遍历/替换模型、配置编排等属于历史兼容路径：可以继续留在 MindIE 中兼容旧用户，但不迁移到 SGLang/vLLM-Omni，也不进入新架构、交付路线或验收门禁。

推荐：MindIE 交付稳定的 runtime layer/provider API，上游框架只写薄桥接。

SGLang/vLLM-Omni 自己拥有模型图、并行 Linear、权重加载、component 路由和 scheduler；其 QuantMethod 在加载后把 tensor/shard 描述交给 MindIE runtime 的 prepare()，forward 再调用 run()。MindIE 内部继续复用现有 Linear/MoE/FA layer 与 ACLNN/CANN/custom op。公共 SPI 保持平台无关，因此 CUDA、ROCm、XPU 或其他加速库也能实现同一接口，但无需依赖 MindIE。

02 / SCOPE
Scope & evidence

分析口径：以代码路径为准，不把“接口兼容”当成“后端可用”

报告以本地源码快照为主、官方文档为交叉证据。所谓“支持”拆成算法语义、checkpoint 表示、framework adapter、hardware platform、kernel provider、模型、并行方式与编译模式八个维度。

MindIE 研究对象

quantization/layer.py 及其 Linear/FA runtime、量化 kernel wrapper、自定义算子、pack/layout、step 输入与 capability。quantize.py 仅作历史背景，不是改造对象。

功能范围

证据等级

03 / MINDIE SD

计算资产直接复用

Linear、MX、DualScale 与 FA 的算子选择、padding、scale 处理和自定义 op 封装继续留在 MindIE runtime 包内，避免上游各维护一份。

权重所有权外置

新 API 接收 tensor bundle/shard metadata；不要求 runtime layer 自己打开 checkpoint。由上游 loader 管理 Parameter、meta-device 与分片。

稳定语义入口

QuantMode 可继续作为 MindIE 内部实现细节；对外用版本化 scheme/capability，避免 GPU 或其他库被 NPU mode id 绑住。

step 必须显式

runtime layer 不读取进程级 TimestepManager；step/policy 由上游 scheduler 通过 context 传入，才能支持连续批处理。

Attention 作为 runtime API

暴露 run_attention(q,k,v,metadata,context)，由上游 attention backend 调用；不要求给模型对象注入字段或改 forward。

能力启动期可见

probe() 在执行前返回 SoC、CANN、dtype、shape、layout 和 graph 约束；不支持时明确拒绝，禁止 silent fallback。

本地：vllm_omni/quantization/{factory,component_config}.py
重要现状：多平台框架已经存在，并不代表同一量化算法自动跨平台。vLLM-Omni 的 Int8 已有 CUDA/NPU 分支，MXFP4 文档也已出现 ROCm 与 NPU 的不同实现，但当前方法仍会直接判断平台并导入具体库。这证明“语义可共用、执行需分 provider”，也说明 provider SPI 是增量收敛，不应先重写全部现有后端。
05 / TARGET
Recommended architecture

目标架构：共享语义面，隔离框架控制面与平台执行面

MindIE 不提供第三套模型框架，而是把现有 runtime layer 封装成 Ascend provider。公共包只定义可验证的量化语义、tensor/计划请求与上下文；SGLang/vLLM 适配器管理模型生命周期，MindIE runtime provider 复用原 layer 计算核心完成准备与执行。

边界 01
谁拥有模型图

永远由上游框架拥有。SGLang/vLLM adapter 创建各自的方法对象，再委托 MindIE runtime provider；MindIE 不返回模型、不替换并行 Linear、不接管模型构造和 loader。

边界 02
谁拥有 checkpoint 语义

公共 manifest 描述数学语义和 canonical storage，不在根配置硬编码 SoC/CANN/CUDA。msModelSlim 原始输出可保留；若只含 NZ 或其他厂商 layout，则必须标记为不可移植 variant，不能宣称“一份权重跨平台”。

边界 03
谁选择执行实现

平台插件回答“在哪种设备上运行”，provider registry 回答“用哪个算子库执行”。resolver 按 capability、用户 policy 与稳定优先级生成 ExecutionPlan；普通模型文件不出现 is_npu()/is_cuda() 分支。

边界 04
谁拥有物理 layout

provider 在权重完成 TP/FSDP shard 后执行 pack/transpose/reorder。Ascend 路径由 MindIE runtime layer 生成 NZ 等 opaque PreparedWeight；GPU provider 则生成 Marlin/CUTLASS 私有布局。二者互不解释内部状态。

边界 05
谁拥有 step

diffusion scheduler/engine 拥有 step；量化方法只消费上下文。若一个 batch 含不同 step，策略必须支持逐样本或在 scheduler 层按 quant policy 分桶。

边界 06
谁决定 fallback

配置与 capability resolver 共同决定，并在启动时冻结执行计划。运行中仅允许预声明的 FLOAT/FP8/W4A8 或 reference provider 回退；任何未声明回退都计入错误与指标。

06 / PORTABILITY
Cross-platform design audit

兼容性结论：接口能跨平台，packed 权重与 fused kernel 通常不能

“算法同名”不等于二进制兼容。真正可复用的是数学定义、tensor 语义、计划协商协议、运行时上下文与黄金向量；设备 dtype、packing、workspace、图捕获和 fused op schema 必须由 provider 拥有。

TWO-AXIS DISCOVERY

Platform ≠ Provider

CUDAPlatform 只提供设备、stream、通信与 graph 能力；cuda.cutlass、cuda.marlin、cuda.flashinfer 是并列 provider。Ascend 主入口为 ascend.mindie_runtime，其内部可按能力使用 ACLNN 或 MindIE custom op。用户可显式 pin，默认选择必须稳定且写入执行计划日志。

禁止：在 QuantSchemeSpec 中 import torch_npu/cutlass；禁止用平台名冒充算法名；禁止 provider 互相解释 opaque prepared weight。

共享

公式、logical dtype、scale/zero-point 语义、storage encoding、plan request、golden vectors。

Provider 私有

设备 dtype、pack/reorder、workspace、kernel symbol、stream/event、graph capture 与 autotune cache。

不可伪装可移植

FRACTAL_NZ、Marlin/CUTLASS 专用布局、NPU mode id、只对单一 kernel 校准的隐含 mul_scale。

证明方式

至少一个 torch reference provider + NPU 与 GPU 两个真实 provider，共用一组语义/反量化 golden。

刻意不做的“统一”：Linear、MoE 与 Attention 只共享 plan/capability 外壳，不共享一个带几十个 optional 参数的 execute 函数。各 op family 保留独立协议；否则抽象会退化成最小公分母，既不能表达 fused expert，也不能表达 varlen attention。
07 / CONTRACT
Runtime delegation lifecycle

上游管理生命周期，MindIE runtime layer 管准备与执行

不把 MindIE layer 拆散后复制到上游，而是增加窄外观接口。上游 Linear 仍注册参数、加载与分片；加载完成后把 tensor bundle 交给 MindIE prepare()，forward 通过 run() 委托现有 runtime 实现。

UPSTREAM

select + load

框架根据 layer、prefix 与 checkpoint 选择方法，注册参数并完成 TP/FSDP shard。

→
MINDIE RUNTIME

probe + prepare

校验设备/shape/dtype，把已分片 tensor 转成 NPU 专用布局与 opaque prepared state。

→
DELEGATE

run

上游传 activation、bias、stream 与 request context；MindIE runtime layer 调用现有 kernel 路径。

这是 facade，不是重写：现有 runtime layer 的算法与算子调用继续复用；只把“从文件/模型对象取数据”改为“接收 tensor bundle”，把进程全局状态改为显式 context。旧层若仍需自加载，可留兼容构造器；新 provider API 不调用它。上层改图逻辑完全不在此契约内。

09 / ADAPTERS
Framework-specific plan

框架适配器保持薄，硬件与加速库通过 provider 扩展

上游的 parallel layer、loader 与 runtime context 不同，适配层不能强行共用；Ascend 执行核心只维护在 MindIE runtime provider 一处。公共语义/SPI 允许 GPU 或其他加速库实现并列 provider，物理 weight transform 和 op wrapper 各自私有。

SGLANG

短期：分别落 SRT 与 multimodal_gen

  • SRT 继续使用 ModelSlimConfig → ModelSlimLinearMethod → scheme；SRTPlatform.get_quantization_config() 只做平台级覆盖，scheme 内再解析 provider。
  • diffusion 继续由 TransformerQuantLoadSpec 解析 config/safetensors，再把 quant_config 传入 DiT 的 parallel Linear。
  • 把 multimodal_gen 内引用 SRT scheme 的边界收敛为稳定 contract 包，避免反向跨子系统导入完整 SRT runtime 或设备库。
  • 每个 DiT 模型必须声明 packed_modules_mapping 和 checkpoint→runtime WeightsMapper。
  • Attention 走 multimodal_gen backend registry；不要塞进 Linear registry。
VLLM / OMNI

优先利用官方 OOT 注册与 component 路由

  • vLLM 的 OOT platform plugin 与 @register_quantization_config 是两个独立扩展点；NPU adapter 驻留 vLLM-Ascend，公共 scheme 不驻留其中。
  • vLLM-Omni 的 factory 只提供 diffusion 特有 override，CUDA/ROCm/NPU/XPU/MUSA 继续使用各自 Platform；能复用 core/provider 的就不要 fork。
  • ComponentQuantizationConfig 负责 transformer / text_encoder / VAE / stage 作用域，不把 BF16 组件错误套上预量化 method。
  • DiffusersLoader 必须保留 layerwise meta materialization、postprocess 幂等标志与 CPU offload 规则。
  • 每个 stage 自己解析磁盘 quantization_config；cascade 的 transformer 与 transformer_2 可有不同 fallback。
PROVIDER SPI

MindIE 是 Ascend provider，不是公共框架

  • ascend.mindie_runtime 以 entry point 或框架 registry 注册，声明 id/version/op_families；上游不依赖 MindIE 的模型/改图包。
  • probe() 返回精确 constraint 与 reason，不只返回布尔值；包含 arch、shape、dtype、layout、compile、TP 与 workspace。
  • resolve() 先满足语义和正确性，再按用户 pin、稳定优先级/benchmark profile 选择；结果可复现。
  • 第三方库只需实现某个 op family：例如 Marlin 只接 Linear，FlashInfer 只接 Attention，不必伪装完整平台。
  • MindIE provider wheel 只依赖公共 contract、torch_npu/CANN 与所需 custom-op wheel；SGLang/vLLM bridge 不反向导入旧框架层。

不可只看类名

QKV、gate/up 与 expert 可能在 runtime 融合。checkpoint 的三个 scale 是否允许合并，必须由 scheme 显式验证；“部分 shard BF16”应启动失败。

不可只看 prefix

prefix 要经过 model-owned mapper。字符串 replace 只能作为模型适配器，不应散落在通用量化配置里。

不可在 scheme 里堆平台分支

请求指定量化但 provider 不存在或 shape 不兼容时应 fail fast；只有 manifest/policy 声明的 fallback 才可执行。平台差异进入 registry/provider，不进入模型和语义对象。

10 / ABI
Runtime tensor contract

Runtime 接受规范化 tensor spec，不负责配置迁移

SGLang/vLLM adapter 从各自 checkpoint/config 得到规范化的 scheme 与 tensor 描述，再传给 MindIE runtime。下方 manifest 是跨平台接口示例，不要求 MindIE 新运行时读取旧 quant_model_description.json，也不把 legacy JSON 转换器列为加速库交付物。

{ "format": "quant.contract.v1", "producer": {"name": "msmodelslim", "version": "x.y"}, "component": {"name": "transformer", "namespace": "diffusers", "mapper": "wan22.v1"}, "layer": "blocks.0.ffn.proj", "scheme": { "id": "mxfp4.dualscale.v1", "semantics": {"weight": "fp4_e2m1", "activation": "fp4_e2m1", "fine_group": 32, "coarse_group": 512, "axis": "K", "rounding": "nearest_even", "accumulator": "fp32"} }, "tensors": { "weight": {"encoding": "packed_u8", "bit_order": "low_nibble_first", "layout": "K_MAJOR_CANONICAL", "shard_axis": "N"}, "fine_scale": {"dtype": "e8m0", "granularity": "K:32"}, "coarse_scale": {"dtype": "fp32", "granularity": "K:512"}, "mul_scale": {"dtype": "fp32", "granularity": "input_channel"} }, "requires": {"features": ["mx.fp4.e2m1", "scale.e8m0", "dualscale.v1"]}, "variants": [ {"id": "canonical", "portable": true}, {"id": "ascend-nz-cache", "portable": false, "provider": "ascend.aclnn", "cache_only": true} ], "extensions": {"org.ascend.msmodelslim": {"calibration_recipe": "wan22.v1"}} }

名称

声明 checkpoint namespace 与 mapper id；映射器由模型所有并可版本化。

布局

canonical storage 与 provider cache 分开；NZ/Marlin reorder 是加载后布局，不应伪装成算法 dtype。

分片

每个 tensor 声明 sharding axis；scale 的分片轴可能不同于 weight。

兼容

未知 format major、缺 tensor、部分 fused shard、online/offline 或 provider cache 版本错配均在执行前失败。

可移植性的硬边界：若 checkpoint 只有 NPU NZ、Marlin 或其他 provider 专用 packed variant，runtime 可以加载，但它是“受限 checkpoint”，不是跨平台 checkpoint。要承诺跨平台，必须同时提供 canonical variant，或提供经过黄金向量验证的离线转换器；不能在 loader 中猜测 bit order 和 scale 公式。
11 / FA + STEP
Diffusion-specific design

FA 量化与 timestep 是接入难点，不是 Linear 的附属参数

Linear 量化可以按 layer prefix 静态选 method；FA 的 Q/K/V 是运行时 tensor，timestep 又随请求推进。二者需要 attention backend 与 scheduler 共同参与。

量化 AttentionBackend 契约

  • 输入：Q/K/V、layout、mask、scale、sequence metadata、可选 rotation。
  • 能力：FP8/MXFP8/MXFP4、BNSD/BSND、varlen、SP/ring、torch.compile。
  • 选择：启动期按 platform/provider/arch/op/shape 决定候选；每次调用只做轻量 dispatch。
  • 交付：Ascend ACLNN/custom op、CUDA/ROCm attention 库分别作为 provider；缺失时只允许显式策略 fallback。
  • 观测：记录 chosen platform/provider/version、quant mode、fallback count 与 padding overhead。

请求级 StepQuantPolicy

  • 由 scheduler 把 step_index、sigma/timestep 与 policy id 放入 forward context。
  • 策略是纯函数：(layer, step, shape) → W4A4 | W4A8 | FP8 | FLOAT。
  • 同一 batch 策略不同时：优先按 mode 分桶；不支持逐样本 kernel 时禁止混跑。
  • torch.compile 图按有限 mode/shape 建缓存，避免把任意 Python 字典捕获进图。
  • 取消、重试和 stage 解耦必须携带 step/policy，不能读取 worker 全局变量。
关于 rotation：离线校准的 q_rot/k_rot 与在线生成 Hadamard rotation 不是等价 checkpoint。manifest 必须标注 rotation 来源、seed、head_dim 与应用顺序；模型 fusion 若改变 Q/K head 排布，rotation 也必须跟随重排。
12 / ADR
Decision ledger

六项关键架构决策

以下 ADR 建议作为实施前的评审基线；状态均为 Proposed，需由 MindIE、SGLang、vLLM-Ascend/Omni 及至少一个非 Ascend provider 维护者共同确认。

ADR-001
PROPOSED
MindIE 的新交付单元是 runtime layer/provider，不是模型框架。

现有 Linear/MoE/FA 执行实现通过 probe/prepare/run facade 复用；SGLang/vLLM 自己拥有模型图、参数和 loader。历史 graph rewrite 继续兼容但明确不进入依赖图、路线图和新 API。

ADR-002
PROPOSED
runtime tensor ABI 表达数学语义与 canonical storage，不绑定某设备布局。

adapter 负责把所在生态的 config/checkpoint 解析成 normalized spec；MindIE runtime 只消费该输入。这样 NPU provider 可生成 NZ，GPU provider 可生成 Marlin/CUTLASS 布局，而不要求 MindIE 维护旧配置转换链。

ADR-003
PROPOSED
平台发现与 kernel provider 发现采用两个正交注册表。

vLLM/SGLang platform 回答设备/runtime；provider 回答 Linear/MoE/Attention 实现。同一 CUDA/NPU 可有多个 provider。拒绝“每平台复制全部 scheme”和“一个万能 kernel API”：前者重复，后者退化为最小公分母。

ADR-004
PROPOSED
物理 weight transform 在分片后由 provider 拥有，PreparedWeight 不透明。

正向：容纳 NZ、Marlin、CUTLASS、AITER 等专用 reorder 与 workspace；负向：跨 provider cache 不能复用。cache key 必须包含 scheme、provider/version、arch、shape、sharding 与 layout id。

ADR-005
PROPOSED
FA 量化从 LinearQuantizationConfig 分离。

可在顶层 QuantPlan 中组合 linear 与 attention 子计划，但执行时分别走 LinearMethod 与 AttentionBackend provider；避免让 checkpoint weight scheme 决定所有运行时 attention 行为。

ADR-006
PROPOSED
禁止未声明的 provider 或精度回退。

op、shape 或 runtime 不满足时启动失败；仅 policy 中明确的 provider 次序及 BF16/FP8/W4A8/reference fallback 可执行并暴露指标。代价是首次接入更严格，收益是可复现且不会“看似量化、实际浮点”。

13 / ROADMAP
Runtime-first delivery plan

五阶段交付：先稳定 MindIE runtime，再由上游接入并跨平台验约

MindIE 团队的责任止于 Ascend runtime provider、数值参考和能力声明；SGLang/vLLM adapter 由对应集成侧完成。GPU provider 用来证明公共 SPI 没有泄漏 NPU 语义，不要求 MindIE 团队实现或维护 GPU kernel。

PHASE 0 · 1–2 周

冻结 runtime 边界

盘点可复用 Linear/MoE/FA layer 与 op；冻结 probe/prepare/run、tensor bundle、prepared state、context 和错误模型。旧 graph/config/loader 不进入包依赖。

EXIT → runtime wheel 可独立 import；依赖图中没有模型改写模块
PHASE 1 · 2–3 周

Ascend W8A8 切片

用 facade 包住现有 W8A8 static/dynamic runtime layer；外部 tensor 在分片后 prepare，forward 委托原 NPU kernel；补纯 torch reference 与 golden。

EXIT → 算子实现未复制；runtime API 独立通过数值、shape 与 capability 测试
PHASE 2 · 3–4 周

两个上游桥接

分别实现 SGLang 与 vLLM-Omni QuantMethod/AttentionBackend bridge，沿用各自 loader、TP/FSDP、component config 与 mapper，只把 tensor 和 context 交给 MindIE provider。

EXIT → 两框架不改图、不绕 loader；严格权重覆盖 100%
PHASE 3 · 3–5 周

扩 runtime 能力

按同一 facade 纳入 MXFP8/MXFP4/DualScale、FA、MoE；把 step 改为显式 context 输入，custom op 独立版本握手。

EXIT → 所有 Ascend 路径可 probe；FA 不依赖模型字段注入；并发 step 无污染
PHASE 4 · 2–4 周

跨平台验约

由 CUDA/ROCm 现有加速库实现同一 SPI 的一个真实切片，共用 scheme/golden，验证公共接口没有 NZ、CANN mode 或 MindIE class 泄漏。

EXIT → 新 provider 不改模型代码与公共 scheme；MindIE 仍只维护 Ascend runtime
PR 拆分建议：runtime facade、W8A8 provider、reference/golden、SGLang bridge、vLLM/Omni bridge、MX/FA/MoE provider、custom-op wheel、显式 context、跨平台 conformance 分开提交。不要把旧 graph rewrite 或配置框架清理混入这些 PR；它们既不阻塞新接口，也不是本方案范围。

15 / RISKS
Failure modes

最可能让“能跑”变成“不能交付”的风险

R1 · HIGH

权重名即隐形 ABI

Diffusers、msModelSlim 与 runtime fusion 名称不同。缓解：model-owned mapper + manifest mapper version + strict coverage。

R2 · HIGH

scale 分片错轴

weight、fine scale、coarse scale、mul_scale 的 TP 轴不同。缓解：tensor spec 声明 shard axis，单独测试 Row/Column。

R3 · HIGH

step 状态串请求

全局 manager 在异步/连续批处理下污染结果。缓解：context 显式传递，策略分桶与并发回归。

R4 · MED

在线/离线语义混淆

DualScale offline 有 calibrated mul_scale，online 没有。缓解：serialized flag + tensor presence + mode mismatch fail-fast。

R5 · MED

provider ABI 漂移

PyTorch、CANN/torch_npu、CUDA/ROCm 与第三方 op schema 组合变化。缓解：独立 wheel、版本握手、fake/meta、兼容矩阵和 lazy probe。

R6 · MED

优化组合非交换

量化与 QKV fusion、LoRA、offload、SP/ring、compile 组合可能改变布局或误差。缓解：按组合验收，不从单项通过推导组合通过。

R7 · OPS

两上游版本漂移

vLLM/SGLang method 与 loader 接口频繁演进。缓解：薄 adapter、受控版本窗口、每月 rebase CI。

R8 · QUALITY

只看最终图片

最终像素可能掩盖中途爆炸或偶然收敛。缓解：latent trajectory、敏感层输出与语义指标联合门禁。

R9 · LICENSE

代码搬运边界

MindIE SD 为 Mulan PSL v2，上游多为 Apache-2.0。缓解：法务确认；优先重写适配器、保留来源与许可证头。

R10 · HIGH

厂商语义泄漏

把 NZ、CANN mode id 或某个 CUTLASS layout 写进公共 scheme，会让“跨平台”只剩改名。缓解：schema review 要求 reference 公式；厂商字段必须 namespaced extension。

R11 · MED

provider 选择漂移

安装一个新库后默认实现变化，可能改变数值或性能。缓解：稳定优先级、plan 日志、production pin、升级时重新跑 golden/benchmark。

R12 · MED

过度抽象成最小公分母

万能 execute 接口无法表达 fused MoE/varlen FA，又给每条路径增加间接层。缓解：只共享 plan 外壳，Linear/MoE/Attention 保留独立协议；无第二实现不抽 SPI。

R13 · HIGH

历史框架反向渗透

若 runtime wheel 为复用一个 layer 又导入 graph rewrite、模型 registry 或旧 loader，上游仍会被重框架绑住。缓解：依赖图门禁 + 独立 import test；只允许 runtime/common-op 方向依赖。
