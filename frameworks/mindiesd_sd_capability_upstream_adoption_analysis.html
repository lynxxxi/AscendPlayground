01 / METHOD & METRICS
Evidence before score

先定义“接入”，再谈覆盖率

本报告的证据来自五个上游仓库与 MindIE-SD 仓库的本地默认分支快照，全部结论可由文件路径、导入语句、注册表和枚举值复核。评分衡量的是 MindIE-SD 被上游采纳的程度，不是上游自身能力的强弱：一个社区即使把同类算法做得很完整，只要没有接入 mindiesd，本表就不会给它高分。

事实 可在仓库/文档直接验证样本 有窗口或快照限制推断 从事实推导的分析目标 建议项，不是现状

五个被审计社区，三种角色

  • 服务化框架：vLLM-Omni（多模态服务）、SGLang（LLM + multimodal_gen 扩散栈）。
  • 模型生态框架：DiffSynth-Studio（面向 diffusers 的模型/训练引擎）。
  • 专业生成框架：FastVideo（视频 DiT 训练+推理）、LightX2V（轻量视频生成、多平台算子层）。

为什么必须区分“接入”与“移植/平行实现”

  • 运行时接入：存在 import mindiesd 或 find_spec("mindiesd")，能力由 MindIE-SD 提供。
  • 代码移植：把 MindIE-SD 的算法代码搬进上游，只换算子命名空间（已发现一例且无署名）。
  • 平行实现：上游用 torch_npu、sgl_kernel_npu、fastvideo_kernel 自研同名能力。
  • 参考实现：只在上游注释里被引用为设计来源，无代码依赖。
  • 四者对“MindIE-SD 生态位”的含义完全不同，因此必须分开计分。

04 / VERDICT
Executive readout

不是“MindIE-SD 不够强”，而是它把接入成本推给了每一个上游

同样的 RainFusion，在 vLLM-Omni 里是带能力门禁、typed 配置和文档的一等后端；在 LightX2V 里是一个绕过公开 API 的 assert；在 SGLang 里则连算法代码带 kernel 参数表被整体搬走，却不留依赖、不留署名。差异不在内核质量，而在接入契约：谁提供了注册表、枚举、typed 配置和回退路径。

已观察事实

vLLM-Omni 是唯一真正落地的接入

NPU 平台上，FLASH_ATTN 是否成为默认扩散注意力后端，直接取决于 importlib.util.find_spec("mindiesd")；RAINFUSION_ATTN 有独立枚举、typed 配置、专门文档页与单测；USP 通过 AscendUSPExecutor 做能力探测 + USPError 门禁 + 原生实现回退。

结构缺口

缓存、显存、时间步量化三项全线失守

Cache 得分最高的社区只有 2 分，且都是自研替代：FastVideo 的 TeaCache、LightX2V 的 KV Cache 池、DiffSynth 的两份重复 TeaCache。Offload 与显存共享同样如此。MindIE-SD 的 CacheAgent 在这五个仓库里出现次数为 0。

生态推断

“同名不同源”已经开始固化

SGLang 的 RAIN_FUSION_ATTN、LASER_ATTN、BLOCK_SPARSE_ATTN 与 MindIE-SD 的 rain_fusion_attention、ascend_laser_attention、block_sparse_attention 名字几乎一一对应，而其中 RainFusion 一路是带着 MindIE-SD 的参数表与辅助函数搬家、却没有署名、也没有 import。命名趋同会掩盖依赖关系的缺失，使“昇腾稀疏注意力”长期存在两套并行实现，并叠加一层 Mulan PSL v2 → Apache-2.0 的归属待澄清问题。

一句话策略：MindIE-SD 下一步不该再扩能力清单，而应该把已有能力改成可注册的插件形态——发布 diffusers AttentionProcessor、vLLM 风格 QuantizationConfig、CacheBackend 基类，并把私有子模块路径（sparse_flash_attn_rf_v2.rain_fusion_attention）正式提升为公开 API。接入成本每降一档，覆盖分会立刻从 1.5 上移。

_mindiesd_supports_precision() 检测已安装的 sparse_attention 是否接受 precision=；旧版本会通过 **kwargs 静默忽略该参数并跑 BF16，因此 vLLM-Omni 选择在请求非 bf16 时直接抛错，而不是静默降级。

正式后端而非隐藏开关

RainFusion 拥有独立枚举值、BlockSparseSpec typed 配置、专门用户文档页、以及 tests/diffusion/attention/test_rainfusion_plan.py 覆盖 validate_available 与精度门禁分支。

回退是显式契约

USP 执行器在契约不满足时返回 None，由上层通用注意力层继续用自己的 Ulysses/Ring 实现；注释明确写出“不重复实现集合通信”。这是把“回退”当成接口的一部分来设计。

仍未覆盖的部分

Cache / Offload0 处使用 CacheAgent、enable_offload 或 share_memory；vLLM-Omni 自己的扩散缓存栈是 cache_dit + teacache/stepcache/mag_cache，offload 用自研 diffusion/offloader/。
时间步量化未观察到 TimestepManager/TimestepPolicyConfig 的调用；NPU 量化走自己的 config 体系。
Linear 量化quantization/mxfp4_config.py 在注释中引用 MindIE-SD 的 W4A4MXFP4QuantLinear 与 W4A4MXFP4DualQuantLinear 作为设计来源，但实现基于 torch_npu，属参考实现而非运行时依赖；mxfp8_config.py、int8_config.py 同理。
编译后端NPUOmniPlatform.supports_torch_inductor() 返回 False，NPU 上 torch.compile 被主动关闭，因此 MindieSDBackend 完全不可用；vLLM-Omni 接入的只是导入 side-effect（算子路径注册），不是编译后端。
融合 MoE 与残差算子NPU 的 fused_moe 走 vllm-ascend（AscendMoERunner）；muls_add、residual_gate_add、scale_shift、get_activation_layer、frequency_regulator 均未取自 mindiesd。
DyEPLBvLLM-Omni 的 MoE 负载均衡沿用 vLLM 体系，未见 mindiesd.eplb。

维度观察到的做法暴露的问题

接入建议与一个不利条件：正确切入点是新增一个 NPU 注意力后端（把 FLASH_ATTN 与 BSA_ATTN 映射到 mindiesd.attention_forward 与 mindiesd.sparse_attention），按 docs/contributing/attention_backend.md 的 5 步清单施工，并参照 nabla.py 的模块 docstring 风格声明 SP 支持缺口。但要注意：fastvideo/tests/attention/ 与 fastvideo/tests/layers/——正是 MindIE 后端单测与融合算子对齐测试的天然落点——被 tests/contract/test_ci_test_collection.py 显式列入“无 CI lane”白名单；CI 全部跑在 Modal 的 H100/L40S 上，GitHub 侧不跑任何 pytest。因此新增的 NPU 路径在当前配置下无法被 CI 看护，只能本地手工验证。此外 FASTVIDEO_ATTENTION_BACKEND 是性能基线记录的 identity 字段之一，新后端需要配套一份全新的性能基线。
09 / LIGHTX2V
Single-slot runtime dependency

唯一第二个真跑 mindiesd 的社区，但只有一条 op 槽位、一个私有 API

LightX2V 的 lightx2v_platform/ 是一套设计良好的多平台算子注册体系（attn / mm / norm / rope 四类 × 九种硬件平台），理论上可以逐槽替换成 MindIE-SD。现实中它只填了一格：ascend_npu 的 RainFusion 注意力，而且调用的是 MindIE-SD 的私有子模块路径。

全仓只有 1 个文件、6 处 mindiesd 引用，全部在 lightx2v_platform/ops/attn/ascend_npu/npu_rainfusion_attn.py。同目录下的 npu_flash_attn.py、npu_rms_norm.py、npu_layer_norm.py、npu_rope.py、mm_weight.py 一律使用 torch_npu。

四个更深层的问题：依赖、代际、注册表与打包

它其实是最好的接入载体，却没有被用满

注册体系完备

  • registry_factory.py 暴露 device / attn / mm / rms / layernorm / rope 六个注册表，装饰器支持 @REG("key") 与裸 @REG 两种写法。
  • 另有跨平台层 ATTN_WEIGHT_REGISTER（lightx2v/common/ops/attn/），已注册 flash_attn2/3/4、sage_attn2/3、ulysses、ring、rainfusion_attn、svg_attn 等约 30 项。

但其余槽位全部指向 torch_npu

10 / CROSS-CUTTING PATTERNS
What actually gates adoption

决定接入成败的四个结构性因素

把五个社区的差异拆开看，接入率并不取决于社区规模，也不取决于 NPU 是否被官方支持，而取决于下面四件事是否成立。

01 / REGISTRY上游有没有注册表有注册表：vLLM-Omni、LightX2V、FastVideo、DiffSynth（量化侧）。无注册表：DiffSynth（注意力侧）。
02 / PUBLIC APIMindIE-SD 暴露的接口形态公开函数可直接替换；私有子模块路径会把接入变成版本脆弱的硬绑定。
03 / FALLBACK失败时怎么办返回 None/回退原生实现可被接受；assert 与静态异常会挡住真实部署。
04 / CI有没有人替它看门只有 vLLM-Omni 把 NPU + mindiesd 路径放进 ready/nightly pipeline。
05 / SEMANTICS算法层归谁上游自己算稀疏掩码、自己管 cache 时，MindIE-SD 只剩内核位置。

阻断点分类：MindIE-SD 侧 vs 上游侧

阻断点归属证据消除方式
缺少框架级插件入口：没有 AttentionProcessor / CacheBackend / 官方 QuantizationConfig 适配层MindIE-SD 侧五个社区里，凡是需要改自己模型代码才能接入的能力（C8/C9/C6/C12/C14）得分全部 ≤ 2发布 diffusers AttentionProcessor 与 vLLM 风格 QuantizationConfig，把接入从“改模型”降级为“注册”

公开 API 覆盖不足：真实接入方要下沉到私有子模块MindIE-SD 侧LightX2V 调用 sparse_flash_attn_rf_v2.rain_fusion_attention；该路径参数（select_idx 等）未被 sparse_attention 公开把带掩码入参的内核入口提升为公开 API，或提供“自算掩码”模式

同名内核平行实现 / 代码移植：sgl_kernel_npu 的 attentions 提供同名能力，RainFusion 一路则直接搬运了 MindIE-SD 的算法代码上游侧SGLang 的 LASER_ATTN/BLOCK_SPARSE_ATTN 走 attentions；RAIN_FUSION_ATTN 与之同名，但算法与辅助函数（含 docstring）与 MindIE-SD 逐项一致MindIE-SD 需要证明内核层面的可比收益，或与 sgl-kernel-npu 明确分工；同时需澄清移植代码的归属与许可
注意力层无注册表：模块级冻结常量 + if/elif上游侧DiffSynth core/attention/attention.py 的 ATTENTION_IMPLEMENTATION可先用 monkey-patch 方式接入（DiffSynth 已有 NPU 补丁先例），最好推动上游引入注册表
NPU 平台分支写死：只允许 SDPA、显式关闭 torch.compile上游侧FastVideo platforms/npu.py 的两处向上游提交 NPU 后端实现，复用现成的 AttentionBackend 契约
闭源枚举 + 硬校验：新增后端必须改主仓；--attention-backend 对未知名字直接 ValueError上游侧SGLang server_args.py 的 _normalize_attention_backend_name、dits/base.py 的逐模型白名单、denoising.py 的元数据 if/elifMindIE-SD 可先在 sglang.srt.platforms 式的 entry-point 机制上争取一等公民，但 MM 侧插件体系尚不存在（代码里仍是 TODO）
算子命名空间不互操作：torch.ops.attentions.*/torch.ops.npu.* 与 torch.ops.mindiesd.* 无 ABI 兼容双方SGLang 的四个 NPU 后端全部指向 sgl_kernel_npu 与 torch_npu需要一层适配而不是替换；这决定了 SGLang 接入的真实工程量
代际/SoC 无门禁：上游硬编码 rf_v2，而 MindIE-SD 在 A5 上对 rf_v2 抛错、自己的 sparse_attention 会自动路由 rf_v3MindIE-SD 侧LightX2V npu_rainfusion_attn.py 固定调用 rain_fusion_attention把代际路由保留在公开 sparse_attention 内，并提供 SoC 能力查询，让上游无需硬编码策略名
代码移植无署名：算法实现被搬走但未声明来源上游侧SGLang rain_fusion_attn.py 无 SPDX/attribution 头，参数表与辅助函数（含 docstring）与 MindIE-SD 逐项一致；许可为 Mulan PSL v2 → Apache-2.0需要 MindIE-SD 侧主动澄清归属与许可，否则“同名不同源”会同时带来合规与升级同步风险
打包与文档缺位：mindiesd 不在 requirements、不在 Ascend 镜像、不在任何文档双方LightX2V 全仓唯一安装指引是代码注释；vLLM-Omni 的安装说明只存在于 4 个模型 recipe；FastVideo/DiffSynth 完全没有MindIE-SD 应发布“上游接入手册”，上游应把可选依赖写进 extra 与平台镜像
归因结论：十三条阻断点里有六条完全在 MindIE-SD 自己手里（缺插件入口、文档与实现不一致、公开 API 覆盖不足、并行能力以文档代替 API、文档内部矛盾、代际路由要求上游硬编码），且都不涉及算法或性能。这意味着当前 1.5 的覆盖分有相当大的改善空间是低成本的；真正需要长期投入的只有“算子命名空间互操作”与“上游闭源注册表”这两条，它们需要与上游共同设计。
11 / ROADMAP
From capability to adoption

按“降低接入成本”排序的四阶段

目标不是再增加能力，而是让已有能力被更多社区加载进运行时。每个阶段的验收标准都写成可核对的仓库状态，而不是主观感受。

PHASE 0 / 2 周

接口与文档自洽

  • 删除或补齐文档中的 Linear；把 muls_add/residual_gate_add/SparseLinearAttention 提升到顶层 __all__。
  • 把 MindieSDBackend 注册成具名 torch.compile 后端（torch_dynamo_backends entry point），否则按名字选择后端的框架永远发现不了它。
  • 在 parallelism.md 中标注 TP/CFG/Ring 的实际实现状态，消除与 usp.md 的矛盾。
  • 为 sparse_attention 增加“调用方自带 select_idx”的公开模式，并把 SoC 代际路由纳入公开 API。

发布可注册的插件形态

  • diffusers AttentionProcessor：让 pipe.transformer 一行切换 FA / RainFusion。
  • vLLM 风格 QuantizationConfig 适配层，便于 SGLang 与 FastVideo 复用其既有注册表。

PHASE 2 / 4–8 周

把 vLLM-Omni 契约产品化

  • 发布 mindiesd.capabilities.has_capability()，替代上游自建的 5 处 find_spec 与 3 个 inspect.signature 探测。
  • 发布《上游接入手册》，以 vLLM-Omni 的门禁 + 回退模式为参考实现，并给出每个能力的版本下限（这是上游唯一缺的那块，才能写出 mindiesd>=X）。
  • 为每个公开能力规定“缺失时的推荐回退分支”，避免上游写 assert 或让 find_spec 通过却崩溃。
  • 澄清 SGLang 侧代码移植的归属与许可问题。

PHASE 3 / 8–16 周

攻真实接入位

  • SGLang：把 LASER_ATTN 与 RAIN_FUSION_ATTN 的内核经适配层切到 mindiesd，保留既有枚举与平台分派（需先解决算子命名空间互操作）。
  • FastVideo：新增 NPU 注意力后端替换写死的 SDPA，替换 get_device_capability() 的能力代偿，并修复 SP 预热里写死的 CUDA 设备。
  • DiffSynth：先以 NPU 融合算子补丁方式接入 C3（已有 Z-Image 先例），再推动注意力注册表；同时为其接入一台可跑测试的 CI。
