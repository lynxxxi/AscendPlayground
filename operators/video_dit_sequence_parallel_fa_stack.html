01先回答五个问题

Q1 · 我该用 Ring 还是 AllGather？

取决于瓶颈是显存还是延迟，而视频 DiT 的答案和 LLM 不同。 AllGather 的显存是常数级的（完整 KV 一份，不随 P 下降）；Ring 是 1/P。 但 Ring 的通信量约为 AllGather 的 2 倍，且每轮一个同步点。 视频 DiT 的序列虽长（Flux.1 在 4096px 时达 420 万 token）， 但它非因果、且 KV 长度与 Q 长度相同——这既让 Ring 免于因果不均衡， 也让 AllGather 的显存压力在当前主流分辨率（720P/768P，约 10 万 token 量级）下通常还能承受。 所以：现在多数团队选 AllGather/Ulysses 是合理的；只有当你要冲更高分辨率或更长视频、 显存真正爆掉时，Ring 才是必需。

Q2 · 稀疏叠上序列并行，最大的坑是什么？

负载不均衡，而且它分两个层次。 db-SP 量化了这个坑：稀疏不均衡比 ρ_s（最重 rank ÷ 平均负载） 在视频任务上实测 1.159–1.513。含义很直接—— 稀疏省下来的算力，有 16%–51% 会被最慢的 rank 吃掉。 更关键的是：Ring 的 ρ_s 系统性地低于 Ulysses（1.25–1.27 vs 1.36–1.51）， 因为 Ring 沿序列/块划分，把头间的稀疏度差异摊薄了。

Q3 · 那是不是应该用运行时负载均衡？

在少步蒸馏场景下，是。 FVAttn 实测：相邻去噪步之间，同一 head 的密度变化最高 97%， 同一 rank 的负载变化最高 44%。 这意味着任何「提前预测布局」的方案都在用过期信号做决策。 FVAttn 的做法是等掩码真正生成出来、看到真实负载后再用受限 P2P 迁移修复， 把不均衡从 1.34 压到 1.08，attention 相对 FlashAttention 4.41×。

Q4 · 有没有办法从源头避免这个问题？

有，而且这是 OSP-Next 最重要的贡献，也是我认为最值得你研究的方向。 db-SP 和 FVAttn 都是在「稀疏已经产生不规则负载」之后去补救。 OSP-Next 换了个思路：直接设计一种稀疏模式，使它在序列并行下天然均衡—— Skiparse-2D 的稀疏子序列长度相等，因此切到各 rank 后天然负载均衡， 且切换稀疏模式只需要一次 All-to-All（Ulysses 需要 4 步）。 结果是通信量降低 75%，而且它完全不需要负载均衡器。

Q5 · 量化能和稀疏、序列并行一起上吗？

能，OSP-Next 已经做到了，而且是在昇腾上验证的。 OSP-Next 把 稀疏微调与 8bit（HiF8）量化联合训练， loss 曲线与 BF16 几乎重合，VBench 只掉 0.4%， 在 Ascend 950PR 单卡上拿到 2.27×（768P）。 但要注意它的量化是 per-tensor 粗粒度的 HiF8——这与「细粒度 FP8 才能保精度」的常规认知相反， 原因是 HiF8 的动态范围更大，所以可以靠粗粒度量化省掉 per-token/per-block 的 scale 归约开销。 这条结论对你的算子选型有直接影响。

02视频 DiT 的战场为什么和 LLM 不同

这一点必须先讲清楚，因为它决定了后面一半的结论是否成立。

维度自回归 LLM视频 / 图像 DiT对 attention 算子的影响
注意力类型 causal（下三角） full attention（非因果） Ring 的因果三角负载不均衡（1:2:…:P）在 DiT 上不存在， zigzag / Striped 那套修正不需要
Q 与 KV 长度 decode 时 Q=1、KV 很长 Q 与 KV 等长（都是整段时空 token） DiT 是 compute-bound；LLM decode 是 memory-bound。 「把 LLM 推理系统直接搬到 DiT」是不可行的（xDiT 原话）
是否流式 逐 token decode，KV 持续增长 整段前向，多去噪步重复同一形状 量化 scale 不会随序列漂移；但稀疏掩码会逐去噪步变化（FVAttn 实测步间变化 97%）
序列量级 32K–1M Flux.1 1024px ≈ 26.2 万 token；4096px ≈ 420 万 token； CogVideoX 1 分钟 4K ≈ 400 万 token 序列并行必须做，且是长时空序列而非单纯长文本
条件注入 — MM-DiT 把 text 与 image 拼接在同一条序列上（SD3/Flux/CogVideoX） 切序列时条件和图像都要切，否则条件张量被复制、 且编码部分无法并行（xDiT 明确：只切图像序列「is not feasible」）
模态结构 一维序列 三维（T×H×W）时空结构，存在强局部性 这是最大的机会：稀疏可以按空间维度设计， 而不是退化成任意的一维掩码——OSP-Next 正是吃这一点

两个直接推论

  1. 「非因果」把 Ring 的实现难度降低了一大截。 不需要处理因果跳过、不需要 zigzag 配对、每轮所有 rank 的块都是稠密满算。 如果你要自己实现 Ring，DiT 是比 LLM 更友好的起点。
  2. 「三维局部性」是稀疏的天然抓手。 视频的注意力冗余不是随机的，而是沿空间/时间邻域聚集。 这意味着你可以设计规则化的稀疏模式（可预测、可切分、可均衡）， 而不必依赖动态的、不规则的 token 选择——后者恰恰是与并行化冲突的根源。

但有一个例外要注意：自回归视频生成

如果目标是自回归视频生成（如 Magi-1，约 400 万 token）， 掩码形态会变成 varlen block-causal。 这时「非因果所以没有不均衡」的结论不再成立： 不规则掩码会让每个 rank 的实际计算量产生差异， 而且 Ring 的 P2P 会引入 >33% 的传输冗余（MagiAttention 定量，对比简单 causal 的 25%）。 所以请先确认：你的目标是双向 DiT（Wan/Flux/CogVideoX 类）还是自回归视频（Magi-1 类）。 本文结论对前者更直接适用。

03db-SP：把不均衡算清楚

Siqi Chen, Ke Hong, Tianchen Zhao, Ruiqi Xie, Zhenhua Zhu, Xudong Zhang, Yu Wang（清华大学）· arXiv:2511.23113 · 2025-11-28 · abs · code

3.1 它定义的指标是本领域的通用语言

db-SP 的核心贡献之一是形式化了 稀疏不均衡比 ρ_s—— 最重 rank 的负载 ÷ 全部 rank 的平均负载。这个量的物理意义是 「做完美均衡后理论上能拿到的加速比」，因为序列并行在每个同步点都要等最慢的 rank。

# 通用定义（按同步周期 i 求和）
ρ_s = Σ_i max_{g∈G}( b_{i,g}(s,p) ) / [ Σ_i Σ_{g∈G} b_{i,g}(s,p) / |G| ]

# b_{i,g} = GPU g 在第 i 个同步周期内的稠密块数
# s = 稀疏模式，p = 并行策略

# Ring / Ulysses 各自的特化形式：
Ring: ρ_s = Σ_i max_g(b_{i,g}) / avg ← 每个 ring step 一个同步点
Ulysses: ρ_s = max_g(b_{0,g}) / avg ← 只有 attention 后一个同步点

这张表告诉你三件事

  1. 不均衡是真实且显著的：最高 1.513，意味着 51% 的潜在加速被浪费。 「稀疏 + 序列并行」不是免费的组合。
  2. Ring 在这个维度上比 Ulysses 更优。 Ulysses 沿 head 切分，而稀疏度恰恰是逐 head 差异最大的量， 于是差异被直接放大到 rank 级。Ring 沿序列/块切分，把头间差异摊薄了。 这为「为了省显存选 Ring」提供了一个额外的、独立的理由。
  3. 越激进的稀疏，不均衡越严重（PAROAttention 1.26 → SpargeAttn 1.51）。 如果你打算用高稀疏率换性能，必须同步准备均衡机制。

db-SP 观察到头级和块级的不均衡是耦合的，直接联合优化会得到一个不可解的问题。 它用一个关键先验把问题解耦：每个层级都能独立达到接近完美的均衡。 于是拆成两个顺序子问题：

04FVAttn：运行时修复而非预测

Hao Liu（中山大学 / 腾讯微信 HPC）、Chenghuan Huang、Ye Huang、Zhiying Wen、 Hao Liu、Mohan Zhang、Chen Li、Ziyang Ma、Jing Lyu、Jiangsu Du · arXiv:2607.16190 · 2026-07-17 · abs

4.1 它从少步蒸馏场景的实测出发，直接挑战 db-SP 的前提

FVAttn 的出发点是一个很硬的观测：在 4 步蒸馏的 Wan2.2 I2V 上，

观测对象相邻步最大变化后果
同一 head 的注意力密度97%任何基于历史/离线 profile/近似相似度的预布局都建立在过期信号上
同一 rank 的负载44%

它还指出了一个更根本的时序问题： 在 Ulysses 风格并行下，当前层的真实负载只有在 「序列→head 的 All-to-All 完成、且当前稀疏掩码被 materialize 之后」才可观测。 所以「预调度」在原理上就拿不到准确输入。而「掩码后全局重划分」虽然能用真实负载， 却需要再一次大规模集合通信，把稀疏省下来的收益又吃掉。

4.2 它的洞察：负载倾斜高度局部化

不需要全局重排，只需要搬走少数几个「重头」

FVAttn 的关键观察是：Top-p 路由造成的负载倾斜集中在少数几个 head 上， 而不是均匀散布。所以把几个稠密 head 从过载 rank 迁到有空闲的 rank， 就能消除大部分掉队时间——代价只是极小的 P2P 流量。

实测：只迁移 20% 的本地 head（8 卡下即每 rank 1 个）， 就把平均不均衡从 1.34 降到 1.08。继续增加迁移预算收益很小。

05OSP-Next：让稀疏天然可并行

Yunyang Ge, Xianyi He, Zezhong Zhang, Bin Lin, Bin Zhu, Xinhua Cheng, Li Yuan （北京大学 PKU-YuanGroup / 南洋理工 / Rabbitpre AI）· arXiv:2605.28691 · 2026-05-27 · abs · code

为什么这篇最重要

db-SP 与 FVAttn 解决的是「稀疏已经产生了不规则负载，怎么补救」。 OSP-Next 解决的是「怎么设计稀疏，使它一开始就不会产生不规则负载」。 前者是调度问题，后者是协同设计问题——而后者才是根治。 更关键的是：它是目前唯一在视频生成上把「稀疏 + 序列并行 + 8bit 量化」三者跑通的系统， 并且给出了 Ascend 950PR 的实测数据。

5.1 Skiparse-2D Attention：规则稀疏，且原生兼容 FlashAttention

背景：Open-Sora Plan v1.3 首先提出 Skiparse-1D——把视频拍平成一维序列， 交替施加 token-wise skip 与 group-wise skip 两种稀疏注意力。 OSP-Next 把它扩展为 Skiparse-2D：沿 height 和 width 两个维度正交地施加同样的模式。

# 稀疏比 k（skip interval）
token-wise / group-wise 均把序列维降到原来的 1/k，
同时把 batch 维放大 k 倍 → attention 总计算量降为 1/k

# 关键性质：任意两个 token 至多经过 2 次 attention 操作即可交互
# 这正是「交替 token-wise 与 group-wise」的设计目的

为什么 2D 比 1D 好

  • 符合图像/视频的二维局部性：1D 拍平后，空间相邻的 token 可能无法在一次 attention 内交互， 必须借助中间 token。
  • 全局 token 的交互模式与 2D 结构对齐——1D 下这个模式是错位的。
  • 稀疏率越高，1D 的缺陷越明显。
  • 任意分辨率下更稳定：1D 方案在 any-resolution 训练时， 同一空间位置在不同形状视频里可能被分到不同子序列，交互模式不一致，难以优化。

为什么「规则」是算子友好的关键

这是我认为最值得你借鉴的一点：

  • Skiparse-2D 避免了在序列维上动态构建 2D 掩码。 当 H、W 都是 k² 的倍数时，掩码直接为 None；否则也只是一维掩码。
  • 因此它原生支持 FlashAttention kernel，不需要自定义 Triton/CUDA， 也避免了其他稀疏方法所需的 FlexAttention 编译开销。
  • 对比：动态 token 选择类方法「需要动态构建注意力掩码，通常用 FlexAttention 或 为稀疏专门优化的内核实现，难以与高效 FlashAttention 内核原生集成」， 且「不规则掩码难以并行化，会导致 rank 间负载不均衡」（论文原话）。

5.2 Sparse Sequence Parallel (SSP)：一次 All-to-All 解决稀疏切分

核心机制：Skiparse Rearrange 的「局部等价性」

Skiparse 的第一步是 Skiparse Rearrange：把原序列切成多条子序列， 沿 batch 维拼接后再并行算注意力。

OSP-Next 发现这个 rearrange 具有 local equivalence（局部等价）： 对整条序列做 rearrange，等价于独立地对每个最小可重复单元做 rearrange。 而这个最小单元是一个 k² × k² 的子图。

由此直接得到并行的合法性：不同子序列可以分配到不同 rank，各自独立算注意力。 而当稀疏模式在 token-wise 与 group-wise 之间切换时， 局部等价性保证每 rank 一次本地重排 + 通信组内一次 All-to-All 就能完成数据交换。

诚实的边界：SSP 是 All-to-All，不是 Ring

OSP-Next 的 SSP 沿用了 All-to-All 通信原语，不是 ring P2P。 这意味着它并没有解决「KV 显存随序列线性增长」的问题—— 在 All-to-All 之后，每个 rank 仍然需要持有它所负责的完整序列段。

所以准确的说法是：OSP-Next 用「稀疏感知的 All-to-All」替代了「朴素 All-to-All」， 在稀疏这个维度上做到了最优；但显存这个维度它交给并行度去解，没有用 Ring。 如果你未来的瓶颈从「通信」变成「显存」，Ring 仍然是绕不开的—— 但那时你需要面对的是 Ring 与稀疏的兼容性问题（见第 7 节）。

5.3 HiF8 量化：联合训练稀疏与 8bit

HiF8 是什么

一种 8bit 精度格式，动态调整指数位与尾数位的分配， 因此同时具备较高精度与较大动态范围。

论文的关键论断是：正因为 HiF8 动态范围大，它可以依赖「粗粒度 per-tensor 量化」 就维持接近 BF16 的训练精度，从而省掉细粒度 FP8 所需的元数据与归约开销。

与主流细粒度量化的对比（论文对细粒度 FP8 的批评）

  • per-token：需要先算 token-wise 最大值， 引入 reduction 开销并造成 MatMul 前的串行依赖。
  • per-channel / per-block（如 128×128）与 MXFP8（每 32 元素共享 microscale）： 精度更稳，但 scale 元数据更稠密、硬件支持更复杂。
  • 总体：「频繁的 scale 计算、存储、加载与广播增加内存带宽压力并复杂化硬件实现， 部分抵消了 8bit 计算的效率收益」。

这个论断对序列并行尤其重要：per-token scale 的串行依赖与归约， 正好会破坏 Ring/CP 想要的「通信被计算掩盖」。

训练配置约束fsdp_size=8, sp_size=4, skiparse_sp_size=4， 要求 sp_size × skiparse_sp_size ≤ fsdp_size； 14B + sparse_ratio=2 时有效组合为 (1,4)/(2,2)/(4,1)

我的综合判断

这三篇其实构成了一条递进的技术路线，而不是三个并列选项：

  1. db-SP 回答「问题有多大」——它给出了 ρ_s 这个可复用的度量， 并用实测证明不均衡在 1.16–1.51 之间。这个数字本身就有决策价值： 如果你实测自己的模型 ρ_s < 1.1，那么整个负载均衡话题可以直接跳过。
  2. FVAttn 回答「少步场景怎么修」——它证明了预布局在 4 步蒸馏下不可靠， 并给出一个低开销、可分级启用的修复机制。
  3. OSP-Next 回答「能不能不修」——这是最有价值的答案： 通过设计规则化、局部等价的稀疏模式，让序列并行下的负载天然均衡， 同时保持与 FlashAttention 的原生兼容，并把量化也一起叠上。

如果只能选一条路走，我建议以 OSP-Next 为骨架（稀疏模式决定并行方式、量化联合训练）， 把 FVAttn 作为「万一不均衡仍超标」的兜底机制， 用 db-SP 的 ρ_s 作为贯穿全程的验收指标。

07Ring 还是 AllGather：正面回答

7.1 先把账算清楚

记号：序列长度 S，KV 头数 N_kv，头维 D， 并行度 P，每元素字节 b。

# Ring 原论文给出的显存模型（arXiv 2310.01889）
M_ring = b · 6 · c · h ← 随块大小 c 线性，与序列长度 s 无关
拆解：1 块 query + 2 块当前 K/V + 2 块接收中 K/V + 1 块输出
对照 vanilla: 2·b·h·s²（随 s 平方）

# 通信可被计算完全掩盖的条件
4·d·c² / F ≥ 4·c·d / B ⟹ c ≥ F / B (块大小 ≥ 算力 / 带宽)

# 简化的对比账（每 rank 每层）
AllGather: M = KV_total Comm = KV_total·(P−1)/P
Ring: M = KV_total / P Comm = KV_total·2(P−1)/P

关键修正：Ring 省的是显存，不是通信

Comm_ring ≈ 2 × Comm_ag——Ring 的通信量大约是 AllGather 的两倍， 因为 KV 块要在环上被每个 rank 各消费一次。 Ring 的唯一但决定性的优势是 M_ring = M_ag / P。

所以判据非常干净：显存够，就别用 Ring；显存不够，Ring 是唯一出路。 中间没有多少灰色地带。

7.2 但视频 DiT 让这个判据偏向 AllGather

对 Ring 有利的因素（DiT 特有）

  • 非因果：没有因果三角不均衡，不需要 zigzag / Striped， 每轮所有 rank 满算——Ring 的实现难度和效率都明显好于 LLM 场景。
  • db-SP 实测 Ring 的 ρ_s 低于 Ulysses（1.25–1.27 vs 1.36–1.51）。 如果你要用稀疏，Ring 在负载均衡这个维度上反而更优。

对 Ring 不利的因素（DiT 特有）

  • DiT 是 compute-bound，而 All-to-All 在高带宽互联上效率很高。 Ring 的 P2P 优势主要在 PCIe / 以太网等弱互联上体现（xDiT 原话： 「用集合通信的方法只适合 NVLink 这类高带宽互联，用 P2P 的方法更适合 PCIe 或以太网， 但在 NVLink 上没有优势」）。
  • Q 与 KV 等长：LLM 里 pass-Q 的省通信优势（Llama3 405B 的 N_H/N_KV = 16×）在 DiT 上不成立，Ring 的两种变体没有明显优劣。
  • 序列还能靠分辨率/帧数折中，而 LLM 的上下文长度是硬需求。
DIRECT ANSWER

现阶段：优先 AllGather / Ulysses（含 OSP-Next 式的稀疏感知 All-to-All）。 理由是视频 DiT 的主流分辨率（720P/768P）序列量级在 10 万 token 附近， AllGather 的 KV 显存通常还在预算内，而它的通信量只有 Ring 的一半、同步点少一个量级。

触发换 Ring 的条件（任一满足即应认真评估）：

  • 目标分辨率推到 2K/4K，或帧数显著增加， 使单层 KV 显存 × 层数超出预算（Flux.1 在 4096px 已是 420 万 token）；
  • 需要同时保持大 batch（多 prompt 并发）与长序列，显存双重挤压；
  • 部署在 PCIe / 以太网等弱互联集群上——此时 All-to-All 的代价上升， Ring 的 P2P 反而更合适。

换 Ring 时必须同时接受的两个新问题： ① 稀疏兼容性收窄（见 7.3）；② 你失去 SSP 那种「一次 All-to-All 切换稀疏模式」的便利。

7.3 Ring 与稀疏的兼容性：不是所有稀疏都能上 Ring

一个必须知道的反向结论

社区对 NSA（Native Sparse Attention）做 context parallel 实现时， 给出的兼容性判定是：Ring Attention ❌ Not suitable， 理由是「位置敏感性」，以及更根本的两点：

  1. NSA 的 compress/select 需要全局 K。 压缩分支产出 K̃_t^cmp，选择分支直接复用压缩分支的注意力分数 p_t^cmp = Softmax(q_t^T K̃_t^cmp)，再做全局 top-n 排序 I_t = { i | rank(p_t^slc'[i]) ≤ n }， 并要求 GQA 组内跨 head 的块选择一致。 全局排序在「每 rank 只持一段 KV」的 Ring 上无法本地完成。
  2. 需要绝对位置语义，而 Ring 的块在环上流转时位置是间接的。

来源：Scalable-Flash-Native-Sparse-Attention 的 CP 策略兼容性判定表（第三方实现， 基于 NSA 原论文 arXiv 2502.11089）。是实现者的工程结论，非 DeepSeek 官方结论， 但两条理由都是架构性的、可复核。

由此得到的筛选规则（很有用）

判断一个稀疏方法能不能配 Ring，只问两个问题：

  1. 稀疏决策是否需要全局 K？ 需要（全局 top-n、全序列排序、跨全序列聚合）→ 与 Ring 冲突。 不需要（固定模式、局部窗口、块内自洽的选择）→ 与 Ring 兼容。
  2. 是否依赖绝对位置编号？ 依赖 → 风险高（可用全局对齐的块 ID 网格缓解）；不依赖 → 安全。

按这个规则套三篇论文：

  • OSP-Next 的 Skiparse-2D：完全兼容 Ring—— 固定规则模式、最小单元仅 k²×k²、局部等价。 讽刺的是它自己选了 All-to-All，但它的稀疏模式恰好是 Ring 最友好的那类。
  • PAROAttention / SpargeAttn（db-SP 用的）：块级、局部为主，基本兼容。
  • NSA / 动态 token 选择类：不兼容 Ring。

7.4 Ring 的传输冗余：一个被忽略的优化点

即使解决了兼容性，朴素 Ring 还有一个所有场景共有的低效。 MagiAttention 给出了定量：KV₀ 必须广播给所有设备、 dKV₀ 需要 all-reduce，但 KV₇ 其实只被 rank 7 本地需要， 却仍然绕环走了整整一圈。

掩码形态Ring P2P 冗余
简单 causal mask25%
不规则 mask（varlen block-causal，含最后一个 global block）>33%

这是稀疏与 Ring 最自然的协同点

如果稀疏机制已经知道哪些块重要，那就没有理由把不重要的块在环上传一遍。 「KV 块传输跳过」不需要新算法（稀疏已经给了决策）、不需要额外通信（是减少通信）， 而且与量化正交（跳过的是块，与块内精度无关）。

这会让稀疏从一个「造成 Ring 负载不均」的负担， 变成一个「让 Ring 传得更少」的收益来源。 如果你最终要走 Ring 路线，这是我认为最值得做的联合优化。

SpargeAttn 的算法里已有 δ_K[j] 随 KV 块加载的写法， 可以作为「块 + scale 一起沿环走」的参考模板。

08量化 × 序列并行 × 稀疏的叠加规则

8.1 规则一：scale 的作用域必须与分块边界对齐

scale 粒度与序列并行的兼容性代价代表
per-tensor（全局 amax） 冲突：需要一个前置 all-reduce 该同步点无法与 attention 重叠，直接把 Ring 退化成带全局屏障的算法 标准 FP8 E4M3 训练常用
per-token 勉强：需 token-wise 最大值归约 MatMul 前的串行依赖 + reduction 开销（OSP-Next 明确批评） 细粒度 FP8 训练
per-tile / per-block 兼容：块内自洽，scale 随块流转 元数据与负载随粒度的权衡；传输体量本身很小 MXFP8（每 32 元素）、per-block 128×128
HiF8 + per-tensor 兼容且最省 依赖格式本身的动态范围，无需细粒度 scale OSP-Next（NPU 侧）

顺带把 scale 的传输成本算掉，避免评审时被追问：

# per-token-head scale（如 tile_size=128），N_kv=8, D=128, FP8 payload
payload = 128 · 8 · 128 · 1 = 131072 B
scale = 128 · 8 · 1 · 4 = 4096 B ⟹ ≈ 0.8%

# 最坏情形：FP4 payload + 32 元素块
payload = 65536 B, scale = 4096 B ⟹ ≈ 6.25%

# 结论：字节数不是问题，问题在打包方式
# 若 scale 与 payload 分两个 buffer 走两次 P2P → 多一次同步 + 小包开销 ← 这才是损失来源

8.2 规则二：量化必须作用在 K/V/P 上，绝不能作用在 softmax 统计量上

为什么 (m, l) 必须保持高精度

在线 softmax 的合并依赖重缩放因子 exp(m_prev − m_new)。这个因子有两个危险特性：

  • 当新块含极大值（m_new ≫ m_prev）时，因子趋近 0—— 之前累积的 O 几乎被完全丢弃。数学上正确， 但低精度下 O_prev 已经历多轮舍入，被放大回来时误差同步放大。
  • 因子本身需要 exp 的精度。作为参照：E4M3 的尾数只有 3 bit， 相对误差量级约 6%，直接乘在部分输出 O 上。

昇腾把 ring_attention_update 的 softmax_max/sum 强制为 FLOAT32， 这是一个正确的设计决策。不要为了省显存把 softmax 统计量降到 BF16/FP16。

8.3 规则三：精度验收必须按并行度扫描

环形/序列并行下的量化误差具有累积路径： 第 k 轮的部分输出由量化后的 P 与 V 相乘得到， 在后续轮次中被反复重缩放并累加。迭代次数随并行度增加，累积路径随之变长。 这是一个「并行度 → 精度」的隐性耦合——同一模型 P=8 的精度可能与 P=1 不同。

建议的验收口径

  • 把 P ∈ {1, 2, 4, 8} 作为独立精度扫描轴，观察误差随 P 的单调性。
  • 若随 P 明显恶化，说明需提高 P（注意力概率）的精度，或减少环上迭代累积。
  • 不能只在单卡上验证量化精度，然后假定 P=8 一样。

8.4 规则四：低精度 attention 在视频生成上不是免费的

SageAttention 论文给出的反面对照（CogVideoX / RTX4090）

配置CogVideo Fscore ↑Unidiffuser FID ↓
全精度3.768163.33
SageAttention（smooth K + per-block INT8）3.718166.93
FlashAttention-3 的 FP8 实现3.394394.13
不做 smooth K 的朴素量化1.902–2.014—

两个结论：

  • 「用 FP8 就行」是危险假设。FA3 的 FP8 在视频生成上 FID 从 163 恶化到 394， 而加了 outlier 平滑的 SageAttention 基本无损。格式选择必须逐案做质量验收。
  • 平滑（smooth K/Q）可能是必需项而非可选项。 注意它有个副作用：mean(K) 是全序列的通道均值， 在序列并行下需要一次跨 rank 归约。 好消息是它只有 d 维（如 128 个 float），通信量可忽略，主要代价是多一个同步点； 只要把它与 KV 块的首次量化放在同一阶段、只做一次，代价可控。 而这个 trade-off 在公开文献中没有任何实验——属于空白。

09昇腾算子可行性速查

因为 OSP-Next 已在 Ascend 950PR 上验证，你的方案大概率也要落在昇腾上。 这里只列与本文结论直接相关的算子事实（不展开实现细节）。

三个落地前必须实测的点

  1. RingAttentionUpdate 的 workspace 上限。 TND 布局下的约束为 align64(N·D)·(dtype·6+8) + align64(N·8)·56 ≤ 196608 字节。 按 fp16 近似推算，D=128 时 N 上界约 65、D=256 时约 33—— 这意味着常见的 N=64/D=256 组合可能被直接拦截。 （此为按公式推算，实际含对齐取整会更紧，务必用最小用例实测。）
  2. LightningIndexer 的块选择是局部的还是全局的。 这直接决定它能否配 Ring（见 7.3 的筛选规则）。 若内部依赖跨全序列的归一化或排序，就属于与 Ring 冲突的那一类。
  3. softmax 统计量的显存膨胀。 它以 8 个重复值存储（[B,N,S,8]）， B=8, N=128, S=100K 时约 400 MB（fp32）。 这笔开销在 Ring 路径下容易被忽略，必须单列进显存预算。

10给这个课题的建议

10.1 三条可发表的空白（如果你的目标是产出研究工作）

  1. 「序列并行 + 量化 attention」没有论文。 SageAttention / SageAttention2 / FA3 全部是单卡 kernel 论文， 均未讨论 context parallel；SageAttention 的 related work 只用一句话提到 RingAttention， 无任何结合设计或实验。最接近的只是工程实现（DAX：SageAttention2 + 序列并行； xDiT+AMD Quark：明确开 ring + fp8，但量化范围是 Linear 层而非 attention）。 这是确证的空白。
  2. 「Ring + 稀疏 + 量化」三者同时叠加没有论文。 OSP-Next 覆盖了「稀疏 + 序列并行 + 8bit」，但用的是 All-to-All 而非 Ring。 把 OSP-Next 的 Skiparse-2D（对 Ring 友好）真正跑在 Ring 上，本身就是新工作。
  3. 平滑统计量的全局化 trade-off 没有实验。 SageAttention 的 mean(K) 是全序列均值， 在序列并行下需要跨 rank 归约。是「多一个同步点换取复现单卡量化结果」， 还是「改用量化粒度以避免归约」，没有任何论文做过这个对比。

  • 规则化稀疏可能比动态稀疏更适合你。 动态 token 选择精度更高、更「聪明」，但它与并行化、FlashAttention 兼容性、 负载均衡三者都有摩擦。OSP-Next 用固定规则模式拿到了超过 Wan2.1 full-attention 的 VBench， 说明在视频这个强局部性模态上，规则的代价比想象中小。

  • 未取证的数值缺口：Meta CP 论文部分数值表、Striped Attention 逐模型加速比、 NSA §5 具体 speedup、SageAttention2 实验精度表、xDiT §5.2–5.3 逐模型数据、 MagiAttention / DAX / MoBA 的部分 benchmark（原文仅以图片给出，无可引用数值）。
  • 未涉及：SAAP 与「Sparse Flash Attention」类工作——未检索到可靠原文，故完全未涉及。
  • 推算已标注：ring workspace 上界换算、通信量与 scale 开销的代入计算、 图 1/图 3 中的示意性量化。
  • 三处论文编号订正：arXiv 2407.08608 就是 FlashAttention-3 本身 （不是独立的「FA3 FP8」论文）；xDiT 是 arXiv 2411.01738（2405.07719 是 USP）； BurstAttention 是 arXiv 2403.09347（不是 2406.16835）。 另：SageAttention2 的标题是 Per-thread INT4 Quantization（非 INT8）。
