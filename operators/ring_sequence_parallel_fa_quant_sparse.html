01结论摘要与决策建议

CORE VERDICT

1. Ring 与 AllGather 不是「谁更快」的问题，是「放不放得下」的问题。 在序列并行度 P 下，AllGather 路径要求每个 rank 在 attention 期间持有 完整序列的 K/V，单层 KV 显存不随 P 下降；Ring 路径每 rank 只持有 1/P 的 KV。当模型大到「权重已经吃满显存」时，AllGather 路径的直接后果是 OOM 或被迫降低 batch/分辨率，而不是变慢。这正是本项目要换 Ring 的根本理由。

2. 必须先确认模型是因果还是全注意力——这决定了一半的结论。 DiT / 视频生成用 full attention（非因果），因此 Ring 家族最有名的 因果三角负载不均衡（1:2:…:P）在 DiT 上根本不存在，zigzag / Striped 那套修正 也不需要。反之若目标是自回归 LLM 生成，因果不均衡是结构性的、必须在 P1 就处理。 本报告对两条路线分别标注。

3. 稀疏与 Ring 的兼容性是分档次的，不是统一的。 简单的固定/块级稀疏（昇腾 SFA、PAROAttention 类）与 Ring 兼容良好，db-SP 实测其 ρ_s 在 1.159–1.513 之间（db-SP）。 但需要全局信息的稀疏机制与 Ring 架构性冲突：社区对 NSA 的 CP 实现明确给出 「Ring Attention ❌ Not suitable」，理由是 NSA 的 compress/select 需要全局 K 与绝对位置 （见 第 7 节）。选稀疏算法前必须先判定它是否需要全局视野。

4. 量化与 Ring 的冲突是「装出来的」，靠 per-block scale 就能解开。 只要坚持 per-tile / per-block scale 与 payload 同块打包、随块流转， 量化就不需要任何跨 rank 规约，且 scale 的额外通信量在 FP8 + 128×128 tile 下仅约 0.8% （每 token-头一行）。反之若用 per-tensor amax 全局 scale，就会与 KV 分片直接冲突—— 因为它需要一个无法与 attention 重叠的前置 all-reduce。昇腾现有算子都是 tile 级，方向正确。

5. 三轴同时叠加已有强先例，但都不是 Ring。 最接近本项目目标的是 OSP-Next（稀疏 Skiparse-2D + 稀疏感知序列并行 + HiF8 量化， 视频生成，在 Ascend 950PR 上实测 2.27×）——但它的并行是 all-to-all 类而非 ring。 「Ring + 量化 attention」与「Ring + 稀疏 + 量化」两者 在公开文献中均未检索到，属真实研究空白。

6. 推荐路线：Ring 作为显存底座，量化优先于稀疏，稀疏按「是否需要全局信息」分级引入。 收益与风险不对称——量化几乎无额外风险（tile 内自洽），稀疏则可能引入跨 rank 的调度与 数值不确定性。而且量化本身对视频生成不是免费的：SageAttention 实测 FA3 的 FP8 在 CogVideoX 上 Fscore 从 3.768 掉到 3.394、Unidiffuser FID 从 163 恶化到 394， 说明低精度 attention 在生成任务上必须逐案验收。

三个必须前置确认的问题（否则选型会走错）

  1. 模型是因果还是全注意力？ DiT / 视频生成是 full attention， 因果不均衡不存在，zigzag/striped 不需要；自回归 LLM 则相反。
  2. 要用的稀疏算法需要全局信息吗？ 固定 / 纯局部块稀疏（SFA 类）与 Ring 兼容； NSA 这类需要全局 K 做 compress/select 的，公开实现明确判定与 Ring 不兼容。
  3. 量化是 per-tile 还是 per-tensor？ per-tile 随块走、零额外同步； per-tensor amax 需要一个无法与 attention 重叠的前置 all-reduce。

一句话决策

如果「特别大的模型」是硬约束，Ring 是必要的，不是可选的；请把它当作地基， 先跑通 Ring + FP8/INT8 tile 量化 的两轴叠加并完成精度验收， 再以「可回退开关」的形式引入 块稀疏 + 负载均衡器。 不要一开始就冲三轴同时叠加。

同时请把 OSP-Next（arXiv 2605.28691）作为最重要的对照基线—— 它是目前唯一在视频生成上把「稀疏 + 序列并行 + 8bit 量化」跑通并给出 Ascend 950PR 实测的系统。它的并行是 all-to-all 类而非 ring， 但它证明了这条三轴路线在昇腾上是可行的，其 HiF8 方案与 「序列并行下稀疏掩码如何切分」的工程细节都值得直接借鉴。

02问题定义：三轴叠加的冲突矩阵

我们要研究的是三个相互正交、但会互相破坏前提的技术同时生效时的系统行为：

为什么这三件事会互相破坏前提

SP 破坏「全局视野」

量化需要看到数据的极值（amax）才能定 scale；稀疏需要看到完整的 QK 分数才能选块。 SP 把这两者的视野都切碎了——除非把决策空间也一起切碎并保证块网格全局对齐。

量化破坏「数值余量」

Ring 的 online softmax 需要反复做 exp(m_old − m_new) 的重缩放。 当 m 以低精度存储或 P 被量化到 MXFP4（4 bit）时， 重缩放的相对误差被放大（第 4 节）。

稀疏破坏「同步假设」

Ring 的流水线假设每一轮各 rank 的计算量相近，通信才能被计算完全掩盖。 稀疏让这个假设失效，通信暴露成纯开销（第 7 节）。

03Ring Attention 机制拆解

3.1 为什么 AllGather 在「特别大的模型」上会先死

先算清楚两条路径的显存与通信账。记号：序列长度 S，KV 头数 N_kv，头维 D，并行度 P， KV 元素字节数 b，层数 L。

# 单层 KV 总字节
KV_total = 2 · S · N_kv · D · b

# AllGather 路径：attention 期间每 rank 常驻
M_ag = KV_total ← 与 P 无关
Comm_ag(每 rank) = KV_total · (P−1)/P

# Ring 路径：attention 期间每 rank 常驻
M_ring = KV_total / P ← 随 P 线性下降
Comm_ring(每 rank, 每层) = KV_total · 2(P−1)/P ← 两次遍历（因果下见 3.4）

代入一个具体配置感受量级：S = 128K, N_kv = 8, D = 128, b = 1 (FP8), L = 1：

KV_total = 2 · 131072 · 8 · 128 · 1 = 256 MiB / 层
P = 8: AllGather 常驻 256 MiB vs Ring 常驻 32 MiB ← 8× 差距
40 层模型: AllGather 10 GiB vs Ring 1.25 GiB（若同时只驻留 1 层 KV）

关键修正：Ring 省的是显存，不是通信

从上式可见 Comm_ring = 2 · Comm_ag · (P−1)/P ≈ 2 × Comm_ag。 Ring 的通信量大约是 AllGather 的 2 倍（因为 KV 要在环上被每个 rank 各消费一次）。 Ring 的唯一但决定性的优势是 M_ring = M_ag / P。

所以选型判据非常干净：只要不是显存不够，AllGather（或 Ulysses）在通信上更划算； 一旦显存成为硬约束，Ring 是唯一出路，且必须靠 量化 把 b 压下来（直接按比例降低通信与显存）， 靠 稀疏 把「需要流转的块」减少（跳过不重要的块，等价降低有效 KV_total）。

3.1b 原论文的显存模型与重叠条件（已核实）

3.2 Blockwise attention 与环上流转

核心循环可写成如下伪码（lse 即 log-sum-exp 统计量， 昇腾对应 softmax_max / softmax_sum）：

# 每个 rank 持有 Q_chunk（本地序列段）与完整 KV 的一个分片
def ring_attention_forward(Q_local, KV_local, P, rank):
    O = zeros_like(Q_local)        # 累计输出
    m = full_like(Q_local, -inf)   # 运行最大值（online softmax）
    l = zeros_like(Q_local)        # 运行分母
    kv_send = KV_local
    for step in range(P):
        kv_recv = p2p_exchange(kv_send, src=(rank-1)%P, dst=(rank+1)%P)   # 非阻塞，与下轮计算 overlap
        # 因果掩码：只有 kv 块的全局位置 <= Q 块位置时才参与
        if causal_ok(Q_local.global_pos, kv_recv.global_pos):
            S = (Q_local @ dequant(kv_recv.K).T) * softmax_scale
            m_new = maximum(m, rowmax(S))
            alpha = exp(m - m_new)
            P_ = exp(S - m_new)
            l = l * alpha + rowsum(P_)
            O = O * alpha + P_ @ dequant(kv_recv.V)
            m = m_new
        kv_send = kv_recv
    return O / l, m, l   # 或返回 (O, m, l) 交给 RingAttentionUpdate 合并

3.3 LSE 合并：昇腾把这一步做成了独立算子

这是本报告最关键的一个工程事实：昇腾算子库已经提供了 ring 所需的跨块合并原语， 但它只做合并、不做通信。也就是说，Ring 的「调度与通信」必须由框架层自己写。

RingAttentionUpdate / npu_ring_attention_update

功能定义（原文）：「将两次 FlashAttention 的输出根据其不同的 softmax 的 max 和 sum 更新。」 即把两个已算完的部分注意力结果，按 online softmax 语义合并成一个。

softmax_max = max(prev_max, cur_max)
softmax_sum = prev_sum · exp(prev_max − softmax_max)
            + cur_sum · exp(cur_max − softmax_max)
attn_out = prev_out · exp(prev_max − M) · prev_sum / S
        + cur_out · exp(cur_max − M) · cur_sum / S

三个必须记住的硬约束

  1. 最后一维的 8 倍膨胀：softmax 统计量以 8 个重复值存储，因此 [B,N,S,8] 的 float32 张量在 B=8, N=128, S=100K 时约 400 MB（计算：8×128×100000×8×4 B）。这是 Ring 路径上一笔容易被忽略的显存开销， 必须在显存预算里单列。
  2. workspace 上限公式（TND 布局）：
    align64(N·D) · (dtype_size·6 + 8) + align64(N·8) · 56 ≤ 192 · 1024（字节）。 这直接把 N·D 的可用组合锁死，超限会被 tiling 拦截——第 5 节会给出受影响的范围。
  3. TND 下 D 必须是 64 的倍数，且 actualSeqQlen 必填。

04跨 rank 合并：online softmax 与 LSE 语义

Ring 的正确性完全建立在 online softmax 的可结合性上。 理解这一点，才能看清低精度会在哪里出问题。

4.1 为什么 (O, m, l) 三元组可以合并

标准 softmax 需要全局 max，但 online softmax 发现：只要同时携带 m（当前最大）与 l（当前分母）， 就可以把「未归一化的部分输出」O 以 m 为基准暂存， 之后再用新的 m' 一次性重缩放：

O_merged = O_prev · exp(m_prev − m_new) + O_cur · exp(m_cur − m_new)
l_merged = l_prev · exp(m_prev − m_new) + l_cur · exp(m_cur − m_new)
最终输出 = O_merged / l_merged

注意 RingAttentionUpdate 的公式把 l 折进了系数： exp(m_prev − M) · prev_sum / S，这与上式等价， 好处是直接输出归一化后的 attn_out，同时把新的 m, l 也输出， 于是可以链式调用 P 次完成整个环。

数值风险点：exp 的重缩放会放大低精度误差

exp(m_prev − m_new) 这个因子有两个特性：

  • 当 m_new ≫ m_prev（新来的块含极大值）时，该因子趋近 0—— 意味着之前所有块累积的 O 被几乎完全丢弃。这在数学上是正确的， 但在低精度下，O_prev 已经经历过多轮量化/舍入，被放大回来时误差也一起被放大。
  • 因子本身需要 exp 的精度。昇腾把 m 和 l 强制为 FLOAT32， 这是一个正确的设计决策——千万不要为了省显存把 softmax 统计量降到 BF16/FP16。

结论：量化必须作用在 K/V/P 上，绝不能作用在 (m, l) 上。 这条约束在现有算子接口中已经被固化（softmax 统计量只收 FLOAT）。

4.2 因果掩码下的负载不均衡

因果注意力有一个 ring 特有的结构性问题：第 i 个 Q 块只需要看 前 i 个 KV 块。在按序切分的朴素 ring 里，rank 0 的 Q 块只需 1 次迭代， 而 rank P−1 需要 P 次——负载相差 P 倍，同时算完的 rank 空转等待。

说明：zigzag/striped 切分的思想来自 Striped Attention（arXiv 2311.09431） 与各类 ring 实现中的负载均衡调度。图 3 中的「加速上限」为按块数计算的示意值，用于说明趋势，非实测数据。

⚠ 重要限定：如果你的模型是 DiT / 视频生成，上面整节不适用

xDiT（arXiv 2411.01738）明确指出：「TeraPipe is designed for transformers using causal attention... In contrast, DiTs employ full attention, where each token attends to the computation of both previous and subsequent tokens.」

也就是说：DiT 用全注意力，因果三角在 Ring 上根本不存在，zigzag / Striped 那套修正 在 DiT 上没有必要。Megatron 官方文档把 Ring 的优点之一定为 「avoiding extra work from lower-triangle causal masking」——非因果场景下 Ring 反而更干净。

因此本节的结论请按目标模型分流： DiT / 视频生成 直接跳过 4.2，把精力放在第 3、6、7 节； 自回归 LLM 则需要把 zigzag 作为 Ring 实现的默认基线。

4.3 Ring 的结构性通信冗余（与因果无关，DiT 也有）

即使没有因果不均衡，Ring 还有一个所有场景共有的低效： KV 块绕环一圈，但其中有些块根本不该被传。

MagiAttention（SandAI）对此做了定量：在朴素 ring 中，KV₀ 必须广播给所有设备、 dKV₀ 需要 all-reduce，但 KV₇ 其实只被 rank 7 本地需要， 却仍然绕环走了整整一圈。

对本项目的两个直接含义

  • Ring 的有效通信量应当按「掩码决定的最小必要集合」来算，而不是按 KV 总量。 朴素实现的 25%–33% 冗余，正是「KV 块跳过」优化的收益空间—— 而且这个优化与稀疏是同一套机制：既然稀疏已经知道哪些块重要， 就不该把不重要的块在环上传一遍。
  • 稀疏 + Ring 存在一个「传输跳过」的联合优化点（第 7.4 节）， 它比「稀疏 + AllGather」更自然——因为 Ring 的块边界本来就是传输单元。

06量化 × Ring：接口断点与解决方案

6.1 断点一：scale 的作用域（最关键）

per-tensor amax 全局 scale ✘

量化前需要扫全序列求 max|KV|。在 Ring 下，每个 rank 只有 1/P 的 KV，必须额外做一次跨 rank 规约才能定 scale。

  • 引入一个全环同步点 → 破坏通信/计算 overlap
  • KV 是流式生成的（decode）时，scale 还会随序列增长漂移
  • 先算完 scale 才能量化，而量化完才能开始 ring → 串行化

per-block / per-tile scale ✔

块内自洽：每个 KV 块用自己的 amax 定 scale， scale 与该块的数据一起打包、一起在环上流转。

  • 零额外同步：量化在块生成时就能就地完成
  • 与 AllGather/Ring 都兼容，切换并行策略不需要改量化逻辑
  • 昇腾现有算子（QFA GROUP_SCALING/PER_BLOCK、KVQSA per-tile 128）都是这条路

6.2 scale 的通信开销到底有多大

这是评审时最常被问的问题。要先区分两种 scale 粒度，它们的账完全不同：

情形 A：per-tile / per-block scale（推荐，昇腾现有算子的做法）

# per-token-head scale（KVQSA 的 tile_size=128 即此类），D 个量化组
scale_bytes / block = block_tokens · N_kv · (D / group_size) · sizeof(scale)

# 典型值：N_kv=8, D=128, group/block=128, FP8 payload, scale 取 FP32
payload = 128 · 8 · 128 · 1 = 131072 B
scale = 128 · 8 · 1 · 4 = 4096 B
ratio = ≈ 0.8%

# 若按 MX 规范用 E8M0（1 byte）做 block-32 分组：
scale = 128·8·(128/32)·1 = 4096 B ⟹ 同样 ≈ 0.8%

# 最坏情形：FP4 payload + 32 元素块
payload = 128·8·128·0.5 = 65536 B, scale = 4096 B ⟹ ≈ 6.25%

结论 A：per-tile scale 的额外通信量在 1%–6% 量级，不构成障碍

但真正的成本不在字节数，而在布局与依赖：

  • 若 scale 与 payload 分成两个 buffer、走两次 P2P，就会多一次同步与小包开销—— 这才是实际损失来源。昇腾 kv_quant_sparse_flash_attention 的 quant_scale_repo_mode=1（combine 模式，scale 与数据混合存放） 正是为此设计，建议在 ring 实现中沿用。
  • 不同量化粒度（如 per-thread，见 SageAttention2）会把 scale 与线程/内存映射绑死， 跨 rank 传输时布局可能失真。per-tile 因为与 tile 边界对齐，反而最适合流转。

情形 B：per-tensor 全局 amax scale（不推荐用于 Ring）

量化前需要扫全序列求 max|KV|。在 Ring 下每 rank 只有 1/P 的 KV，必须额外做一次跨 rank all-reduce。

这个问题比「多花点通信」严重得多：all-reduce 是一个前置同步点， 它必须在任何量化与 attention 之前完成，因此无法与 attention 计算重叠。 而「通信被计算掩盖」恰恰是 Ring 的全部卖点。换句话说， per-tensor 量化会把 Ring 退化成一个带全局屏障的算法。

此外，KV 流式生成的场景下 scale 会随序列增长持续漂移，需要反复重算——开销进一步放大。

6.2b 一个被忽略的断点：平滑统计量也需要全局视野

mean(K) 的全局性问题

SageAttention 的核心技巧之一是 smooth K： γ(K) = K − mean(K)，其中 mean(K) 是 全序列 token 的通道均值（1×d 向量，用于消除 K 的 channel-wise outlier）。 SageAttention2 又把 smooth Q 引入，其 k̄ = mean(K) 同样是 全张量均值。

这个统计量与 per-tensor amax 有完全相同的问题：在 Ring 下要复现相同的量化结果， mean(K) 必须先在并行组内归约。

好消息：mean(K) 只有 d 维（如 128 个 float）， 通信量完全可以忽略，代价主要是多一个同步点，而不是带宽。 如果把它与 KV 块的首次量化放在同一阶段、只做一次（而不是每轮），代价可控。

坏消息：这个 trade-off 在公开文献中没有任何实验—— SageAttention / SageAttention2 都是单卡 kernel 论文，未讨论 context parallel。 属于本报告标注的证据缺口之一。

6.3 断点二：量化 P（注意力概率）与 online softmax 的相互作用

QFA 支持对 P 做 MXFP4 量化（quantize_p），这对 ring 有特殊含义：

  • P 是每轮局部产生的，不需要跨 rank 流转——所以 P 的量化与 ring 无接口冲突。
  • 但 P 的量化会放大 LSE 合并的误差累积： 第 k 轮的 O_cur 由量化后的 P 与 V 相乘得到， 在后续轮次中会被 exp(m_cur − m_new) 重缩放并累加。 环形迭代次数越多，累积路径越长。
  • 参数量化噪声会随 P（并行度）增加而累积，这是一个 「并行度 → 精度」的隐性耦合：同一个模型，P=8 的精度可能略差于 P=1。

验收建议

精度验收必须在目标并行度下做，不能只在单卡上验证量化精度然后假定 P=8 一样。 建议把 P ∈ {1, 2, 4, 8} 作为一条独立的精度扫描轴， 观察误差随 P 的单调性——若随 P 明显恶化，说明需要提高 P 的精度或减少环上迭代的累积。

6.4 断点三：低精度通信与反量化时机

MindIE-SD 的 USP 实现给了一个可直接借鉴的范式（mindiesd/layers/usp.py）： 量化在通信前完成，payload 与 scale 都保持量化态，直到 fused quant FA 消费它们， 中间不做「量化→通信→反量化→再量化」的往返。源码注释明确写出这是 model-repository 的 quantized KV AllGather 路径。

参考实现范式：MindIE-SD/mindiesd/layers/usp.py 中 _fa_block_quantize → _all_gather_quant_fa → _concat_quant_fa 链路；以及 _block_quantize 对 mxfp8（scale 取 2 的整数次幂）的支持。

07稀疏 × Ring：负载均衡与决策一致性

这是三轴里唯一无法靠接口约定消除的冲突，也是 db-SP 与 FVAttn 两篇论文的共同主题。

7.1 问题被两篇工作量化了

db-SP（arXiv 2511.23113）

提出 稀疏不均衡比 ρ_s：最重 rank 的负载 ÷ 全部 rank 的平均负载， 即「做完美均衡后理论上能拿到的加速比」。

实测（Table 1）：

  • Wan2.1 + PAROAttention：Ulysses 1.355 / Ring 1.255 / USP(U4R2) 1.253
  • Wan2.1 + SpargeAttn：Ulysses 1.428
  • CogVideoX1.5 + PAROAttention：Ulysses 1.447 / Ring 1.269 / USP(U2R4) 1.159
  • CogVideoX1.5 + SpargeAttn：Ulysses 1.513

关键观察：Ring 的 ρ_s 系统性地低于 Ulysses（1.25–1.27 vs 1.36–1.51）， 因为 Ring 沿序列/块维度划分，稀疏度的头部差异被摊薄了。

方案：双层贪心（head 级 + block 级），跨去噪步复用划分计划（阈值 P_s）， 运行时按延迟预测动态选择并行策略。结果：端到端 1.25×、 attention 1.40× 平均加速。

FVAttn（arXiv 2607.16190）

立场与 db-SP 相反：不做全局重划分，而是运行时修复。

动机来自 few-step 蒸馏场景的实测：相邻步同一 head 的密度变化最高 97%， 同一 rank 的负载变化最高 44%——任何「预测式」布局都基于过期信号。

方案：

  • RLB（Runtime Load Balancing）：等稀疏掩码 materialize 之后， 按已实现的 per-head 负载，用受约束的 P2P 迁移少量重头 head （默认每 rank 最多迁出 1 个，约 20%）。搜索是确定性的，各 rank 独立求解，避免 rank-0 广播同步。
  • SASA（Slack-Aware Sparse Augmentation）：把非关键 rank 的残余空闲 「花掉」——按重要度顺序追加额外高价值块，只加在有 slack 的 rank 上， 不抬高全局 Top-p 阈值，因此不延长关键路径。参数 n₁=0.8, n₂=0.07（8×H20）。
  • 分级启用：ρ < k₁ 跳过；k₁ ≤ ρ < k₂ 只开 SASA；ρ ≥ k₂ 开 RLB + SASA。

结果：Wan2.2 I2V 上负载不均衡从 1.34 → 1.08， attention 相对 FlashAttention 4.41×，DiT 推理 2.02–2.11×， 可见运行时开销 0.7 ms。

两篇工作对昇腾项目的启示（本文推断）

db-SP 的路线对训练/多步更合适，FVAttn 的路线对少数步推理更合适—— 因为划分计划复用依赖「稀疏掩码跨步相似」这一前提，而步数蒸馏到 4 步后这个前提被削弱 （FVAttn 实测 97% 的步间变化正是反例）。 本项目若是 DiT 生视频推理且使用少步蒸馏，应优先考虑 FVAttn 式的运行时修复， 而不是 db-SP 式的静态划分。

另一个重要判断：Ring 在稀疏场景下比 Ulysses 更「抗不均衡」（db-SP 实测数据支持）。 这与「为了省显存才选 Ring」的动机形成了正向叠加——Ring 既省显存，又天然摊薄了头级稀疏差异。

7.1b 但并非所有稀疏都与 Ring 兼容：需要全局视野的机制会架构性冲突

这是本次调研中最需要引起项目注意的反向结论。社区对 NSA（Native Sparse Attention） 做 context parallel 实现时，明确给出了下列兼容性判定：

CP 策略与 NSA 的兼容性关键限制
DeepSpeed-Ulysses⚠ 部分兼容受 KV head 数约束；NSA 通常只用 2–4 个 KV head，会产生额外通信与 topk 计算；仅适合不太长的序列（≤32K）
Ring Attention❌ 不适用位置敏感性（position sensitivity）
All-Gather✅ 最优选择可扩展性最好

其给出的两条架构性理由是：

  1. NSA 的 compress / select 模块与 Ring 的根本冲突。 NSA 的压缩分支要产出 K̃_t^cmp = { φ(k_{id+1 : id+l}) }， 选择分支的重要性分数直接复用压缩分支的注意力分数 p_t^cmp = Softmax(q_t^T K̃_t^cmp)，再做全局 top-n 排序 I_t = { i | rank(p_t^slc'[i]) ≤ n }， 并且要在 GQA 组内跨 head 求和以保证块选择一致 （p_t^slc' = Σ_h p_t^slc,(h)，原文明确 "consistent block selection across these heads has to be ensured"）。 top-n 是全局操作，而 Ring 下每个 rank 只持有一段 KV——排序无法在本地完成。
  2. NSA 需要绝对位置语义，而 Ring 的块在环上流转时位置信息是间接的。

来源：mdy666/Scalable-Flash-Native-Sparse-Attention 的 CP 策略兼容性判定表（第三方实现， 基于 NSA 原论文 arXiv 2502.11089）。这是实现者的工程结论，不是 DeepSeek 官方 NSA 论文的结论， 但两条理由都是架构性的、可复核。

对本项目的判定清单

上昇腾前，先用这两个问题筛掉不兼容的稀疏算法：

  • 稀疏决策是否需要全局 K？ 需要（全局 top-n、全局排序、跨全序列聚合）→ 与 Ring 冲突。 不需要（固定模式、局部窗口、块内自洽的选择）→ 与 Ring 兼容。
  • 是否需要绝对位置语义？ 需要且依赖全局位置编号 → 风险高； 改用「全局对齐的块 ID 网格」可缓解（见 7.2）。

昇腾 SFA / LightningIndexer 的定位需要实测确认： 若 LightningIndexer 的块选择是在「每个 query 可见的 KV 范围」内做的局部选择， 则与 Ring 兼容；若它内部依赖跨全序列的归一化或排序，则需要按 7.2 的方案改造。 这一点在本报告的资料范围内无法定论，建议做一次针对性的源码/规格核实。

7.2 一个 db-SP / FVAttn 都没覆盖的昇腾特有问题：稀疏决策空间的一致性

问题描述

在 Ring 下，每个 rank 只有 1/P 的 KV。但每个 rank 的 Q 都需要看到全部 KV 块 （否则注意力结果不完整）。而稀疏选择器（LightningIndexer 类）需要跑在 KV 上才能给出索引。

于是产生一个拓扑矛盾：

  • 若选择器只在本地 KV 分片上运行 → 每个 rank 只能为「自己那段 KV」给出块级重要性， 无法为其他 rank 的 KV 段决策 → 各 rank 的稀疏掩码在全局意义上不一致。
  • 若让每个 rank 都在本地跑完整序列的选择器 → 需要 KV 全量副本 → 直接抵消了 Ring 省显存的意义，退化成 AllGather 的显存开销。

FVAttn 与 db-SP 都建立在 Ulysses 风格或「序列到 head 的 all-to-all 之后每个 rank 持有完整序列」 的前提上（FVAttn 明确写了 "each GPU holds complete sequences for a subset of attention heads"）， 因此它们都没有面对这个问题。

可行解法（本文建议）

  1. 全局对齐的块网格：定义固定的 block ID 空间 （block = 128 token，与 KVQSA 的 tile_size=128 对齐）， 所有 rank 用同一套编号。这样稀疏索引是全局可解释的，与哪个 rank 持有无关。
  2. 索引器与注意力解耦地随块流转：让块的稀疏索引（而不是整块 KV） 沿环一起传播。索引的字节数是 sparse_size · 4 byte(INT32) 量级， 相比 KV 块（block_tokens · N_kv · D · b）可以忽略。 这样每个 rank 在 step 轮拿到「别人对我需要的这段 KV 是怎么判的」。
  3. 或者：索引器用低精度小模型近似在本地算——例如在 1/32 下采样的 KV 上跑索引器（MInference / 池化思路）， 用可接受的索引质量换取「不复制完整 KV」。

推荐第 1+2 条组合：块网格全局对齐 + 稀疏索引随块流转。 代价是每轮多传 O(sparse_size) 的 INT32，收益是稀疏决策全局一致、且不破坏 Ring 的显存优势。

7.3 与因果 ring 的交互：不要重复发明负载均衡

注意第 4.2 节的因果不均衡（1:2:…:P）与稀疏不均衡是两个独立来源（仅自回归 LLM 场景； DiT 只有后者），总延迟由两者叠加后的最慢 rank 决定。落地顺序应当是：

  1. 先解决因果不均衡（zigzag 切分）——这是确定性的、一次性的收益，无运行时开销。 DiT 场景跳过此步。
  2. 再解决稀疏不均衡（RLB 或 block 级贪心）——这需要运行时机制。
  3. 最后考虑稀疏 + 量化的联合优化（见 7.4）。

7.4 与稀疏的联合优化机会

机会一：KV 块传输跳过（本项目最值得做的联合优化）

如 4.3 节所述，朴素 Ring 有 25%–33% 的 P2P 冗余。 而稀疏机制本来就已经算出「哪些块重要」—— 把这两个信息打通，就得到一个稀疏与 Ring 天然协同的优化： 不重要的 KV 块不参与环上流转。

这个优化的吸引力在于：它不需要新算法（稀疏已经给了决策）， 不需要额外通信（是减少通信），且与量化正交（跳过的是块，与块内精度无关）。 稀疏由此从一个「让 Ring 负载不均」的负担，变成「让 Ring 传得更少」的收益来源。

注意：SpargeAttn 的算法里已有 δ_K[j] 随 KV 块加载的写法， 可以直接作为「块 + scale 一起沿环走」的模板参考。

机会二：用精度兑换 slack（本文推断，未见公开工作）

SASA 的「用完残余 slack」逻辑与量化有一个协同点： 在残余 slack 内追加的块，如果用低精度（FP4/FP8）计算，同样的时间预算能覆盖更多块。 也就是在非关键 rank 上用更低精度换更大掩码覆盖， 数学上等价于「把 slack 兑换成 attention 质量」。 db-SP 与 FVAttn 都没有提出这个方向，建议作为后续工作。

10.2 本报告检索到的重要反向结论

反向结论 1：Ring Attention 与 NSA 类稀疏「架构性不兼容」

社区对 NSA 的 context parallel 实现明确判定 Ring「Not suitable」， 理由是 NSA 的 compress/select 需要全局 K 与绝对位置（详见 7.1b 节）。 这意味着「稀疏 + Ring」不是一个无条件成立的组合—— 必须先按 7.1b 的两个问题筛掉需要全局视野的稀疏算法。

对本项目的直接影响：在上稀疏之前，必须核实 LightningIndexer 的块选择是局部的还是全局的。

反向结论 2：Ring 在 decode 阶段是负收益

Meta 的百万 token CP 工作（MLSys 2025）实测：TTIT 随 CP 增大而上升 （CP=1/2/4 时为 46 / 60 / 71 ms），论文因此建议 prefill / decode 解耦（PD 分离）。 原因是 decode 阶段每步只有 1 个 token，通信无法被计算掩盖。

对本项目的直接影响：Ring 的收益集中在 prefill 阶段。 如果生成模型的推理是「长 prefill + 长 decode」（自回归视频/LLM）， 应当把 Ring 只用于 prefill，并采用 PD 分离架构。不要指望 Ring 改善 decode 延迟。

反向结论 3：低精度 attention 在视频生成上不是免费的

SageAttention 论文的对照实验显示（CogVideoX / RTX4090）：

  • 全精度：CogVideo Fscore 3.768，Unidiffuser FID 163.33
  • SageAttention（smooth K + per-block INT8）：Fscore 3.718，FID 166.93 —— 基本无损
  • FlashAttention-3 的 FP8 实现：Fscore 3.394，Unidiffuser FID 恶化到 394.13
  • 不做 smooth K 的朴素量化：Fscore 崩到 1.902–2.014（画面基本损坏）

对本项目的直接影响：「用 FP8 就行」是一个危险的假设。 昇腾 QFA 支持 FP8/HiFloat8/FP4 多种格式，但格式选择必须逐案做质量验收， 而平滑（smooth K/Q）这类消除 outlier 的前置步骤在生成任务上可能是必需的、 而非可选的优化。注意平滑统计量的全局性问题见 6.2b 节。

10.3 公开证据缺口（已明确标注）

三处真实空白

  • 「Ring / CP + 量化 attention 算子」：未检索到任何论文。 SageAttention / SageAttention2 / FA3 全部是单卡 kernel 论文；SageAttention 的 related work 仅用一句话提到 RingAttention，无任何结合设计或实验。最接近的工程实现是 DAX（SageAttention2 + sequence parallel）与 xDiT + AMD Quark（命令中明确同时开 --ring_degree 2 --ulysses_degree 2 与 fp8 量化， 但量化范围是 Linear 层，不是 attention）。
  • 「Ring + 稀疏 + 量化」三者同时叠加：未检索到。 但找到最接近的系统 OSP-Next（见下）。
  • 昇腾平台上的 ring 实测数据：不存在公开数据。 vllm-ascend 与 MindIE-SD 均无 ring 实现，因此所有性能预期只能通过 P0 / P1 自测获得。

最重要的对照基线：OSP-Next（建议直接研究）

Yunyang Ge 等（北京大学 PKU-YuanGroup / Open-Sora Plan 团队）， arXiv 2605.28691，2026-05-27。 这是检索到的唯一同时覆盖「稀疏注意力 + 序列并行 + 8bit 量化」的完整系统， 且是视频生成场景。四项协同设计：

  • Skiparse-2D Attention：为图像/视频定制的固定规则稀疏模式， 沿高与宽独立施加，质量接近 3D Full Attention， 且原生兼容 FlashAttention kernel（不需要自写 Triton/CUDA）。
  • Sparse Sequence Parallelism (SSP)：相比 Ulysses SP， 降低 inter-rank 通信量 75%，每块通信步数从 4 步降到 1 步； 通过单次 All-to-All 完成子序列划分与稀疏模式切换。
  • HiF8 量化（NPU only）：动态精度的 HiF8，per-tensor 指数/尾数分配， 在稀疏模型之上施加；论文称是首个证明 8bit 量化与稀疏模型微调可联合进行的工作。
  • Mix-GRPO 强化学习：首个在稀疏视频生成模型上做 RL。

10.4 验证口径建议

正确性

  • 逐 bit 对齐：P1 阶段（无量化无稀疏）应与单卡密集注意力在 fp32 下达到极小误差。利用 ring_attention_update 的 默认确定性特性，可以做严格的重复性验证（同输入两次结果完全一致）。
  • P 扫描一致性：同一序列在 P=1,2,4,8 下的输出应互相一致（在容差内）， 这是 ring 实现正确性的最强单测。
  • 因果边界：重点测 S/P 不能整除、 以及 Q 块跨越多个 KV 块的边界情形。

性能与显存

  • 显存：必须实测 attention 期间的峰值，而不只是稳态占用。 double buffer 会让峰值比稳态高 1–2 个块。
  • 扩展性：画 P=1→8 的延迟曲线，与两个理论上限对比—— 线性上限（P×）与因果受限上限（P²/Σi）。落后于后者说明 ring 实现有额外开销。
  • ρ 指标：直接采用 FVAttn 的 ρ = max_r L_r / mean_r L_r 定义，便于与文献数字（1.34→1.08）直接对照。
  • 通信占比：用 profiling 确认 P2P 是否真的被计算掩盖。 若通信占比随 P 上升，说明 overlap 没做对，而不是 ring 本身的问题。

最小可行验证（建议第一个实验）

用一个最小配置（如 B=1, N=8, D=128, S=32768, P=4）跑通 「单卡密集注意力」vs「4 卡 ring（仅 ring_attention_update + 手动 P2P）」 的逐 bit 对齐。这个实验一天内可以完成，但能同时证伪 R1（workspace 上限）、 R7（因果不均衡）和 P1 的核心可行性，是性价比最高的起点。
