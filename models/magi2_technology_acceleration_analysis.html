MAGI-2 Preview 不是把 Wan2.2 放大，也不是 MAGI-1 自回归路线的直接续作。它将文本、视频、音频放进单流 Transformer，以超细粒度 MagiMoE 把总容量推到 114B，同时把每 token 激活量压到约 6B。代价是：推理加速从“优化一个 DiT”升级为模型、专家路由、通信、稀疏注意力与阶段调度的联合工程。

ONE-LINE VERDICTMAGI-2 的核心门槛不是算力峰值，而是能否高效承载 100 步 × 长序列 × 细粒度 MoE × 8 卡通信。

在蒸馏模型发布前，先后顺序应是：跑通融合内核与双并行 → 压低通信和搬运 → 稳定两阶段流水 → 再做量化与缓存。

01 / Executive summary

三个判断，决定优化方向。

MAGI-2 的论文与仓库公开信息非常明确：它首先是一项“如何把视频生成模型扩到 100B 且仍可执行”的架构—系统协同实验，而不是面向单卡低成本推理的产品模型。当前版本没有公开端到端耗时，所有性能判断必须从计算图和系统路径推导，并通过实机 profile 验证。

NOT MAGI-1

放弃自回归分块起点

MAGI-2 没有沿用 MAGI-1 的时间分块自回归去噪。它采用统一音视频单流 DiT/flow 生成，目的是先降低百亿级联合训练中的系统变量。因此，KV Cache 不是当前主线，去噪步数仍是首要乘数。

FINE-GRAINED MOE

MoE 不是“两套模型切换”

Wan2.2 在不同噪声阶段切换两位 14B 专家；MAGI-2 则在每个 token、每个 latent head 上执行 Top-6/256 路由。前者重点是模型驻留与 timestep 调度，后者重点是路由、重排、小 GEMM、scatter 与专家并行。

SYSTEM FIRST

8 卡是架构的一部分

默认 CP=8、EP=8，依赖 Ulysses、NCCL、FlashAttention-3、Triton MagiMoE、MagiAttention 与 MagiCompiler。单纯把 PyTorch 算子替换到另一硬件后端，不能复现原始执行效率。

最重要的加速杠杆：近期是融合细粒度 MoE + 高效上下文/专家并行；中期是减少 100 次 Preview 网络调用的步数蒸馏。官方 README 已把“far fewer steps”的 distilled 权重列为 coming soon——它潜在的收益通常远大于单个内核再快 10%–20%。
02 / Technology stack

从提示词到 1080p 音视频。

MAGI-2 Preview 是一个强耦合流水：Qwen3.5-27B 提供长结构化文本条件；Preview 在低分辨率联合生成音视频 latent；Refiner 以局部窗口注意力提升空间分辨率；视频和音频分别由 VAE 解码，最终通过 FFmpeg 合流。

01 / PROMPT结构化增强T2V/I2V 模板把短提示重写为 10 秒事件、镜头与音频时间线。
02 / QWEN文本编码Qwen3.5-27B，权重约 56 GB；text_in_channels=5120。
03 / PREVIEW114B MagiMoE512×896，40 层；中间 36 层稀疏；100 步联合音视频去噪。
04 / TRANSFER阶段换入换出Preview 与 Refiner 默认 roundtrip，避免同时占据 80GB 卡。
05 / REFINER稠密局部注意力30 层、hidden 4096、5 步；窗口稀疏注意力提升至 1088×1920。
06 / DECODE双 VAEWan2.2 视频 VAE / Turbo VAE；Stable Audio Open 音频 VAE。
07 / OUTPUT封装与缩放默认 25 fps；生成宽度 1088，可缩放成 1080×1920 并 mux 音频。
SINGLE STREAM

文本、视频、音频全自注意力

三种模态进入同一个 token 序列，避免多塔与固定 cross-attention 接口；跨模态关系可以在整个骨干中持续交换，但序列更长、Attention 与并行通信压力更大。

ATTENTION

Gating + Sink + mHC

Preview 配置启用 attention gating、1 个 sink token 与 4-stream mHC；实现调用 FlashAttention-3。Refiner 使用 3D block window，所有 30 层均为 local attention。

FLOW

Flow UniPC 多步采样

仓库 sampler 明确包含 Flow UniPC 调度器；基础版使用 100+5 步。它仍是并行生成整段 latent 的迭代去噪，不是 MAGI-1 式逐 chunk 自回归。

03 / MAGI-2 vs Wan2.2

相似的是 DiT，差异在扩展方式。

Wan2.2 是当前成熟、易部署的主流开源参照：A14B 以噪声区间专家提高容量，TI2V-5B 以高压缩 VAE 降低 token 数。MAGI-2 更激进：同时追求百亿级容量与原生音视频统一生成，系统复杂度显著上升。

04 / MoE anatomy

“MoE”不是同一种优化问题。

WAN2.2 · COARSE

按去噪阶段选模型

高噪阶段使用负责布局的专家，低噪阶段切到细节专家。每步只执行一个完整 14B DiT。

  • 路由由 timestep/SNR 决定，不随 token 波动
  • 每步 GEMM 仍是规则的大矩阵
  • 优化重点：两套权重驻留、切换、offload、FSDP
  • 通信形状稳定，通用 DiT 内核可复用度高
VS
MAGI-2 · ULTRA-FINE

每 token × 每 head 选专家

3072 维 routed representation 拆成 12×256 维 head；每个 head 从 256 个窄专家里激活 Top-6。

  • 每层共有 12×256=3072 个 head-local expert unit
  • 每 token 激活 12×6=72 个窄专家单元
  • 需要路由、排序、gather、tiny FFN、加权 scatter 全链融合
  • Head Parallel 让跨设备通信形状固定，不随 Top-k 放大
hidden [N, 3072] → split projection → [N, 12 heads, 256] → fixed-shape Head Parallel all-to-all → independent sigmoid router × 12 → Top-6 / 256 → expert-wise compact layout → fused (gate + up + SwiGLU7) → down projection → routing-weighted deterministic / fast scatter → combine heads → hidden [N, 3072]

官方技术博客给出的标准 MoE 通信量近似为 N·k·H，而 Head Parallel 近似为 N·H：跨设备只交换固定 head slice，Top-k 的动态性留在 head owner 本地。这能消除动态 all-to-all 的形状波动，却把性能压力转移到大量极窄专家的本地执行效率上。

COMPUTE

算力不等于高利用率

专家矩阵仅 256→1280→256，单 expert token 数又受路由分散。若逐 expert 发 kernel，launch 和中间读写会吞掉稀疏收益；必须做 grouped/fused execution。

NETWORK

同一 8 卡承载 CP 与 EP

Ulysses attention 需要 all-to-all；Head/Expert Parallel 也需要集体通信。若通信组、流与拓扑设计不当，两个并行维度会竞争链路，形成 device idle。

MEMORY

参数省算不省存储

114B 总权重仍需保存和分片。Preview 权重约 228GB，Refiner 14GB，文本编码器 56GB；默认 roundtrip 表明 CPU 内存与 H2D/D2H 带宽进入关键路径。

06 / Acceleration priorities

07 / Ascend readiness

昇腾迁移：可行，但不是换设备名。

昇腾生态已有 Ulysses、专家并行、FSDP2、Flash Attention、MoE GroupedMatMul、permute/unpermute 融合等基础能力；MindSpeed-MM 也已支持 Wan2.2 的 Ulysses 路线。这些为 MAGI-2 提供“能力积木”，但 MAGI-2 的 Multi-Head LatentMoE、Flash-MH-MoE、mHC 与 3D window attention 仍需专项适配。

CAPACITY

建议起点：8×64GB 或更高

这是容量估算而非官方认证。Preview 权重 228GB/8≈28.5GB 每 rank，仍需激活、通信 buffer、Refiner/Text/VAE 与框架开销。建议宿主机内存至少 512GB，并为 roundtrip 留出余量。

TOPOLOGY

先做单机 8 卡

默认 CP=EP=8；单机高带宽互联能最大限度压低两个 all-to-all 维度的风险。跨机扩展前，先量化 HCCS/HCCL 通信占比与每层 device idle。

KERNEL

算子适配优先于量化

如果 expert FFN 或 3D window attention fallback 为小算子/通用实现，低精度只会“省显存但不加速”。先达到 BF16 高利用率，再投入 FP8/W8A8。

与 Wan2.2 移植的关键差别：MindSpeed-MM 已列出 Wan2.2 + CP(Ulysses) 支持，说明标准视频 DiT 主干、FSDP/CP 和 VAE 路径有可复用资产；但 MAGI-2 的超细粒度 MoE 不是 Wan2.2 的双模型切换，不能据此推断“已经支持 MAGI-2”。
