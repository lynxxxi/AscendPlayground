实时生成的每一毫秒都可以归因到四个正交杠杆：① 减少主干调用次数（蒸馏：几十步 → 1–4 步）、② 消除历史重算（块级因果 + KV Cache + RoPE 重定位）、③ 压缩单步成本（稀疏/线性/低比特注意力 + 分块量化）、④ 把波动藏进调度（异步 DiT–VAE 流水、合批、会话迁移与弹性扩缩容）。前三个杠杆由后训练决定上限，第四个杠杆由服务系统决定能不能兑现；只做其中一层，其余层会立刻成为 Amdahl 瓶颈。

01A 段 · 模型结构

基座与四家模型结构：先看「信息流」，不看画质榜

本章的判据只有一条：模型允许信息往哪个方向流动、允许注入什么条件、允许复用哪些状态。这三个问题决定了后续所有章节是否有可能成立——画质、分辨率、时长都可以后补，信息流不能。

先给结论：2026 年的实时世界模型已经收敛到同一个骨架——潜空间 + 音视频（或视频+动作）联合 DiT + 块级因果注意力 + 可复用状态 + 少步蒸馏。四家产品的差异不在骨架，而在四个选择上：条件怎么注入（token 拼接 / AdaLN / cross-attention / 投影变换）、记忆怎么做（滑窗 KV / sink / 多时间尺度 / 动态调度）、因果化怎么做（TF / DF / MoBA）、少步与降分辨率怎么配（纯少步 / 低分辨率主干 + Refiner）。

1.1谱系起点：U-ViT → UniDiffuser 留下了什么

U-ViT · 2022-09 · arXiv 2209.12152

两个设计选择定义了它的身份

  • 把所有输入都当 token：时间步 token、条件 token、图像 patch 一律按 token 处理，不做特殊分支。
  • 浅层↔深层长跳连接（拼接后线性投影）；消融结论是关键的是长跳连接，U-Net 式的下采样/上采样算子并非必需。

这解释了为什么后来 Vidu 能自然地把「参考图」也当作一路条件 token 塞进同一个主干——从 U-ViT 开始，主干就没有为任何单一模态设过专用通道。潜空间扩散设定下 ImageNet 256×256 类条件生成 FID 2.29、MS-COCO 文生图 FID 5.48（当时在不用大型外部数据集的条件下最优）。

UniDiffuser · 2023-03 · arXiv 2303.06555

统一建模的理论来源

  • 解决「一个模型如何同时表达边缘分布、条件分布与联合分布」：所有模态都加噪，并且给不同模态分别输入各自的时间步，网络预测所有模态的噪声。
  • 训练完成后，只要设置合适的时间步组合，同一模型即可做图像生成、文本生成、文生图、图生文与图文对生成。

这条思路直接对应后来的三条产品主张：统一问题形式、统一架构、压缩即智能，以及「不再需要 LoRA 微调」。它也是 2025-12 开源的 Motus（世界动作模型）明确沿用的底座。

为什么谱系对迁移工作重要：「一切都是 token」意味着新增一种条件不需要改主干结构，只需要定义该条件的 token 化方式与位置编码。而「不同模态各自的时间步」意味着音视频联合建模可以通过拼接模态维实现——这正是 Vidu S1/S2 的 x₀ = [v₀ ; a₀] 的理论来源。读懂这两条，后面四家的结构差异就都变成「参数选择」而非「架构创新」。

1.2生数 Vidu S1 / S2：参考图作为条件 token 的联合音视频因果 DiT

Vidu S 系列的结构可以精确写成三行公式，这也是目前公开材料里最完整的一份「流式 DiT」结构描述：

双向阶段： x̂₀^{1:N} = f_θ^bi ( x_t^{1:N} , t , r , c^{1:N} ) r ：参考图，对所有 segment 共享 c^{1:N} ：逐 segment 条件（每段自己的 caption） 因果阶段： x̂₀^i = f_θ^causal ( x_{t_i}^i , t_i , r , c^i , x_{τ_i}^{<i} , τ_i ) 每个 segment 只能看：参考图 r + 本段条件 c^i + 合法历史状态 x_{τ_i}^{<i} 参考图是块级因果掩码中唯一的全局可见例外 音视频联合：x₀^i = [ v₀^i ; a₀^i ] ← 视频与音频隐变量沿模态维拼接，进入同一个 DiT
结构要点 1

参考图注入方式：序列拼接式 in-context 条件

参考图 不是经文本编码器改写的语义条件，也不是加性位置编码偏置，而是作为条件张量 r 与噪声隐变量、时间步、逐段文本条件并列进入同一个 DiT，没有独立的参考编码器分支。这与 UniDiffuser「所有模态都加噪、各自输入时间步」同源。

结构要点 2

因果化的具体做法：块级因果掩码 + 三阶段训练

把双向时序注意力替换为 block-wise causal attention mask。S2 在双向阶段联合训练 I2V 与 R2V（r 分别是目标视频首帧 / 参考图），并按 segment 用各自的条件 cⁱ 监督——而不是整条序列共用一个 prompt，这显著改善了指令遵循。

结构要点 3

两阶段生成：低分辨率主干 + 单步 latent 超分 Refiner

z_{t_r}^i = (1 − t_r)·U(x̂_{0,LR}^i) + t_r·ε^i，U 为 latent 空间上采样，t_r 为跨 segment 固定的精修时间步。S2 由此把 540p → 720p 而保持 25–42 FPS：主干继续低分辨率快跑，轻量 Refiner 单步抬分辨率。

状态管理：TwinCache 与 RoPE 重定位

这是 S 系列最值得借鉴的两项设计，都属于「运行时状态」而非「网络结构」：

TwinCache
阶段感知双缓存
每个后续状态维护两份缓存：取自预设去噪步的 noisy cache 与最终去噪步后的 clean cache。中间去噪步用 noisy 历史——其中残余噪声保留粗粒度时序动态、抑制高频伪影随长自回归累积，相当于一种隐式低通先验，提供稳定时序引导但不对外观强约束；最终去噪步切换为 clean 历史以恢复细节、保持时序连贯与身份一致。本质是把时序传播与外观精修解耦。
持久参考上下文
sink 的对应物
滑动窗口由三部分构成：① 持久参考上下文（用户首帧的 latent token + 第一个生成的音视频状态，只构造一次、全程固定，作用类似 LLM 的 sink token）；② 窗口内缓存的历史音视频状态；③ 当前正在去噪的状态。因为窗口定长，每步推理时延与已生成长度无关。
RoPE Repositioning
见 §5.3
先缓存 KV、再施加 RoPE；窗口前进时按缓存特征在新窗口中的相对位置重新施加 RoPE。
非对称噪声缓存
S2 新增
主干关注高噪声缓存 x̂_{τ_B}^{<i} 以传播粗粒度运动与长程时序结构；Refiner 关注低噪声、高分辨率缓存 x̂_{τ_R,HR}^{<i}，且 τ_B > τ_R。同一条 replay 轨迹内所有 chunk 共享同一 τ_R。由此把时序传播与空间细节恢复彻底解耦。
S2-Editing 的结构差异值得单独记：编辑任务的目标不是「生成合理内容」，而是完全保留源视频的运动与时序、只替换外观。其核心机制是 frame-aligned attention——每个目标帧只读同一时间步的源帧，从而保证运动与节奏严格一致；同时参考图对所有帧可见，使新外观贯穿全片。流式运行时，源帧在与对应目标帧一起被消费后不进入缓存，以节省显存。这是一条通用的设计模式：把「必须严格对齐的输入」按时间对齐消费掉，而不是塞进长期缓存。

1.3爱诗科技（PixVerse）R2：单一因果骨干 + 三通道记忆

先澄清一个命名问题：公开可核实的公司世界模型线是 R1 → R2，未发现任何名为「realm」的模型。R2 的技术报告（2026-08-23）与产品博文（2026-09-22）披露了目前四家中最完整的训练配方。

R2 的方法论贡献在于「砍掉了两个阶段」。传统链条是「双向 → AR 转换 → 任务专用蒸馏 teacher → DMD → self-rollout DMD」，R2 合并为两步：① Omni Causal AR 持续预训练；② Real-Time Acceleration 直接蒸馏同一个因果底座——student 的 ODE 初始化与 teacher 都来自同一因果模型，不另训 fast model。这一点的工程含义很大：避免了「双向教师 → 因果学生」之间的架构间隙（见 §2.3 关于 frame-level injectivity 的讨论）。

六项系统设计

Phase 1 · 相机可控微调：PRoPE 如何把几何注入注意力

给定相机参数 {(K_i, T_i^{cw})}，把每帧相机抬升为投影矩阵 P̃_i = [[ K_i 0 ] T_i^{cw} ; e₄ᵀ ] ∈ R^{4×4} 对属于第 i(t) 帧、空间坐标 (x_t, y_t) 的 token，构造块对角变换 D_t^{PRoPE} = diag( I_{d/8} ⊗ P̃_{i(t)} , diag( RoPE_{d/4}(x_t) , RoPE_{d/4}(y_t) ) ) 以 GTA 形式注入自注意力 Attn_PRoPE(Q,K,V) = D ⊙ Attn( Dᵀ⊙Q , D⁻¹⊙K , D⁻¹⊙V ) ⇒ token 间交互显式依赖相对投影变换 P̃_{i(t₁)} P̃_{i(t₂)}⁻¹ （同时编码相对内参与相对位姿），且不破坏原自注意力的生成结构

关键在于「不是把动作简单拼到 latent 上」：PRoPE 用投影矩阵把相机内外参转化为 token 间的相对射影变换，因此保留了原有生成结构，同时让空间 token 感知相机运动。工程含义是：需要支持 Q/K/V 前后的结构化变换与 RoPE 融合，避免大量小算子与 layout 往返。

02B 段 · 后训练

Forcing 家族：把训练分布搬到推理分布

块级因果结构给了我们「能增量算」的形状，但它立刻制造了一个新问题：训练时模型看到的历史是真实的、干净的；推理时它看到的历史是自己生成的、带噪的、有误差的。这个落差会让长 rollout 在几十块后崩塌。Forcing 家族就是专门修补这个落差的训练方法集合——而且它的最新进展已经把一个看起来是工程细节的问题（用哪个 teacher 做初始化）提升为理论问题。

本章按「修什么」组织：先给出误差累积的形式化描述，再拆开 forcing 的两个独立旋钮（历史加噪与梯度穿透），然后给出目前已收敛的四阶段因果化流水线，最后逐条对照 10+ 个 forcing 变体。读完本章应能回答：给定一个双向教师，把它变成能长跑的因果学生，最少需要哪几步，以及哪一步最容易被做错。

2.1病根：暴露偏差在视频里比在语言里更致命

把流式生成写成自回归形式：第 n 块的生成依赖前 n−1 块的输出，而这些输出又是模型自己采样得到的。于是误差满足一个递推关系：

训练期（Teacher Forcing）： x̂_n = f_θ( x_{<n} , c_n ) ← 历史是真值 推理期（Autoregressive）： x̂_n = f_θ( x̂_{<n} , c_n ) ← 历史是自己的采样 设单块误差 ε_n = ‖x̂_n − x_n‖，则 ε_n ≤ ‖∂f/∂x‖ · ε_{n−1} + η （‖∂f/∂x‖ > 1 时误差指数放大） 视频与语言的关键差别： LLM 的误差落在离散 token上，解码器有采样温度与重复惩罚等纠偏机制； 视频 DiT 的误差落在连续 latent上，会通过 VAE 解码放大为可见伪影 ⇒ 表现为身份漂移、动作断裂、背景突变，而非「某一句话跑偏」 Causal Forcing 论文对这一步给了更精确的诊断： 「连续 latent 空间中的误差复合」── 学生训练视野之外外推时质量显著退化

这就是 forcing 类方法的目标函数来源：不是提高单块质量，而是提高「在自己生成的历史条件下继续生成」的稳定性。它天然是一项后训练任务——必须建立在已经具备块级因果接口的模型之上。

2.2两个独立旋钮：加噪级别与梯度是否穿透

把所有 forcing 变体拆开看，它们都在回答两个正交问题。这两个旋钮的组合几乎穷举了整个设计空间，也是判断一篇新工作是否真的「新」的最快方法：

旋钮 1

历史被加噪到什么程度？

  • 不加噪（干净历史）：Teacher Forcing。最保守，误差累积最严重。但 Causal Forcing 的消融给出了一个反直觉结论：TF 优于 DF 作为 AR 阶段的训练方式——干净历史保住了质量上限。
  • 随机级别加噪：Diffusion Forcing。每个时序 token 独立采样噪声级，证明优化所有子序列似然的变分下界，能力是生成长度超出训练视野的 rollout（baseline 会发散）。
  • 按概率混合：Vidu / LingBot / 爱诗 R2 采用的做法——每样本按 Bernoulli(p) 抽样决定该用干净 GT 前缀（TF）还是加噪前缀（DF）。TF 保证条件同步与运动一致性，DF 提升对不完美前缀的鲁棒性。
  • 重放时再独立加噪：Self-Replay Forcing。在自生成轨迹上按 Diffusion Forcing 对所有 segment 独立重新加噪。
旋钮 2

梯度是否穿过历史？

  • 完全 detach：Self-Forcing 的做法——原文明确「we additionally detach the gradients of the previous frames from the current frame during training by restricting gradient flow into KV cache embeddings」。省显存，但后段损失无法修正前段表示。
  • 只对最后一步反传：Self-Forcing 的随机梯度截断——只对每帧最后一个去噪步反传，反向过程只回传到第 s 步。
  • 随机退出步：每序列每轮从 Uniform(1..T) 采样 s，用第 s 步输出作最终输出，保证所有中间去噪步都收到监督。这是使梯度截断可行的关键配套。
  • 分块重放（replay）：Self-Replay Forcing——rollout 时 detach，再在单次梯度使能的因果 replay 中重放整条轨迹；replay 内所有 segment 处于同一计算图，后段 loss 可传播至前段，但梯度不回穿原始 rollout。

2.3已收敛的四阶段因果化流水线

把 minWM、Causal Forcing、LingBot、Vidu、爱诗 R2 的配方并排看，会发现它们已经收敛到同一条流水线。这不是巧合，而是被一个理论结论逼出来的：

关键理论结论（Causal Forcing，arXiv 2602.02214 · ICML 2026）：ODE 蒸馏要求 frame-level injectivity。把双向 DiT 蒸馏成少步 AR 学生存在架构鸿沟。既有做法用 ODE 蒸馏初始化 AR 学生，但 ODE 蒸馏要求「每个带噪帧在 teacher 的 PF-ODE 下必须映射到唯一干净帧」——用双向 teacher 违反该条件：双向模型的 PF-ODE 只在 video level 单射，于是同一个 noisy frame 会对应多个 clean frame，回归解退化为条件期望，产生模糊与不一致。作者用「用标准 DMD 初始化 AR student」的对照实验证明 DMD 阶段无法弥补这个初始化缺陷。
解法：ODE 初始化的 teacher 必须是 AR 模型，不能是双向模型。
STAGE 1TF 训练 AR 扩散模型把干净视频与其加噪副本拼接 + 因果注意力掩码。
产物：有 AR 能力但仍多步、且因 exposure bias 质量低于双向模型。
注意：论文同时从理论与实证说明 TF 优于 DF 作为这一阶段的方式。
STAGE 2少步 AR 初始化（ODE 或 CD）两种等价路径：
· causal ODE（Causal Forcing）：用 AR teacher 在 PF-ODE 轨迹上采样，回归 G_θ(x_t^i, x_gt^{<i}, t) → x_0^i
· causal CD（Causal Forcing++）：用 AR teacher 从 x_t^i 走一步 ODE 得到 x̂_{t−Δt}^i，与 EMA student 做加权距离。免去离线 ODE 数据的生成时间与存储开销。
论文洞察：causal CD 学到与 causal ODE 相同的 AR-conditional flow map，但监督来自相邻步之间单次在线 teacher ODE step。
STAGE 3非对称 DMDstudent 自 rollout 生成完整序列 → 加噪 → 用冻结双向模型 s_real 与在线训练 s_fake 的分数差做 DMD 梯度。
爱诗 R2 的表述更简洁：student 的 ODE 初始化与 teacher 都来自同一因果模型，不另训 fast model——从根上规避架构间隙。
STAGE 4长轨迹 / 长上下文精炼把 DMD 放到长 self-rollout 轨迹上做（LingBot v2），或用长上下文 teacher 蒸馏长上下文 student（Context Forcing），或引入错误回放（爱诗 R2 的 Error Bank）。
目标是让优化状态覆盖推理时真正会到达的状态分布。

这条流水线的三个「易错点」值得单独标出：① Stage 2 的 teacher 必须是 AR 模型（否则初始化理论上不成立）；② Stage 1 用 TF 而非 DF（与直觉相反，但论文有理论与实证支持）；③ 条件必须贯穿全流程——minWM 的相机条件在 Stage 1/2/3 全部注入，否则蒸馏会把条件抹掉。

03B 段 · 后训练

蒸馏与少步化：把 NFE 从几十压到 1–4

结构决定了「每块要算几次主干」，蒸馏决定这个次数是多少。这是四个杠杆里单项收益最大、也最容易被误用的一层：它能把采样步数砍掉一个数量级，但代价是模式多样性下降、训练复杂度上升，且与量化、稀疏的误差会互相放大。

本章的核心组织原则是一条 2026 年才被明确提出的理论线索：蒸馏目标分为「前向散度」与「反向散度」两类，它们在质量与多样性上的偏好恰好相反，而且天然互补。理解这条分界之后，DMD / PCM / rCM / DP-DMD / DMAD / TDD 这些名字就不再是一堆并列的选项，而是可以按「我用哪一类散度、怎么补另一类」来归位的。（本节按用户所列名称组织，但把命名核实结果放在 §3.2 与附录中逐条说明。）

3.1先算清楚预算：NFE 是被「实时」逼出来的

采样步数不是审美选择，而是一个可算的约束。以 720p、25 FPS 的数字人为例：

实时约束： 每块生成时间 ≤ 该块播放时长 T_chunk ≤ F_chunk / FPS 其中 T_chunk = NFE × ( T_DiT + T_attn ) + T_VAE + T_其他 F_chunk = 块内帧数 代入一个具体数字：块 8 帧 @ 25 FPS ⇒ T_chunk ≤ 320 ms 若单步主干（含注意力）为 60 ms、VAE 为 40 ms： 60 · NFE + 40 ≤ 320 ⇒ NFE ≤ 4.6 ⇒ 结论：720p 实时数字人的可行区间被算术锁死在 4 步左右， 这正是 Causal Forcing++ 把目标定在「frame-wise 1–2 步」的动机来源。
反过来读这条公式：当 NFE 从 50 压到 4，主干占比下降、VAE 与调度开销的占比相对上升。这正是 §9.5 必须做 DiT–VAE 异步流水的原因——蒸馏把瓶颈从算力搬到了流水线上。

③ 「SpargeAttention」的正确名称是 SpargeAttn，且它是 training-free 通用稀疏+量化方法（两阶段在线过滤：先快速预测注意力图跳过部分 matmul，再用零额外开销的在线 softmax-aware filter 进一步跳过）。

3.3模式崩溃：为什么它比图像领域更严重

视频蒸馏的三个特有难点

难点 1

误差有「时间放大器」

图像蒸馏的模式崩溃表现为局部伪影；视频蒸馏的模式崩溃会通过时间维度放大为运动异常——镜头漂移、动作退化、时序不一致。这就是为什么 Vidu 必须在 DMD 目标上叠加感知特征距离。

难点 2

蒸馏粒度：帧级 vs 块级

块级蒸馏（一次生成若干帧）与帧级蒸馏（逐帧自回归）在误差累积特性上完全不同。帧级路线（Causal Forcing++ 的 frame-wise 1–2 步）把预算压得更低，但每帧都要重新做一次因果推进，误差累积的机会更多。Causal Forcing++ 的报告显示帧级 2 步仍能超过 chunk-wise 4 步，说明粒度选择的收益主要来自初始化质量而非粒度本身。

难点 3

初始化决定上限（2026 年最重要的结论）

Causal-rCM 的诊断很直接：SF + DMD/GAN 对初始化敏感且会 mode collapse（因 DMD 基于 reverse-KL）。文献中已用过的初始化策略包括 ODE-pair regression（Self-Forcing、Causal Forcing、APT2）、DF 式因果适配（LongLive）、混合 TF/DF（Magi-1）。选错初始化，后面的 DMD 阶段补不回来。

联合优化：为什么「分别做到最好」会输给「一起做」

前三章把结构、forcing、蒸馏当成三件独立的事。但真实系统里它们的误差会互相放大，而且共享同一批超参数：量化的块粒度、稀疏的块粒度、kernel 的 tile 大小往往是同一个数字。这一章讨论的正是「不能分开决定」的那部分。

先给出本章的核心判断：所有加速手段最终都在回答同一个受约束优化问题——在固定的质量与延迟约束下，如何分配算力预算。差别只在于它们把预算花在哪个维度、在训练还是在推理时决定。理解这一点之后，各种「×× Diffusion / Flash××× / ×××Fusion」的命名差异就不再重要，重要的是判断它属于哪一类联合、耦合点在哪里。

SparkDiffusion：为什么「训练损失在降、质量在退」

SparkDiffusion 的诊断值得逐字理解，因为它是本章论点的最强证据：在极端注意力稀疏度下，step-local 的训练损失持续下降，但最终（terminal）生成质量停滞甚至退化——作者把这称为 high-sparsity trap（高稀疏陷阱）。他们的结论是，这个陷阱本质上是监督问题而非容量问题：主导性的终端误差源自高噪声的结构生成阶段，而 terminal-aligned（对齐终端的）训练能够修正 step-local 训练即使大幅延长也修不了的终端误差。

staging principle

先把稀疏架构适配成 coarse prior

先用短期的 sparse warm-up 让模型在稀疏模式下建立可用的粗粒度先验，而不是一上来就追求终端质量。

再修正终端分布

少步 trajectory-mixed distillation

在粗先验之上做混合轨迹的少步蒸馏，让监督信号对齐最终输出的分布，而不是各去噪步的局部误差。

精度层收尾

FP8 量化 + fused kernels

最后才引入 FP8 与融合算子，把精度层的近似放在已被稀疏与蒸馏塑形过的模型上。

公开数字（口径要看清）：在 Wan2.1 / Wan2.2 骨干与 T2V / I2V 任务上，长序列 720P 生成维持 97% 注意力稀疏度（Wan2.1-T2V-1.3B-480P 为 90%）且视觉质量强。3 步 CFG-free 推理下，Wan2.1-T2V-14B-720P 在单张 RTX 5090 上相对 50 步 CFG dense baseline 端到端加速 265×（H100 上 220×）；1.3B-480P 去噪一段视频仅 1.3 秒。
注意：这仍是双向离线 T2V/I2V 的口径，与流式世界模型的场景不同——引用时不要与 Self-Forcing 系的实时数字混用。

FlashForward：把「额外前向」变成「顺手复用」

FlashForward 的问题设定非常具体，也是所有少步 AR 系统都会遇到的一个隐藏开销：为记忆已生成的 chunk，既有方法需要额外做一次前向来重建「干净或低噪」的 KV cache——这次前向不推进输出 latent，是纯开销。它的三步解法：

① 复用「在飞」的 KV不做额外的 cache-update 前向每次去噪前向本身就计算了当前 chunk 的 in-flight KV ⇒ 直接复用。当前 chunk 完成一个去噪 stage 后，其 stage-specific cache 已可供下一个 chunk 使用。
② stage 级流水线并行每张 GPU 负责一个 stage于是不同 chunk 可以并发处于不同去噪阶段——这与 §9.5 的「共享时间线」是同一思想的另一种切分：Vidu 按模块切（主干/Refiner/VAE），FlashForward 按去噪 stage 切。
③ clean anchor 双侧条件用稀疏干净锚点补回质量早可用性的代价是 stage-matched history 带噪，导致 chunk 间外观与运动漂移。补法是在对应区域生成之前先生成稀疏的辅助 clean anchor latents，形成双侧条件（two-sided conditioning）。
结果：双时间尺度记忆两种记忆分工稀疏 clean anchor KV 提供粗粒度、长程、双侧结构引导；稠密 stage-matched history 保留精细、近期的演化。
公开数字：最多 4 张 GPU 下，对 ≥20 秒的 16 FPS 视频，比 HiAR 快 1.16–1.69×、比 Self-Forcing 快 1.42–2.92×；覆盖 1.3B 与 14B 骨干、480p 与 720p；在 20s / 35s / 65s 三档时长均生成高质量且时序一致的结果。
注意与 §9.5 的关系：FlashForward 与 Vidu 的共享时间线解决的是同一类问题，但前者不需要改模型（只重排执行），后者需要模型支持主干与 Refiner 的解耦。这正好对应下一节「三种合作形态」中的 B 与 C。

4.3三种「合作」形态：训练期、推理期、调度期

合作形态 A

训练期吸收近似

在训练时就让学生以目标近似模式工作：目标稀疏掩码、目标量化精度、目标步数。近似误差被优化器吸收到权重里，推理期只需执行。
代价：每换一种推理配置就要重训或至少微调一轮。

合作形态 B

推理期动态分配

保持权重通用，按当前块的实际难度动态调整 NFE、稀疏率、量化精度、缓存窗口。稳定段走低成本快路，关键事件临时增步或回退高质量路径。
代价：动态策略与图编译冲突，且需要可靠的难度/漂移估计信号。

合作形态 C

调度期重叠隐藏

算法层已无法再省时，就把不可避免的延迟重叠掉：DiT(n+1) ∥ VAE(n)、生成 ∥ 编码 ∥ 传输、多会话合批、空闲会话卸载。
代价：显存峰值由「同时在飞的块数」决定，需要按阶段估算。

三者不是替代关系，而是一条收益递减的次序：形态 A 收益最大但要重训；形态 B 不需要重训但需要动态执行能力；形态 C 不改变数值结果，是最后一道「免费」收益。工程上常见的错误顺序是先做 C 再做 A——把调度优化建立在尚未被算法层压低的成本上，结果 Amdahl 定律让 C 的收益看起来「不显著」，从而错误地放弃了真正的大头。

4.4三条可执行的联合优化原则

  1. 共享超参只有一个主人。块粒度这类同时影响稀疏、量化、tiling 的参数，必须在设计阶段就由三方共同确定，并在三方各自的评测里分别回归。不允许任何一层「默认沿用」另一层的取值而不做验证。
  2. 误差必须端到端验收，不能分项相加。「蒸馏省 3×、量化省 1.4×、稀疏省 1.8×」不等于「端到端省 7.5×」。公开系统里从来没有出现过乘性叠加的实测结果，通常远低于乘积，甚至出现负收益。唯一的可信做法是在同一份代码、同一硬件、同一质量门槛下测量组合结果。
  3. 先定质量门槛，再谈加速。需要先锁定一组「不可退化的指标」（例如逐块漂移曲线、动作响应误差、多样性下限），然后才允许调预算。反过来做（先追加速再看质量掉多少）几乎必然导致后期返工，因为少步 + 量化的退化是时间累积型而非单帧型。
本章与后续章节的关系：第 5–7 章讨论的 RoPE、KV、服务化都可以被理解为「在既定预算下如何执行」。因此第 4 章是分界线：A 段与 B 段（第 1–4 章）决定预算，C 段（第 5–7 章）决定如何花掉预算。先有后训练、后推理——顺序颠倒会让优化失去目标函数。
05C 段 · 推理

RoPE：长上下文的位置编码改造

块级因果结构解决了「能不能增量算」，KV Cache 解决了「要不要重算」，但两者一旦合起来，就立刻暴露第三个问题：缓存里的 K/V 是在旧的绝对位置下算出来的。位置编码成了长上下文的隐形瓶颈。

本章讨论为什么流式视频模型几乎都要动 RoPE、动的是哪几类、以及 Infinity RoPE / LoL / Flex 这几条路线各自解决什么。要点先给：RoPE 问题不是「能不能外推」，而是「缓存复用与相对位置正确性能否同时成立」。多数工程事故不是模型不会外推，而是缓存与位置编码的施加时机错了。

5.1为什么流式视频比 LLM 更依赖 RoPE 改造

尺寸对齐

空间轴需要精确的 2D 相对关系

LLM 只有一维序列；视频 token 同时有 (t,h,w)，空间相邻关系直接决定画质与几何一致性。RoPE 的频段分配如果偏向时间轴，空间细节会先坏。

长度无界

交互式生成的时长没有先验上界

离线模型只需覆盖 5–16 秒；实时数字人、世界模型要求会话可持续数十分钟。位置索引必然越出训练分布，这是结构性矛盾而非调参问题。

状态复用

缓存让位置编码从「一次性」变成「可迁移状态」

在 LLM 中 RoPE 在写缓存前施加即可；在滑窗视频缓存中，历史 K 会被反复读取，位置编码必须与缓存生命周期解耦。

5.3参考实现：Vidu S1 / S2 的 RoPE Repositioning

证据口径提示：本条机制描述来自生数 Vidu S1/S2 技术报告的口径整理；在本次独立核查中，未能从抓取到的 Vidu 论文正文里定位到「RoPE Repositioning」这一命名的机制段落（可确认的是 S2 保留了 sink blocks + 滑动窗口上下文 + noisy KV caches 与 TwinCache 非对称噪声缓存）。因此本节应读作「与 Deep Forcing / Infinity-RoPE 等同族设计的一个工程表述」，其具体命名与实现细节有待以论文原文二次确认。

S2 论文披露的机制可以逐句核对，也是目前公开材料里最完整的一条流式 RoPE 工程描述：

缓存内容
KV 特征在应用 RoPE 之前被写入缓存——缓存里保存的是「未旋转」的 K。
写入时机
每个历史块的 K 只投影一次，之后不再重算；窗口滚动时也不重新投影历史 token。
读取时机
注意力计算前，按更新后的相对位置对缓存 K 施加位置编码，使当前 Q 与历史 K 的相对差始终等价于一个短窗内的距离。
收益
既避免重算历史特征，又保证可见位置始终落在训练时见过的范围内，从而把「位置外推」问题转化为「位置重索引」问题。
代价
注意力算子必须支持「带外位置源」——位置编码不能提前烘进缓存，对 kernel 接口和图编译都提出新要求。

这条设计把 RoPE 从「模型结构里的一个固定层」变成「推理运行时的一个显式状态转换」。对迁移工作的直接含义是：RoPE 位置表、缓存布局、注意力 kernel 三者必须一起设计，不能分别移植。

5.5LoL 与 sink-collapse：位置编码的反向风险

命名澄清（重要）：LoL 不是 RoPE 外推方法。LoL = 「Longer than Longer」（arXiv 2601.16914 · CVPR 2026，标题 «LoL: Longer than Longer, Scaling Video Generation to Hour»）。检索中未出现「Long-Long RoPE」或「Level-of-Line RoPE」这类展开——那很可能是对标题的误读。

LoL 的真正价值在于它命名并解释了一个由位置编码引发的失败模式：

现象

sink-collapse（注意力汇坍塌）

用 attention sink 帧缓解长时衰减，会诱发一种失败模式：生成内容反复「回退」到 sink 帧，造成突兀的场景重置与循环运动模式。

这不是「忘了」，而是「过度记得」——与 §2.6 中 Matrix-Game 2.0 的消融结论（cache 越大反而越早出现伪影，早期伪影被「记忆」成合法场景元素）是同一种病。

根因

RoPE 周期性与多头注意力的冲突

作者把根因定位为 RoPE 的周期性结构与当前生成模型普遍的多头注意力机制之间的内在冲突：不同 head 在长序列上趋于「注意力同质化」，从而被 sink 帧系统性地吸引。

这是一个值得记住的视角：位置编码的周期性不再是无害的近似，而会成为长时坍塌的机制来源。

解法

multi-head RoPE jitter

轻量、training-free：引入多头 RoPE 抖动，打破头间注意力同质化，从而缓解长时坍塌，同时保持生成质量。

公开结果：作者称首次展示实时、流式、无限长且质量几乎不衰减的视频生成，连续视频最长 12 小时。

把它和 §5.4 放在一起看，会得到一条重要判据：「给位置编码做加法」和「给位置编码做减法」都可能坏事。
· 不做任何处理 ⇒ 相对距离越拉越大 ⇒ 注意力发散、语义还在但画面糊（§5.1 的判据）
· 保留 sink 但不处理它的位置 ⇒ 内容反复回退到 sink ⇒ 场景重置与循环运动（LoL 的 sink-collapse）
· 正确做法 ⇒ sink 保留 + 其位置参与重定位/抖动，使「锚定的稳定性」与「位置的可区分性」同时成立。Deep Forcing 的 Temporal RoPE Adjustment 与 LoL 的 jitter 正是分别从这两侧下手。

动态分配：从「超参」到「策略」的三个可实现形态

缩放类与频率衰减类改造都需要预先决定超参（缩放因子、衰减强度、层间差异）。另一条思路是取消这个先验：把 RoPE 的频率分配做成可按上下文长度、层深、甚至训练阶段调整的策略，而不是一次性写死的常数。工程上对应三种形态——成本差异很大：

  • 按层分配：浅层负责局部细节，深层承担长程聚合；给浅层更高的时间分辨率、给深层更强的缩放。这是最容易被忽略但收益稳定的一项。
  • 按位置分配：近邻 token 用原始频率（保细节），远距离 token 用压缩频率（保可达性）。相当于在位置空间做「分段精度」。
  • 按阶段分配：预训练用原始 RoPE，长上下文后训练阶段再引入缩放或衰减，让模型在新位置分布上做少量适配——这也是唯一能让改造真正「被模型接受」的路径。
不要只改推理：RoPE 改造的效果高度依赖模型是否在目标位置分布上训练过。仅推理端替换缩放因子或衰减强度，通常表现为前 10 秒正常、之后运动幅度衰减。这类改造必须与一个短周期的长上下文后训练阶段配对，或者退回到只使用重定位这条更安全的路线（它不改变位置分布本身，只是重新索引）。这也解释了为什么 Infinity-RoPE 明确把自身定位为 training-free 的「推理期统一框架」——它的三个组件都不需要重新训练。

06C 段 · 推理

分布式稀疏并行：db-SP、FVAttn 与 OSP-Next

前几章的稀疏与量化都是在单卡视角下讨论的。一旦长视频要跨卡，稀疏就从「少算几个块」变成一个分布式调度问题：决定算哪些块所需的信息，在你这一步的局部视野里拿得到吗？拿不到，整个方案就不成立——这不是实现细节，而是可行性边界。

本章以三篇主线论文为骨架：db-SP（arXiv 2511.23113，清华，把「Ring + 块稀疏」的负载不均衡第一次量化出来）、FVAttn（arXiv 2607.16190，中山大学 / 腾讯微信，运行时负载均衡）、OSP-Next（arXiv 2605.28691，北大 PKU-YuanGroup 等，规则化稀疏 + HiF8 量化，只需一次 All-to-All）。核心结论先给：数据依赖的 Top-k 稀疏在 Ring 上有四个结构性障碍，其中两个基本无法工程绕过；能上 Ring 的稀疏必须是「可离线确定」或「阈值型」的。

6.1先写清前提：Ring 的代价模型与三条硬约束

Ring Attention 的代价模型：用 P 倍的 KV 通信，换 1/P 的 KV 显存 M_ring = KV_total / P ← 显存收益，随并行度 P 线性下降 Comm = KV_total · 2(P−1)/P ← 通信代价，约 2× 一次性拉取 原论文的显存模型（arXiv 2310.01889） M_ring = b · 6 · c · h ← 随块大小 c 线性，与序列长度无关 构成：1 块 query + 2 块当前 K/V + 2 块接收中 K/V + 1 块输出 通信被计算掩盖的条件（这是 Ring 的收益前提） 4·d·c² / F ≥ 4·c·d / B ⟹ c ≥ F / B 机制本质：Ring 是深度为 P 的流水线，不是「把序列切开各算各的」。 每个 rank 持有本地 Q，K/V 块沿环流转 P 次，每轮做一次 blockwise attention 并用 online softmax 累加。收益来自第 i 轮的通信与第 i+1 轮的计算重叠。 ⇒ 重叠成立时通信免费；不成立时 Ring 退化成一个通信开销极大的方案。

6.2一个关键的几何事实：Ring 不缺块，它算多了

因果块稀疏掩码，永远是因果稠密掩码的子集。也就是说，一个 query 块需要的所有 K/V 块，因果 ring 本来就都会送到它手上。Ring 并没有「送错块」的问题——它的问题是把所有块都算了。

推论：Ring + 块稀疏的改造目标不是「怎么把需要的块送到」，而是「送到之后怎么决定算哪几个」。这个视角转换会让后面所有分析清晰很多。

6.3OSP-Next：把「稀疏选择」转化为「固定重排」

OSP-Next 是目前拿到最好公开数字的「规则化稀疏 + 序列并行 + 8bit 量化」方案：VBench 83.73%（超过 Wan2.1 基线）、950PR 单卡 2.27×。但它的机制需要被准确理解——它绕开四个障碍的方式不是「更聪明的选择」，而是「不需要选择」。

Skiparse Rearrange 的「局部等价性」

论文 Algorithm 1 里的 orig_to_tsa 是全部关键： def orig_to_tsa(x, T, H, W, P): return rearrange(x, "b (t h p w q) c -> (p q b) (t h w) c", p=P, q=P, h=H//P, w=W//P) 它做的是像素 unshuffle：把一个 H×W 的图，按 (p, q) 下标拆成 P² 个子图， 每个子图 (H/P)×(W/P)。 关键性质：这个 rearrange 是「单元局部」的 对整张图做 rearrange ≡ 独立地对每个 k²×k² 的最小单元做 rearrange 为什么这重要 —— 它把「全局重排」降级成了「局部重排」： · 一个 token 该进哪个真子序列，只由它自己的 (h,w) 坐标决定 · 因此映射可以离线预先算好（一张固定索引表），运行时不需跨 rank 协商 · 更关键：它与序列切分可交换——先切分再各自 rearrange，与先 rearrange 再切分结果一致 ⇒ 这就是「可以分配给不同 rank 各自算」的合法性来源

为什么只要一次 All-to-All（对比 Ulysses 的 4 次）

G = P² / group_size # 真子序列被分成 G 组 b = B_local / G # 每组对应 b 个原 batch 元素 # ① 本地 rearrange（无通信）：把序列拆成 P² 条真子序列，拼到 batch 维 x = orig_to_tsa(x, T, H/P, W/P, P) # → [(p q b), (t h w), c] # ② 一次性 All-to-All：一次完成「序列维切分 → 真子序列维切分」的换轴 x = x.view(group_size, G, G*b, base, C) all_to_all_single(recv, x, group=group) # ③ 本地置换 + ④ 反向 rearrange（均无通信） 论文原话："data exchange to be completed by ONE local rearrangement on each rank followed by ONE All-to-All communication step within the communication group"
原因 1

换的是「轴」，不是「张量」

这里只有一份激活 x（Attention 的输入），Q/K/V 在后面用权重投影出来——所以不需要像 Ulysses 那样分三次搬 Q、K、V，也不需要第四次搬回输出。这是「1 次 vs 4 次」最主要的原因。

原因 2

目的地可离线确定 ⇒ 不需要全局求解阶段

这是更深层的原因。一般动态稀疏需要两阶段：① 全局求解「哪个 token 给哪个 rank」（须看全局信息，在 Ring 上代价高昂甚至不可能）；② 一次 All-to-All 实现它。局部等价性把 ① 消除了——索引表是固定的，直接执行 ②。

原因 3

真子序列等长 ⇒ 交换天然均衡

每个 rank 收发等量数据，All-to-All 是一对一的规则交换，不需要额外均衡；切分后各 rank 计算量天然相同——不触发 C1。

原因 4

稀疏来自「序列重组」，不是「挑块」

Skiparse-2D 的稀疏性来自每条真子序列内部做稠密注意力，而不是从全序列里挑块。它不需要打分、不需要全局排序、不需要预取、子序列等长所以负载天然均衡。

不要把 OSP-Next 的能力理解过头：那一次 All-to-All 的作用是在 token-wise（TSA）与 group-wise（GSA）两种模式之间切换（两种模式的真子序列划分不同，token 需要换手），它不是「把需要的 KV 块拉过来」。OSP-Next 的「稀疏」本质是把序列重组成多条短序列，然后各算 dense。这正是它绕开全部四个障碍的原因：它把「稀疏选择问题」转化成了「固定重排问题」。
另外要注意口径：它用的是 All-to-All（Ulysses 风格），不是 Ring P2P。把它搬到 Ring 上需要另行验证。

两种均衡思路，两个层次的权衡

db-SP · 提前均衡（静态划分）

把耦合的头级/块级问题解耦

用「每个层级都能独立接近完美均衡」这个先验，拆成两个顺序子问题，各自贪心。

开销抑制的关键：利用稀疏掩码在去噪步之间的相似性，设阈值 P_s，低于阈值就复用上一步的划分计划。动态稀疏下划分执行次数 = 层数 × 去噪步数，在 Wan2.1-T2V-14B 上高达约 2000 次——复用是把这份开销压到可忽略的关键。其前提是「跨步相似」，这在多步采样（如 50 步）下成立得很好。

公开结果：端到端 1.25×、attention 1.40×。

FVAttn · 运行时修复

等掩码 materialize 后再搬运

出发点是一个硬观测：4 步蒸馏下，相邻步同一 head 的密度变化最高 97%、同一 rank 负载变化最高 44%。预布局在用过期信号做决策。

做法：等掩码 materialize 后，按已实现的 per-head 负载，用受限 P2P 迁移少量重头 head（8 卡下每 rank ≤ 1 个，约 20% 本地 head），把不均衡从 1.34 压到 1.08；再用 SASA 把非关键 rank 的残余空隙兑换成额外的高价值块（不抬高全局阈值，因此不延长关键路径）。

FVAttn 不能直接搬到 Ring 上——这是结构问题，不是实现细节。FVAttn 明确写了它的前提是 Ulysses 风格：「each GPU holds complete sequences for a subset of attention heads」。在这个前提下每个 rank 的 Q 是完整的，所以它可以 ① 在掩码 materialize 后看到自己负责 head 的真实负载；② 用「迁移 head」而不是「迁移块」来做均衡——因为 head 是完整可搬运的单元。

而在 Ring 上，每个 rank 只有一段 Q，没有「完整的 head」可以搬运。所以 FVAttn 的调度单元在 Ring 上不存在。

6.5两条可执行路线，以及各主流稀疏方法的逐案判定

路线 A · 首选

把稀疏改成「可离线确定」的

做法：约束稀疏掩码只是「块位置坐标」的函数，不含任何数据依赖项。可用形态：Skiparse 类（固定 skip 间隔 + 交替模式，OSP-Next）；滑窗 + 全局块；块因果 + 条带（适用于自回归视频）；静态掩码 + 块内自洽。

收益：直接绕开全部四个障碍；不需要新算法；与 Ring 的流水线天然兼容。

代价：稀疏的「智能程度」下降。但 OSP-Next 的实测说明这个代价在视频上比想象中小——固定规则模式拿到了超过 full-attention 基线的 VBench。原因是视频的注意力冗余沿空间/时间邻域聚集，规则化掩码足以覆盖大部分重要交互。

路线 B · 备选

用低分辨率代理提前决策

思路：不在原始分辨率上打分，而是在下采样后的 KV 上跑选择器。这直接缓解障碍一（循环依赖）——代理 KV 很小，可以在 ring 开始前就准备好。代理的字节量约为 KV 的 1/r（r 为下采样比，如 32）。

风险（三条，逐条都致命）：① 代理仍需一次全局可见性（all-gather 或随环流转一次），引入新同步点，触碰 C2；② 代理给出的块级决策是近似的，误差直接进入注意力输出；③ 代理决策仍逐 Q 块不同，障碍二（Top-k 集合与 Q 属主耦合）没有解决——只是把「需要全精度 K」换成了「需要低精度全局 K」。

结论：路线 B 能缓解障碍一和三，解决不了障碍二和四。只有在路线 A 的规则形态不足以达到质量目标时才考虑。

6.6量化 × Ring：scale 的作用域是第二个可行性边界

稀疏之外，量化在环上还多一层约束——scale 挂在哪里，决定了它能不能随块一起走。四个必须理解的断点：

断点 1

不能在环上反量化

反量化必须发生在数据到达并进入计算之前的本地环节，不能作为环上流转的一部分——否则通信量按高精度计算，量化的全部收益消失。

断点 2

量化只能作用在 K/V/P 上，绝不能作用在 softmax 统计量上

跨块 LSE 合并是 Ring 每轮的合并原语。softmax 统计量必须保持 FLOAT32——这与昇腾 RingAttentionUpdate 算子「softmax 统计量强制 FLOAT32」的设计一致。

断点 3

P 的量化误差会沿环累积

P（注意力概率矩阵）参与每轮的 online softmax 累加，误差随环上跳数累积，而不是一次性的。这与单卡上「P 量化误差局部可控」的结论完全不同。

断点 4

平滑统计量的全局性

SageAttention 用 mean(K) 作平滑因子，而这是全序列均值。在 Ring 上获取它需要一次全局归约——直接触碰 C2。这解释了为什么 SageAttention 的原始形式不能直接上 Ring，必须改用可分块的替代量。

把 §6.1 的 C3 与本节合起来读：块是环上的最小传输单元，所以量化 scale 必须是块级（per-tile）的，并挂在块上一起走。per-tensor scale 需要全局统计（触碰 C2），per-channel scale 需要在环上重排布局（破坏 C3）。这也解释了 OSP-Next 为什么选 HiF8（HIFLOAT8）路线——它的消融显示 HiF8 训练的 loss 曲线与 BF16 基本一致，精度代价小到可以接受，同时格式本身对块级 scale 友好。

07C 段 · 推理

多模态稀疏 MoE：把「容量」与「每步成本」解耦

前面所有章节都在同一个假设下工作：模型有多大，每步就要算多大。MoE 打破的正是这个假设——它让总容量（存多少）与激活量（算多少）成为两个可以分别调节的量。对长视频与世界模型来说，这是除量化之外唯一能同时改变「算」与「存」两条曲线的手段。

本章的组织逻辑是「先分清问题，再谈技术」：MoE 在视频生成里和在大语言模型里遇到的瓶颈完全不同——LLM 侧是显存带宽与 all-to-all 通信，视频侧是大量极窄专家带来的小算子风暴。混淆这两者，会导出错误的优化优先级。本章先给出容量/激活解耦的账本，再拆路由机制，然后分「少算」（系统层，以 FastMoE 为代表）与「少存」（模型层，以 DIET 为代表）两条线讲手段，最后落到视频与世界模型上的可核对实例。

7.1为什么 MoE 在大约 2025 年之后回到视野

把三个杠杆放在同一张账本上，MoE 的位置就清楚了：

三条独立曲线（以密集模型为基线） ① 每步算力 ∝ 激活参数量 ← 蒸馏/稀疏注意力/量化都在压这条 ② 每步显存 ∝ 权重 + KV + 激活 ← 量化与 KV 淘汰在压这条 ③ 模型容量 ∝ 总参数量 ← 只有 MoE 能把这条与 ① 解耦 MoE 的账本 总参数量 N_total = N_shared + N_experts · E ← 决定显存与容量 每步激活 N_active = N_shared + N_experts · k ← 决定算力（k = 激活专家数） ⇒ 稀疏度 s = k / E 典型 1/8 ~ 1/32 ⇒ 容量可以按 E 放大，而单步算力只按 k 增长 代价（必须同时计入） · 权重总量仍要存在某处 ⇒ 「少算」不等于「少存」 · 路由 + 重排 + 分散/聚合 的开销 ⇒ 少数 token、极窄专家时占比急剧上升 · 负载不均衡 ⇒ 专家并行下最热专家决定这一步的时间（与 §6 的 C1 同构）
关键认识：MoE 买到的是「容量」，不是「速度」。它把每步算力从总参数量上解耦，但权重总量并没有减少——只是不需要每次都用上。因此 MoE 的收益必须与「少存」手段（专家卸载、专家缓存、低比特）配合，才能同时改善曲线 ②。这也是本章把「少算」与「少存」分成两节的原因：它们是两个不同的工程问题，用错了手段会得出「MoE 没用」的结论。

7.3系统侧的两条线：少算与少存

这一节按「改系统」还是「改模型」分成两层。FastMoE（arXiv 2103.13262）是系统层的代表——它让 MoE 跑得更快；DIET（arXiv 2609.37829）是模型层的代表——它直接裁掉专家，把「少存」做成一次性的、可验证的结构改动。两者解决的是完全不同的浪费，且可以叠加。

线 1 · 少算（系统层）

把稀疏激活真正变成时间节省

  • 全链融合：把 router / top-k → compact layout（按专家聚合 token）→ gate+up → 激活函数 → down → 加权 scatter 融合进尽量少的 kernel。这是视频侧第一优先项，不做这一步，稀疏只省了 FLOPs 而没省时间。
  • grouped / fused GEMM：把「几千个窄专家」的 GEMM 合并成一次分组矩阵乘，而不是逐专家发 kernel。这是 MoE 推理后端最核心的一项能力。
  • 固定形状通信：把动态 all-to-all 换成固定分片交换（head-local 路由的思路），代价是压力转移到本地窄专家的执行效率上。
  • 专家并行（EP）+ 负载均衡：EP 让每个设备只驻留一部分专家；但最热专家决定这一步的时间，因此需要动态专家负载均衡（EPLB 一类机制）把热门专家复制或迁移。

FastMoE 的定位：它属于这一层——不改模型、不改专家数量，只改 MoE 的执行方式（门控与专家的融合、避免逐专家循环、优化跨设备通信）。因此它的收益是「同一份权重跑得更快」，而对显存占用与 checkpoint 大小几乎没有帮助。引用它时不要把「加速」和「省显存」混为一谈。

线 2 · 少存（模型层）

让权重总量不成为瓶颈

  • 专家卸载（offload）：把当前步未激活的专家留在 host 内存或更低层存储。因为激活是稀疏的，这是 MoE 相对 dense 模型天生更擅长的一件事。
  • 专家缓存 / 预取：按路由的可预测性预取即将用到的专家。这里有一个关键前提——路由越可预测，缓存命中率越高，所以「时间维专家」（按 timestep 路由）天然比「token-choice 路由」更容易做缓存。
  • 低比特权重：MoE 的容量主要体现为权重总量，因此权重量化对 MoE 的「少存」收益格外直接。但要注意：窄专家的低精度 kernel 覆盖度往往差于大矩阵，可能只省显存不提速。
  • 专家裁剪（DIET 路线）：直接删掉冗余专家——这是唯一能把权重总量真正变小、且不引入搬运开销的手段。见下节。
  • 路由相关状态保持高精度：router 与门控通常应保持 FP32 —— 路由一旦抖错，整步的输出分布就变了，误差比单个专家内的数值误差更严重。

DIET：把「少存」做成一次性的结构改动

DIET（DeletIon-response Expert Trimming for Video Diffusion Transformers，arXiv 2609.37829，2026-09，西安交大 / 阿里云 / 上海交大）直指一个被 MoE 文献长期绕开的矛盾：动态稀疏省下了算力，但没有省下存储——E 个专家的权重仍然全部常驻。它给出的解法是裁掉专家，而且是 training-free 的。四步机制环环相扣：

STEP 1一次插桩标定跑一次「全专家」的插桩前向（120 个 case），记录所有专家的输出与 router 的 logits / gates / 选择结果，并对 CFG 的 conditional 与 unconditional token 做配对——共 368,640 对匹配 token，约 375 GB fp16 缓存状态，约为一次普通前向的 16× 专家算力。这部分代价只付一次。
STEP 2冻结状态重放（frozen-state replay）在缓存张量上重放「删除某一个专家 + 其 group 内 top-k 重新路由」的后果 = 纯张量运算，零额外前向。因此可以逐一评估全部 6,144 个 layer-local 删除（48 层 × 128 专家）。这是整个方法能成立的关键：把「评估一次删除」的成本从一次前向降到一次算术。
STEP 3删除响应签名s_{l,e} = 各 case 上 Δ_{l,e}(x) = y_{E\{e}}(x) − y_E(x) 的均值，跨 case 拼接。只用于判断「方向」（余弦相似度）——因为联合删除不满足线性叠加：联合扰动与单次响应之和的余弦相似度会从 1.00 掉到 0.66（k=64），重构误差升到 0.95。
STEP 4ODL 多样性目标 + 跨层预算搜索ODL（Overall Diversity Loss）用 k-median / 指派代价：每个被裁掉的专家要向最近的保留专家支付余弦距离。逐层用 GRASP 贪心初始化 + 单交换局部搜索 + 模拟退火求解。
再用回归引导的跨层预算搜索：在「每层保留数」向量上拟合正则化线性代理 y_d = w_dᵀk + b_d，再做约束 LP + 混合整数步分配——比均匀预算高 1.2 个点。

DIET 最反直觉、也最有价值的一条结论：实验表明质量最好的掩码恰恰是对原始路由扰动最大的那个；而那些「最不破坏路由」的判据，质量损失反而最大。也就是说——「尽量少改变路由」是一个错误的目标函数。

这条结论对整个 MoE 优化都有含义：它说明「让稀疏化尽量不影响原模型行为」这个直觉是错的。原因在于冗余专家被删掉后，路由本来就会重新分配负载；强行保持原路由等于把冗余固定在结构里。这与 §4.3 的「训练期吸收近似」是同一条逻辑——让模型在目标结构下重新工作，比让近似尽量逼近原结构更有效。

本章可以压缩成一句判断：MoE 买到的是容量，不是速度；要把它变成速度与可行性，取决于路由的可预知程度、窄专家的融合执行质量、以及是否愿意动结构去裁掉冗余专家。第一项决定你能不能做静态调度与专家缓存（FastMoE 那一层），第二项决定稀疏激活能不能真的省下时间，第三项决定权重总量能不能真正变小（DIET 那一层）——三项都成立时，MoE 才是长视频与世界模型里最值得投入的一层。

而 DIET 那条反直觉结论值得再强调一次：在 MoE 上，「尽量不改变原模型行为」不是正确的目标函数。这与本报告第 4 章的主线完全一致——让模型在目标结构下重新工作，比让近似尽量逼近原结构更有效。
08C 段 · 推理

KV Cache、注意力与量化：单步成本怎么砍

前两章把「调用几次主干」和「历史要不要重算」解决了。剩下的是纯粹的算子与存储问题：一次注意力到底要搬多少字节，缓存到底能放多长。这一层的收益不像蒸馏那样是数量级的，但它是把实时从「勉强」推到「有余量」、把会话从分钟推到十分钟的唯一路径。

本章围绕一条主线组织：FlashAttention 把 IO 复杂度做对了之后，注意力优化就没有免费的午餐了——只能沿着「少看一些」（稀疏/线性）、「少放一些」（KV 量化/淘汰）、「少搬一些」（布局与调度）三个方向同时吃收益，而这三者对精度的破坏位置完全不同。

8.2方向二：KV 与权重的量化（QuantWM / W8A8 / 分块粒度）

量化在这一层要区分四个完全不同的对象，它们的收益与风险不能混为一谈：

对象 A

权重（Linear / MLP）

收益最直接：显存与带宽近似按位宽比例下降，GEMM 走 INT8/FP8 Tensor Core。风险最低，通常第一个做。

对象 B

激活（W8A8 的 A）

收益依赖 kernel 支持；离群值使 per-tensor 量化脆弱，需要 分块粒度。风险中等，需逐层扫描。

对象 C

注意力（Q/K/V）

Q/K 可低比特、V 通常保守；softmax 邻域与 RMSNorm 对精度最敏感。需要与稀疏策略联合评估。

对象 D

KV Cache 本身

收益是会话容量而非单步速度：位宽减半 ⇒ 同等显存下上下文翻倍。风险最高，误差会随会话时长累积。

QuantWM（arXiv 2609.26425，Temporally Consistent 2-Bit KV Cache Quantization for Video World Models）这一支的出发点正是对象 D：世界模型与长会话生成的瓶颈逐渐从「算不动」变成「装不下」。它给出了本章最有价值的一条反直觉发现：

Key 量化比 Value 量化「更准」，但破坏更大。QuantWM 发现 Key 量化的重建误差比 Value 更小，却导致更大的输出退化。作者把它追溯到世界模型的注意力机制：Key 的扰动会改变 attention logits，从而移动 Query 所「选中」的 temporal-spatial token。因此量化目标必须明确改为保护 attention logits 与时空 token 的选择，而不是笼统地「降低重建误差」。

两条 training-free 技术：① QSAC（quantization-sensitivity-aware clustering）——联合考虑历史 Query 敏感度与残差范围，为 INT2 挑选对量化友好的 Key 聚类中心；② PSAC（principal-subspace attention compensation）——沿主导 Query 子空间用低秩投影恢复剩余 Key 误差，直接校正 attention logits。
公开结果：在 LingBot-World-v2、HY-World 1.5、Matrix-Game-2、Longcat-Video、Causal-Forcing 上改善画质与时序一致性，KV cache 显存最高压缩 6.20×，额外开销有限（一处表格片段显示约 5% 量级的时延代价）。

同方向的另一条已验证路线是 Quant VideoGen（QVG，arXiv 2602.02958，ICML 2026）：同样 training-free，动机是「AR 视频扩散的 KV cache 随历史增长、常超 30 GB，而受限的 cache 预算直接损害身份/布局/运动的长期一致性」。其两组件是 Semantic Aware Smoothing（利用视频时空冗余产生低幅值、易量化的残差）与 Progressive Residual Quantization（由粗到细多阶段，给出平滑的质量—内存权衡），公开结果是在 LongCat Video、HY WorldPlay、Self Forcing 上建立新的质量—内存 Pareto 前沿，KV cache 内存最高降低 7.0×、端到端时延开销 <4%。

这两项工作合起来定义了这一层的正确目标函数：不是「把 KV 压到几比特」，而是「在给定比特预算下，保住 Query 的选择行为」。它与稀疏淘汰是互补而非替代关系：量化决定「每个位置多贵」，淘汰决定「保留多少位置」，两者相乘才是最终的显存上界。

粒度选择
per-block（例如 128×128）优于 per-tensor 与 per-channel：既压住离群值，又保留 Tensor Core 友好的连续访存。Vidu S2 公开采用的是 per-block W8A8 INT8 GEMM（自研 CUDA kernel），并明确说明理由是 per-tensor / per-channel 对离群值脆弱。
收益归属
权重与激活量化主要改善 linear / MLP 段的耗时与带宽；注意力量化改善 attention 段。拆分 profile 是判断「量化到底有没有提速」的唯一方法。
世界模型特有问题
少步模型对误差更敏感。4 步甚至 1–2 步生成时，每一步承担的信息量远大于 30 步采样，量化误差没有机会被后续步骤平滑掉。因此少步 + 量化必须联合校准，不能先蒸馏再量化。
验收指标
不能只测单帧画质。需要沿时间轴测：逐块漂移曲线、动作响应误差、长会话（≥10 分钟）稳定性。「只省显存不提速」是最常见的失败模式。

8.4三个方向如何叠加：一个可执行的收益次序

STEP 1因果 + 重定位 KV先把历史从「重算」变成「只读」。这一层是结构性的，收益最大且质量无损。
STEP 2预分配 / 分页布局消除热路径拷贝，让延迟与显存平台化。不改变数值结果。
STEP 3低比特注意力Q/K 低比特 + 分块量化权重激活。逐层选择，先 Linear 后 Attention。
STEP 4稀疏 / 线性混合与 STEP 3 正交可叠加。长上下文收益最大，但需要训练侧引入稀疏性。
STEP 5KV 量化 + 淘汰策略换取会话容量与有效上下文。风险最高，必须有长时回归与刷新点。
次序为什么不能颠倒：STEP 1–2 决定了「单块延迟是否随长度增长」，STEP 3–5 决定「单块延迟的绝对值」。如果顺序反了——先量化再改缓存布局——你会看到量化省下的时间被热路径拷贝吃掉，从而得出「量化没用」的错误结论。这也是把注意力/缓存优化排在分布式稀疏并行之后、且必须在第 5 章 RoPE 之后的原因：先让状态可复用，再让复用更便宜。
09C 段 · 推理

服务化：把「模型很快」变成「会话很稳」

前六章都在优化一个 worker 跑一块的速度。真实产品要面对的是几百个形态各异的长会话：有的持续活跃、有的长时间空闲、有的突然爆发动作。服务层决定的是这些波动会不会变成用户看到的卡顿与账单。

一句话区分三层职责：模型决定「能不能增量算」、Runtime 决定「一块算多快」、服务系统决定「哪组会话何时在哪张卡上算」。三层缺一层都会被 Amdahl 定律吞掉收益。本章以 TurboServe 与 Vidu S2 的公开推理栈为主线，给出可迁移的系统设计。

7.1先把指标口径统一：四个指标不能互相替代

TTFC

首块延迟

从请求进入到第一个可播放块。必须包含文本/图像预处理、条件编码、首块 DiT、VAE 解码、设备同步与传输。论文里常见的「首帧延迟」若声明排除 VAE，就不能当作 TTFC 用。

TPC

块间延迟

Time per chunk，实时体验的硬约束。必须报告 P50 / P95 / P99 / max：平均值好看但抖动大，用户看到的仍是卡顿。

FPS

生产速率

生成速度必须持续高于播放消耗速度。这里要区分三个 fps：native latent fps、解码帧率、插帧后显示帧率——把三者混为一谈是最常见的口径造假。

$/min

会话成本

长会话下 GPU 常驻、空闲占用与过度预留比单次吞吐更决定成本。这一项才是服务系统真正优化的目标函数。

7.2TurboServe：把 serving 建模成在线调度问题

TurboServe（arXiv 2606.19271，上海交大 + 生数 + 清华）的定位可以精确概括为：它不加速 DiT，它解决长会话在集群里的放置与供给。论文给出的两个公开数字——最坏情况 per-chunk 延迟降低 37.5%、GPU 运营总成本平均降低 37.2%——都是服务系统级指标，不是模型推理延迟指标，引用时不可与模型加速倍数相加。

与 LLM serving 的三点本质差异

差异 1

有状态长会话

会话保存 prompt 上下文与缓存时序状态（通常是 KV cache 及相关元数据），并在 active / idle 间反复切换。而 LLM serving 的典型假设是「响应完成即释放状态」。

差异 2

每个 chunk 有硬时延目标

优化目标不是「请求完成时间」而是每一块的 deadline。一个会话可能持续数十分钟，期间每一块都不能超时。

差异 3

两种异构性同时存在

会话时长异构（短 clip 到数十分钟的迭代 prompt / refine；长期会话让放置决策逐渐失效）+ 用户需求时间异构（30 分钟窗口内活跃会话数剧烈起落）。静态供给要么为峰值过量、要么在突发时欠配。

三项运行时机制，以及一个值得注意的设计选择

coalesced chunk processing

合批而非独立执行

收集「下一个 chunk 已就绪」的会话 → 把同一 GPU 上的就绪会话打成 coalesced chunk batch → 只调用一次模型完成整批 → 把生成的 chunk 与更新后的状态写回各自会话。既摊薄模型执行、提高利用率，又必须限制每 GPU 共置会话数以守住 per-chunk 目标。

状态卸载

空闲会话 GPU–CPU 迁移

空闲会话把持久状态从 GPU 拷到 host 内存并释放 GPU slot，恢复时再装回选定 GPU。

论文明确不做「重计算式状态重建」，理由是：视频生成是计算密集型负载，而 LLM serving 常受限于内存带宽——重算在视频侧的代价远高于搬运。这是一个很好的「负载特征决定系统设计」的例子。

在线迁移

基于 NCCL 的 GPU–GPU 状态迁移

支撑在线再平衡的快速负载转移。这是「会话放置」能真正闭环的前提。

7.4并行策略：什么时候才值得上多卡

流式场景的并行决策与离线推理目标函数不同：离线看吞吐（tokens/s/GPU），在线看单块延迟与尾延迟。这导致一个反直觉的结论：

小模型 + 小 chunk

通信可能大于计算

1.3B 级模型、4 帧 chunk 的情况下，单块计算量很小，all-to-all 与同步开销会主导关键路径。此时多卡是负收益。判断方法：对比 1/2/4/8 卡的延迟曲线而非吞吐曲线。

大模型 / 高分辨率

上下文并行才成立

8B 以上、720p 以上使单卡放不下或跑不动时，Ulysses 风格上下文并行（序列维切分）比张量并行更适合视频 DiT：它切的是 token 维，通信量与序列长度相关而与权重无关。

  • 切分维度选择：视频 DiT 的核心成本随 token 数增长，因此上下文/序列并行（CP/SP）通常是第一选择；张量并行用于权重大到单卡放不下的情形；流水并行对延迟不利（增加气泡），在线场景慎用。
  • 通信量化：跨卡传输可以量化（Vidu S2 即采用量化跨 GPU 张量传输），这是把 CP 从「能跑」推到「值得跑」的常见手段。
  • 动态启用：按 token 数自适应决定并行度——小 chunk 单卡、大 chunk 多卡。固定并行度会在负载变化时系统性偏低或偏高。

7.5流水与共享时间线：把不能消除的延迟藏起来

少步化之后，VAE 解码在端到端中的占比会显著上升——因为去噪被压缩了，而解码没有被压缩。这正是 Vidu S2 采用共享时间线调度的动机：让 VAE 编码器、主干、Refiner、VAE 解码器在同一时间线上动态共享 GPU，某个模块空闲时另一个立即复用。

8.3三块真正的硬骨头

硬骨头 1

滑窗 KV 的运行时管理

不是算子问题，而是运行时机制问题：缓存的分配与回收、窗口滑动、位置基准更新、淘汰与刷新点、会话级隔离与序列化。
它必须与推理引擎的显存管理、图编译策略、调度器深度结合。现有框架里没有对应抽象——DiTCache / AttentionCache 解决的是跨步冗余，不是跨块状态。

硬骨头 2

RoPE 重定位的算子接口

需要「位置源外置」：缓存存未旋转 K，注意力读时再施加旋转。这会同时冲击融合算子接口、图编译（位置源从常量变张量）与缓存布局。
若无法改动算子，退路是接受固定的绝对位置（把「重定位」降级为「训练期覆盖足够长的位置范围」），代价是会话时长有上限。

硬骨头 3

少步 + 量化的联合校准

4 步模型每步承载的信息量远大于 30 步，量化误差没有机会被后续步骤平滑。同时 KV 量化误差会沿会话时长累积。
因此不能照搬多步模型的量化经验（例如「per-tensor 够用」「KV 量化 8-bit 无损」）。必须针对少步配置重新做逐层敏感度扫描与长时域回归。

8.4四级推进路线（每级都有可验收的产物）

LEVEL 1单算子对齐把 FA（含块因果 mask）、RoPE 融合、RMSNorm 融合、量化 GEMM 逐个与参考实现做数值对齐。
产物：逐算子精度报告 + 性能火焰图。
LEVEL 2单模块闭环跑通一个因果 DiT block 的前向，含 KV 的读写与位置施加。
产物：单块延迟与显存基线（BF16、batch=1、固定 chunk）。
LEVEL 3单段流式接通「预填充 → 少步去噪 → 提交状态 → 异步 VAE」的完整循环，验证滑窗与淘汰策略。
产物：100+ 块无漂移；延迟与显存不随块数上升。
LEVEL 4长流 + 服务接入会话管理、合批、状态迁移与弹性供给；跑 1/10/100/1000 块与多会话混合负载。
产物：TTFC / TPC P99 / 每生成分钟成本三项达标。
每一级都要建立与论文同口径的基线。尤其注意：公开论文的延迟数字常常排除 VAE（minWM 的首帧 1.137 s / 3.446 s 明确不含 VAE）。如果第 3 级只对比 DiT 段，就会在接入真实产品链路时发现端到端差出一大截，而这与算子移植质量无关。

9.2数字口径的七条纪律

本报告在对比数字时严格遵守以下规则。任何引用本报告数字的人也应同时引用这七条：

  1. 「实时」必须写明分辨率与帧率。540p/42FPS 与 720p/25FPS 不是同一个「实时」。
  2. 区分三种 fps。native latent 生成频率 / 解码帧率 / 插帧后显示帧率。LingBot-World v2 的 Spatio-temporal Refiner 明确包含时间插帧，因此展示输出的 60fps 不等价于 DiT 原生生成 60 个独立物理状态/秒。
  3. 查清是否包含 VAE。minWM 的首帧 1.137 s / 3.446 s 明确排除 VAE；一旦补上 VAE，端到端首帧会显著变化。
  4. 查清是否包含排队与传输。论文的「首帧延迟」通常不含排队、编码与网络。
  5. 模型加速 ≠ 算子加速 ≠ 系统加速。TurboDiffusion 的 100–200×（单张 RTX 5090，双向 T2V/I2V）、TurboServe 的 37.5% / 37.2%（64×B300，生产 trace）、Vidu 的 25–42 FPS（产品口径）三者不可相加或互换。
  6. 注意任务类型。TurboDiffusion 论文明确把自回归视频扩散列为未来工作——它的 100–200× 是在双向离线 T2V/I2V 上测的，不能外推到流式世界模型。同理 SparkDiffusion 的 265× 也是双向离线口径。
  7. 分布级指标不能替代单样本指标，反之亦然。模式崩溃只在多 seed 的分布离散度上可见；逐块漂移只在长时域上可见。任何单一指标都不足以验收少步蒸馏。

A.2三处必须纠正的常见说法

纠正 1

Causal Forcing ≠ arXiv 2605.15141

这是两篇不同的论文：Causal Forcing = 2602.02214（ICML 2026，提出 frame-level injectivity 与 AR teacher 初始化）；2605.15141 = Causal Forcing++（frame-wise 1–2 步、causal consistency distillation）。把两者混为一谈会同时错掉机制与数字。

纠正 2

rCM 不是「rectified Consistency Model」

rCM = score-regularized continuous-time consistency model。这个区别不是文字游戏：它的核心机制正是把 score distillation 作为 long-skip regularizer 融入 sCM，从而同时拿到质量（反向散度）与多样性（前向散度）。理解错误就无法解释它为什么优于 DMD2。

纠正 3

Memory Forcing 已被作者撤稿
