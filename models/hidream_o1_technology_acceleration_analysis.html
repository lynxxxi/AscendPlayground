HiDream-O1-Image · pixel-level unified transformer

像素，即推理现场

HiDream-O1 的关键不是再做一套“更大的 latent DiT”，而是用一个从 Qwen3-VL 初始化的 8B 统一骨干，把文本、条件图与待生成像素放进同一 token 空间。代价也很直接：VAE 消失了，2048² 下的 4096 个图像 token 却要在每个去噪步参与全注意力。

01 / EXECUTIVE READOUT

先给决策结论

01

创新点在“统一”

文本理解、条件图理解和像素生成共享 Transformer，而不是“LLM / 文本编码器 → latent DiT → VAE”三段拼接。它天然适合把复杂指令、编辑与生成收敛到同一套上下文建模。

02

瓶颈转移到长序列

32×32 像素一个 patch。2048² 形成 4096 个生成 token，外加文本、时间步与参考图 token。核心压力从 VAE 与多组件调度，转移到每层 attention、MLP、激活显存和 28/50 次循环。

03

Dev 是部署首选

按公开默认配置估算，Full 为 50×2≈100 次骨干调用，Dev 为 28×1≈28 次；骨干调用数减少约 72%。这是结构性收益，但不是官方实测的 3.57×端到端加速。

昇腾适配的主矛盾：不是移植 VAE，而是把“AR 前缀因果注意力 + 生成区全注意力”的 Hybrid Unified Attention 做成高效 NPU 路径，并让 4096+ token 下的序列并行、算子融合与静态 shape 桶真正工作。
02 / WHAT “O1” ACTUALLY MEANS

三种“推理”，不要混成一种

推理时 · 可选

Reasoning-Driven Prompt Agent

官方脚本可调用 Gemma-4-31B-it 或 OpenAI-compatible API，将原始需求重写为布局、属性、物理关系、文字渲染更明确的英文提示。默认最多生成 4096 token；若本地部署，它可能比 8B 图像骨干更占显存、也更影响首帧延迟。

模型内 · 核心

统一上下文推理

文本 token、参考图 condition token、噪声像素 patch token 共处同一序列。生成 token 可以全局读取所有上下文，因此编辑、主体保持、布局控制与 T2I 不必由不同网络拼装。

训练期 · 非在线

GRPO / RLHF 后训练

论文使用 OCR、美学、指令遵循与 reasoning quality 等复合奖励做 GRPO。奖励模型位于后训练环节，并非每个去噪步都在线打分。把它算入推理链路，会严重高估部署成本。

实现细节提示：公开 prompt agent 代码对本地模型设置 enable_thinking=False。因此“Reasoning-Driven”更准确地理解为经过推理数据/流程训练的结构化提示重写器，而不是必须暴露长思维链的在线 agent。

04 / PIXEL ECONOMICS

分辨率每翻倍，全注意力账单约放大 16 倍

固定 32 像素 patch 时，边长翻倍会让 token 数变为 4 倍；全注意力的 QK 交互规模近似按 token² 增长，因此理论 attention-pair 量约变为 16 倍。下面只计算生成图 token，不含文本、时间步和条件图。

512 × 512256tokens · QK 相对量 1×
1024 × 10241,024tokens · QK 相对量 16×
2048 × 20484,096tokens · QK 相对量 256×
“去掉 VAE”消除了编解码延迟与 latent 信息瓶颈，但并没有让计算消失——它把高分辨率建模的成本搬进了每一个 Transformer 层、每一个采样步。

Full · 质量基线

默认配置

50 steps × 2 CFG branches ≈ 100 次 8B 骨干 forward。

guidance_scale 5，条件/无条件分别前向；FlowUniPC 调度器。

Dev · 蒸馏部署版

优先落地

28 steps × 1 branch ≈ 28 次 8B 骨干 forward。

guidance_scale 0；采用 DMD + diffusion + adversarial 目标蒸馏。调用数较 Full 少约 72%。

上述为根据官方默认代码路径得到的“网络调用量”估算。实际端到端加速比还受 prompt agent、分词、视觉条件编码、调度器、数据搬运和算子利用率影响，不能直接等同于 3.57×实测性能。

05 / MODEL GENERATION SHIFT

相对主流 latent 模型，取舍发生在哪里

维度HiDream-O1 8B主流 latent DiT（Qwen-Image / FLUX / SD3 类）对加速的含义
图像表征原始像素 patch，32×32；无 VAE先压缩为 latent，再由 VAE 解码O1 少一段编解码，但生成序列通常更长，attention 压力更集中。
文本理解统一骨干的原生词表与 embedding；无割裂文本 encoder常见 CLIP / T5 / LLM encoder 与 DiT 分离少组件、少跨模型边界；但 8B 主干在每个采样步都承担语义与像素计算。
多任务T2I、编辑、主体、布局、故事板共用 in-context 接口常依赖 ControlNet、IP-Adapter 或不同 pipeline部署面更统一，shape/token 类型更多；需按任务建立编译桶与缓存策略。
注意力AR 前缀 causal + 生成区 full 的混合统一注意力DiT self-attn + 文本 cross-attn 或 MM-DiT joint attention不能直接套标准 causal LLM 或纯 DiT kernel；混合掩码是适配重点。
采样Full 50 步 CFG；Dev 28 步 CFG-free依模型而异，常见 CFG、蒸馏或 guidance-free 版本步数和 CFG 分支仍是第一阶性能变量，优先级高于微小 Python 优化。
“推理增强”可外挂 31B prompt agent；训练期 GRPO通常直接用 prompt enhancer 或 LLM 改写需把 agent 首 token/生成时延单独记账；合理拓扑是异步独立服务。

论文表格给出的模型规模口径并不完全一致，部分竞品还包含独立文本模型；因此本报告不使用“8B 一定比 X 更省显存”的简单结论。公开仓库也未给出统一硬件上的 O1 延迟/显存对照表。

06 / ACCELERATION REQUIREMENTS

从精确收益开始，再碰近似加速

P0

Dev + CFG-free：先减少完整骨干调用

部署默认走 28-step Dev，将约 100 次前向压到 28 次。保留 Full 作为高质量/回归基线，并建立 OCR、小字、主体一致性和编辑保真质量闸门。

P0

专用 Hybrid Attention

当前“双 attention 再覆盖”路径会为 full pass 计算最终会被丢弃的 AR query 输出。理想 kernel/图改写应复用 QKV，只为 AR query 做 causal、只为生成 query 做 full，同时保持数值等价；FlashAttention/FlashAttention-like NPU 实现是核心。

P0

长序列 GEMM 与融合算子

围绕 4096 hidden、36 层、GQA 32Q/8KV，打通 BF16 matmul、RMSNorm、RoPE、SwiGLU、残差融合与 patch projection。2048 档关注激活和带宽，不能只看参数是否装得下。

P0

分辨率 / 长宽比 shape 桶

为官方支持的高频尺寸预编译执行图，固定 patch 数与 position id 生成路径；避免每次请求触发重编译。把 1024 作为吞吐主档，2048 作为高质量档单独限流。

P1

精确缓存：先用已有，再探索前缀 KV

公开 pipeline 已在去噪首步后缓存参考图 embedding 与 deep-stack 特征。进一步可研究 AR 前缀逐层 KV 缓存：因文本/条件前缀为 causal、不能看到后续变化的生成 token，理论上存在精确拆分机会；但当前仓库未实现，需重构层级接口并验证 timestep/token 边界。

P1

USP / Ulysses 序列并行

多 NPU 时沿 token 维切分 4096+ 序列，比盲目张量并行更贴近高分辨率瓶颈。单卡能放下时不应默认 TP：36 层 8B 的通信可能抵消收益；应以 2048 峰值内存和批吞吐决定 SP/TP 组合。

P1

Prompt Agent 解耦

31B agent 独立池化部署、异步调用、按规范化 prompt + 任务类型缓存改写结果。图像引擎只接收精炼文本；关闭 agent 时，系统才接近“单 8B 模型”的资源口径。

P2

量化与跨步缓存

FP8/W8A8、step feature cache、稀疏/局部 attention 可能继续提速，但会触碰像素细节、文字拼写与编辑一致性。最后输出头、patch embed、norm 和 attention softmax 建议保留更高精度，逐层做敏感度扫描。

推荐单机拓扑

性能观测必须拆开

T_total = T_agent + T_prefill + N_step × T_backbone + T_scheduler + T_output

同时记录 attention、MLP、通信、编译与 H2D 占比；Full 另拆 cond/uncond。只看整段耗时无法判断应优化 agent、步数还是内核。

08 / IMPLEMENTATION ROADMAP

一条可验收的适配路线

PHASE 0 · BASELINE

跑通 BF16

对齐 tokenizer、position id、patchify、调度器；固定 seed 与 PyTorch 参考逐层比对。先覆盖 512/1024 T2I。

PHASE 1 · EXACT SPEED

消除精确冗余

Dev 单分支、融合 norm/RoPE/SwiGLU、Hybrid Attention 快路径、条件视觉缓存；扩展 2048 和编辑。

PHASE 2 · SCALE OUT

序列并行

USP/Ulysses + 必要 TP；建立长宽比 shape 桶、批调度、通信重叠。输出单卡与多卡 break-even。

PHASE 3 · APPROX

低精度 / 跨步缓存

分层量化与缓存消融；用 OCR、数量、空间关系、主体一致性、编辑保真和人工偏好共同验收。
