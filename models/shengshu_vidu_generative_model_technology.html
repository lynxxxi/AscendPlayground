03 / 技术谱系

从 U-ViT 到 Vidu：一条没有换过底座的路线

生数的论文线是连续可查的：Analytic-DPM（2022-01）→ U-ViT（2022-09）→ UniDiffuser（2023-03）→ Vidu 1.0（2024-04）→ TurboDiffusion / SageAttention / SLA → Vidu S1（2026-07）→ Vidu S2（2026-09）。下面只讲对理解 Vidu 当前形态有用的三块基石。

3.1 U-ViT：把「所有输入都是 token」这件事做彻底

与 DiT 的实质差异

U-ViT 的两个设计选择构成了它的身份：其一，把时间步 token、条件 token、图像 patch 一律按 token 处理，不做特殊分支；其二，在浅层与深层之间使用长跳连接（long skip connection）。论文的消融结论是：长跳连接是关键，而 U-Net 式的下采样/上采样算子并非必需。

这解释了为什么后来 Vidu 能自然地把「参考图」也当作一路条件 token 塞进同一个主干——因为从 U-ViT 开始，主干就没有为任何单一模态设过专用通道。

可核查成绩

潜空间扩散设定下，ImageNet 256×256 类条件生成 FID 2.29；MS-COCO 文生图 FID 5.48。论文强调这两个数字是在不使用大型外部数据集的条件下取得的当时最优。

arXiv:2209.12152 · All are Worth Words: A ViT Backbone for Diffusion Models（CVPR 2023）论文

3.2 UniDiffuser：统一建模的理论来源

UniDiffuser 解决的是「一个模型如何同时表达边缘分布、条件分布与联合分布」。做法是把所有模态都加噪，并且给不同模态分别输入各自的时间步，让网络预测所有模态的噪声。训练完成后，只要设置合适的时间步组合，同一个模型就能做图像生成、文本生成、文生图、图生文和图文对生成。

这条思路直接对应生数后来对外的三条表述：「统一问题形式、统一架构、压缩即智能」，以及「不再需要 LoRA 微调」的产品主张。

三段式演进的工程含义

2024 · 对标期

解决的是「能不能做出来」。技术重点是长视频表示与时空一致性。Vidu 1.0 技术报告（arXiv:2405.04233）以定性对比为主，把 Sora 公开示例的 prompt 直接喂给 Vidu 做并排展示，没有给出任何量化评测。

这意味着评估 2024 年那批宣称时，缺少可对比的数字基线。

2025 · 可控期

解决的是「能不能商用」。两条线并行：能力侧转向多主体一致性（参考生视频），成本侧把单价从行业均价约 0.6 元/秒压到 0.258 元/秒量级，并推出错峰模式。

价格是可公开验证的成本侧证据：单价的持续下探说明推理成本在真实下降。

2026 · 实时期

解决的是「能不能交互」。S 系列把范式从「离线一次性去噪」改成「分块自回归流式生成」，并为此重做了数据、训练算法、推理栈与服务调度四层。

这是本报告技术密度最高的部分，见第 06–08 节。

迁移视角的关键判断：L1 与 L2 是模型结构，相对容易等价实现；L3 到 L5 才是真正的工程量与性能战场——它们由 Sliding Window KV Cache、RoPE 重定位、双缓存调度、INT8 分块量化、多 GPU 通信与在线调度共同构成，且每一项都与具体硬件后端强耦合。
06 / 流式交互

Vidu S 系列：把去噪过程变成一场接力

离线扩散模型一次性对整个视频去噪，用户只能等。流式生成则要求「生成速度跑赢播放速度」，逐段产出、边产边播。难点不在单段质量，而在误差跨段累积——前一段的小偏差会被当成后一段的历史条件，最终表现为身份漂移、动作断裂或背景突变。

6.1 三步走：从双向模型到流式模型

第一步 · 双向预训练 先在 I2V（首帧作参考）与 R2V（参考图作条件）两个任务上联合训练一个双向模型。关键设计是逐段条件监督——每个时间片段配自己的条件描述，而不是整条序列共用一个 prompt，这显著改善了指令遵循。
第二步 · 因果适配（Hybrid Teacher + Diffusion Forcing） 把双向时序注意力替换为块级因果注意力掩码，每段只能看到参考图、本段条件与有效历史状态。历史状态以一定概率注入噪声（Diffusion Forcing），让模型学会在「历史本身也不干净」的条件下继续生成。
第三步 · Self-Replay Forcing（S2 的核心贡献） 先让学生模型按真实推理方式自回归 rollout 一长段（梯度与 KV 缓存全部 detach），再对这条自生成轨迹按块重新加噪，然后做一次开启梯度的因果重放。由于重放段在同一计算图内相连，后段的损失可以回传到前段表示，但不必为整条长轨迹保留计算图。

这条路线并非 Vidu 独创的起点：Self-Forcing 已经建立了「用模型自己生成的历史做条件」的正确设定。S2 指出的两个遗留问题是——自生成历史被干净地喂入（而非加噪），且被从计算图中 detach（没有梯度流过）。SRF 正是针对这两点的修补。

6.2 双缓存与滑窗：让延迟不随视频变长而上升

TwinCache：阶段感知的双缓存

每个历史状态同时维护一份 noisy cache（取自预设的中间去噪步）与一份 clean cache（最终去噪步的输出）。中间步用 noisy cache——论文指出残留噪声构成了一种「隐式低通先验」，有利于粗粒度时序传播、抑制高频伪影累积；最后一步切换到 clean cache 以恢复细节与身份一致性。

RoPE Repositioning：缓存未施加位置编码的 KV

KV 特征在应用 RoPE 之前被缓存；窗口滑动时，按更新后的相对位置重新施加位置编码。这样既避免重算历史特征，又能保证可见位置始终落在训练时见过的位置范围内。

非对称噪声缓存（S2 新增）

主干关注高噪声缓存以传播粗运动与长程时序结构（τB 较大，对高频伪影不敏感）；Refiner 关注低噪声高分辨率缓存以保留局部外观与身份线索（τR 较小，且 τB > τR）。两者分工明确：时序传播与细节恢复被解耦。

Backbone–Refiner 两阶段 + 异步流水线

主干在低分辨率下生成主体结构、运动与语义，轻量单步 Refiner 在潜空间完成超分。官方与媒体口径一致的关键点是：两者不等彼此——细节重建与后续内容生成并行推进，使 720p 输出下不掉帧。

07 / 参考生视频

参考生视频：生数最像「护城河」的一块

「参考生视频」（Reference-to-Video, R2V）指用户给出参考图（乃至视频），模型据此生成保持该主体外观一致性的视频。生数自称全球首创该技术，并在多轮融资稿中把它作为解决「商业场景多主体连续一致性」痛点的核心卖点。

7.1 参考图到底是怎么注入的

这是一个容易被传播话术覆盖的技术问题。论文给出的答案比常见说法更朴素：

x̂01:N = fθbi( xt1:N, t, r, c1:N )
  • 参考图 r 是与噪声隐变量、时间步、逐段文本条件并列的输入，进入同一个 DiT，没有独立的参考编码器分支。原文：「The reference image is shared across all segments to maintain appearance and identity.」
  • 这在机制上属于序列拼接式的 in-context 条件注入，与 UniDiffuser「所有模态都加噪、各自输入时间步」的思路同源；既不是经文本编码器做语义改写，也不是加性位置编码偏置。
  • 在转为流式后，块级因果掩码对历史严格，但参考图是例外：「each video-audio segment can only attend to the reference image, the current segment condition, and its valid historical states.」参考图对全部段落无条件开放。
  • Vidu S1 进一步把参考上下文类比为 LLM 中的 sink token，全程固定不变，并与 clean cache 一起参与细节与身份一致性的恢复。

来源：Vidu S2 · Vidu S1 论文

7.2 「上下文记忆涌现」：传播概念与技术实体之间的落差

2024 年 11 月 Vidu 1.5 发布时，官方与媒体口径是「视频模型拥有记忆了」「视觉模型迎来智能涌现」「不再需要 LoRA」。官方给出的解释是三条与 LLM 对齐的设计哲学：统一问题形式（视觉输入→视觉输出）、统一架构（单个网络建模变长输入输出）、压缩即智能。

  1. Vidu 1.5 没有 arXiv 技术报告。上述主张缺少可复现的量化定义——没有一致性指标、没有参考图数量上限、没有消融实验。

08 / 推理与工程

加速不是一招，是四招叠加

生数的加速能力最集中地体现在 2025-12 开源的 TurboDiffusion 框架上。它的价值不仅是倍数，而是把「低比特注意力 + 稀疏注意力 + 步数蒸馏 + 线性层量化」四件正交的事组合进一个模型。

8.3 服务层：TurboServe

实时交互产品的成本结构里，服务调度与模型推理同样重要。TurboServe 被官方描述为首个专为流式视频生成设计的服务系统，把 serving 建模为在线调度问题，联合优化两件事：会话放置（跨 GPU 重平衡会话以压低最大 per-chunk 延迟）与 GPU 供给（负载驱动的自动扩缩容）。运行时依赖三件事：同 GPU 并发会话的合并处理（coalesced chunk processing）、空闲会话的 GPU–CPU offload 与恢复、基于 NCCL 的 GPU–GPU 状态迁移。

8.4 训练与后训练

数据侧

生数披露的是方法论而非规模：视频条数与小时数在三篇论文中均未公开。可核查的是清洗算子与过滤分类法——S1 的六维过滤（主体检测、画面干净度、视觉质量、内容安全、镜头稳定性、交互性），S2 新增误拒率低于 2% 的 VLM 二级切点复核、基于实测清晰度而非标称分辨率的筛选（High-Clarity Selection）、以及背景稳定化算子。

标注侧

S1 使用结构化描述（主体、环境、运镜分字段）；S2 改为时间有序的稠密描述——按事件时序标注时间边界、构成动作与结果（例如「2.5s–3.8s 之间发生的动作及其后果」），并把分段依据从固定时长改为事件边界。标注管线采用分层多智能体：专家模型做检测与语音识别形成事实锚定层，再分派识别、描述、校验、过滤给专门 agent。

对齐侧

没有使用经典 RLHF/PPO 表述，而是分阶段：双向阶段用 diffusion-based DPO 提升视觉保真、面部表现力、运动自然度与音画同步，论文明确指出其作用是「为后续因果适配提供更强的教师」；流式阶段用 Streaming NFT（Negative-aware Fine-Tuning）作用于因果主干，动机是让优化状态与推理时的自回归分布对齐。

10.2 官方承认的能力边界

  • Vidu 1.0 报告（2024-05）：「细节偶发瑕疵，视频中不同主体之间的交互有时违反物理规律」，并把解决方案押注于 scaling。
  • Vidu S1 报告（2026-07）：行业层面承认长时程视频生成的误差累积会导致漂移、不稳定乃至视觉崩塌；自身在训练层面承认纯 DMD 目标「频繁出现模式崩溃，表现为镜头漂移、内容退化与时序不一致」，因此引入 PCM 感知特征距离作为正则。
  • S2 团队口径：头显对分辨率与延迟要求极苛刻，画面模糊会晕、延迟高会导致转头与画面「打架」，仍在持续优化；未来计划从固定视角扩展到全景空间视频。

来源：Vidu 技术报告 · Vidu S1 · 量子位

10.3 三处「能指与所指的落差」

「上下文记忆涌现」

传播概念：视频模型拥有记忆、迎来智能涌现、不再需要 LoRA。

技术实体：persistent reference context / sink block / 滑动窗口上下文。

落差位置：该主张出自无技术报告的 Vidu 1.5，缺少量化定义与消融；术语在 S1/S2 论文中不出现。

「空间视频」

传播概念：常被读者理解为可漫游的 3D 世界模型。

技术实体：深度估计 + 双目立体转换（view warping、空洞填补、时序稳定），把单目流转为同步左右眼视图。

落差位置：论文自己把全景与自由转向视角列为未来工作。准确的表述是 spatial video，不是 world model。

「万物可参考」的一致性问题

传播概念：任意主体、任意参考都能稳定复刻。

技术实体：参考图作为条件 token 参与注意力 + 因果掩码中的全局可见例外 + 主体数量硬约束。

落差位置：API 明确限制主体数量（合计不超过 7 个、每主体最多 3 张图、视频主体仅一个模型支持且限 1 段 5 秒）；一致性机制本身从 1.5 到 Q2 未见公开的替换或改进证据。

分层结论：Wan2.1/2.2 与 HunyuanVideo 属于「被昇腾框架主动适配」的对象（进支持矩阵、享受全套算子与并行优化）；Vidu 属于「在昇腾云上被商业上架」的第三方模型（进 MaaS 商品目录、进客户案例，但没进框架适配矩阵）。这两件事的价值与含义完全不同，混为一谈是本主题下最容易出现的误判。

来源：MindIE SD 官方支持矩阵 · 华为云 ModelArts NPU 推理指导 · Ascend ModelZoo U-ViT README

绑定程度有多深：来自代码与论文原文的直接证据

  • TurboServe 开源仓库的安装说明要求先装 CUDA 版 PyTorch，安装命令走 download.pytorch.org/whl/cu128；运行要求「requires eight visible NVIDIA GPUs」；配置文件名直接包含 nccl（configs/runtime_8gpu_process_nccl.yaml）。

11.6 对昇腾侧工作的四条建议

  1. 先向华为云侧求证训练口径的颗粒度。官方案例页已确认「昇腾云服务支持了模型训练」，但没有任何比例、机型或作业规模信息。这是目前性价比最高的一步：确认训练算力中昇腾的实际占比，比任何技术推演都更有价值。
  2. 把 SageAttention 的昇腾实现当作算子级抓手。它同时满足三个条件：有官方背书的昇腾落地记录、是 Vidu 推理栈的底层组件、且开源可查（Apache-2.0）。先跑通并对齐精度，风险最低。
  3. 以 U-ViT 的 ModelZoo 适配作为骨架迁移的起点。既然昇腾侧已经有过一次 U-ViT（图像版）的迁移与训练实测，把这条路径复现一遍可以系统性暴露 CANN 版本的算子缺口——注意它是「在研版本」且只支持训练，需要自行补齐推理链路。
  4. 真正的硬骨头是流式推理的三个运行时机制：滑窗 KV Cache 管理、RoPE 重定位、双缓存调度。它们不是算子而是运行时机制，需要与推理引擎的显存管理和调度深度结合。建议按「单算子 → 单模块 → 单段流式 → 长流」四级推进，每级都建立与论文同口径的精度与延迟基线，避免到最后才发现误差累积特性与 CUDA 侧不一致。
一句话总结本节：华为云与生数的合作是官方确凿的，且明确覆盖到「支持模型训练」；但这条关系目前停留在云服务与商业上架层面——Vidu 本体没有进入昇腾的框架级适配矩阵（MindIE SD），也没有任何昇腾侧的性能数据公开。把「客户案例」读成「深度技术共建」，或把「MaaS 上架」读成「模型跑在昇腾 NPU 上」，都是越过证据的推论。
