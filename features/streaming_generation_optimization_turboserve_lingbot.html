从“单个 chunk 算得更快”到“长会话在多 GPU 上稳定、经济地持续生成”：拆解模型、执行引擎与服务系统三层优化，并给出 LingBot-World / LingBot-Video 的可执行适配判断。

一句话结论

LingBot-World v2 已具备因果生成、KV cache 与按块推理，是接入 TurboServe 思路的最佳起点；先把模型执行封装成可暂停、可迁移的有状态 worker，再引入合批、迁移与弹性扩缩容。LingBot-Video 更适合先做离线/在线请求级加速，不宜直接宣称已支持长会话流式服务。

3 层模型效率 × Runtime × Serving；缺一层都可能被 Amdahl 瓶颈吞掉。
01 / READOUT

先统一“流式”的口径

本文讨论的是视频或世界模型持续输出 frame chunk 的长会话服务。它不同于 LLM 的逐 token 输出，也不同于“离线生成完成后再分片播放”。真正的系统目标是：每个 chunk 都按时、状态不断、多人并发时成本可控。

TTFC首块延迟从请求进入到第一个可播放 chunk；受预处理、条件编码和预热影响。
TPC块间延迟Time per chunk；实时体验的硬约束，需同时看 P50 / P95 / max。
FPS生产速率生成速度必须持续高于播放消耗速度，平均快但抖动大仍会卡顿。
$/min会话成本长会话下 GPU 常驻、空闲状态和过度预留比单次吞吐更重要。
判断原则：“模型快”解决单 worker 的服务时间；“Runtime 快”解决 kernel、并行与内存；TurboServe 解决长会话在集群里的放置、合批、迁移和供给。37.5% / 37.2% 是 TurboServe 在其生产 trace 与基线设定下的系统级结果，不能外推成 LingBot 的即得收益。
02 / ARCHITECTURE

先看模型：为什么普通视频模型不能直接“边算边播”

流式能力首先来自模型的信息流，而不是播放器切片。普通视频 DiT 通常对固定时长 latent 做双向去噪；前沿流式模型改成因果 chunk、可复用状态和少步学生，使“下一块只计算新增内容”成为可能。TurboServe 接管的是这个模型接口之上的多会话调度。

OFFLINE VIDEO MODEL

一次请求生成完整 clip

  • 整段视频 token 在每个去噪步内双向注意，未来帧也参与当前帧建模。
  • 通常需要 20–50 次 DiT 前向，并用 CFG 提高提示遵循。
  • 上下文是本次请求的临时张量，生成完成即释放；延长视频往往重叠窗口重算。
  • VAE 在全部 latent 完成后统一解码，首帧必须等待整段采样。
CAUSAL STREAMING MODEL

长会话反复生成 frame chunk

  • frame chunk 只看历史与当前允许区域，未来块不可见。
  • 少步蒸馏把每块去噪压到约 1–4 次前向，才有机会让 TPC 低于播放时长。
  • 每层 KV Cache、latent 历史和位置编码跨块保留。
  • DiT(n+1) 与 VAE/编码(n) 异步重叠，先产出的帧可立即传输。
01 / PREFILL条件与首块文本、图像、动作编码一次；建立 causal mask 与初始 KV。
02 / FEW-STEP DIT生成 latent chunk只对新 token 去噪；历史 K/V 只读不重算。
03 / COMMIT提交会话状态追加 KV、latent、RoPE 位置、scheduler 与 RNG。
04 / ASYNC MEDIA解码 / 增强 / 编码独立 stream 或 worker 处理当前块。
05 / CONTROL接收动作 / prompt控制信号在下个 chunk 边界进入，避免未来信息泄漏。
06 / REPEAT按 deadline 循环活跃时合批；空闲时暂停并卸载状态。

会话状态不是一个 KV 张量

ATTENTION

层级 KV

每层历史 key/value、mask、RoPE 位置；通常是最大迁移对象。

LATENT

视觉历史

当前/近邻 chunk latent、首帧或长期 memory token；用于连续性与恢复。

SAMPLER

采样器状态

timestep/sigma、seed、RNG、guidance 配置；决定暂停后是否能一致续跑。

MEDIA

媒体与背压

待解码块、帧序、编码缓冲、客户端播放水位；决定是否该继续生产。

边界分工：因果模型定义“能否增量计算”；Runtime 决定“一块算多快”；TurboServe 决定“哪组会话何时在哪张卡上算”。如果模型仍要求看到完整未来 clip，就没有可安全迁移的长会话状态，TurboServe 也无法把它变成真正流式模型。
03 / STACK

优化全景：三层联动

最有效的路线通常从减少模型工作量开始，再压缩单次前向成本，最后让服务层把波动、空闲与长尾消化掉。

MODEL

模型与算法

  • 少步蒸馏 / consistency / trajectory distillation
  • 因果与局部注意力、attention sink、KV cache
  • 稀疏 MoE、低秩与结构化剪枝
  • 特征 / timestep / block 缓存
  • 低分辨率生成 + refiner / VAE 解码

RUNTIME

执行引擎

  • Flash / Sage / fused attention
  • FP8 / INT8 / INT4 与硬件原生 kernel
  • 图编译、算子融合、静态 shape bucket
  • FSDP / TP / CP / EP 与通信重叠
  • 预分配、零拷贝、异步 VAE / 编码
→
SERVING

TurboServe 所在层

  • 同 GPU 活跃会话的 chunk 合批
  • 空闲会话 GPU→CPU 状态卸载
  • NCCL GPU→GPU 在线状态迁移
  • 迁移感知的会话重平衡
  • 负载驱动的 GPU 弹性供给

02 / REPEATDiT 去噪步数 × CFG × token 数，是主要算力项。

05 / TURBOSERVE

TurboServe：它到底加速什么

TurboServe 把服务建模为在线调度问题，联合决定“会话放在哪张 GPU”和“此刻应启用多少 GPU”。它补的是多用户、长会话、负载波动下的系统效率，不取代 DiT 推理引擎。

① Observe

收集每个 session 的 active / idle、deadline、状态大小和 GPU 负载。

② Place

迁移感知控制器降低最拥塞 GPU 的预计 per-chunk latency。

③ Provision

根据活跃负载改变 GPU budget，减少固定满池的闲置成本。

④ Execute

活跃会话 coalesce；空闲状态卸载；必要时通过 NCCL 迁移。

状态可描述

06 / LINGBOT

LingBot 系列：适配度分层

“LingBot”不是单一模型。与流式生成服务直接相关的，是能持续按块产生视频或世界状态的分支；VLA / VA 还要额外满足机器人控制周期和安全约束。

BEST FIT

LingBot-World v2

官方公开 generate.py 以 KV cache 做 causal、chunk-by-chunk 推理；14B causal-fast 支持 480P 多 GPU，项目宣称蒸馏实时版可驱动 720p 60fps。因果长时生成与 TurboServe 的 session 模型最匹配。

缺口：官方明确不计划公开部署代码；需要自行补 serving adapter、状态序列化、合批与迁移。

PARTIAL FIT

LingBot-Video

提供 Dense 1.3B 与 MoE 30B-A3B + Refiner；支持 Diffusers / SGLang backend、FSDP、FP8 MoE 路径，官方称 MoE 推理约快 3×。它当前公开工作流偏 T2I / T2V / TI2V 请求级生成。

建议：先用 Dense 1.3B 打通在线 API 与 profile；若要长会话，需改造成因果 chunk 接口并定义跨块状态。

OTHER SLA

LingBot-VA / VLA

LingBot-VA 已强调自回归 diffusion、异步双流与 KV cache，并支持 server-client；但其核心指标是动作控制周期、成功率与安全，不是纯视频播放 FPS。

建议：可借用 TurboServe 的会话/资源思想，但调度目标必须加入 action deadline 与 stale-observation 约束。

07 / ROADMAP

落地路线：先单会话，再多租户

不要一开始就把模型优化、量化、并行、迁移和 autoscaling 全部叠加。每阶段只引入一类变量，并设置明确验收门槛。

PHASE 0 / BASELINE

冻结基线

固定模型 revision、分辨率、chunk 帧数、动作 trace、seed 与硬件；分解 DiT / VAE / encode / transfer 时间。

GATE · 100+ chunk 无漂移；耗时归因误差 <3%
PHASE 1 / WORKER

单会话快且稳

启用官方 causal KV path；评估 FlashAttention、编译、混合精度与 DiT–VAE 流水；建立质量回归。

GATE · 生产 FPS > 播放 FPS；P99 TPC 达标
PHASE 2 / MULTIPLEX

多会话合批

实现 deadline-aware coalescing、背压和状态内存池；按 active / idle 切换，不做迁移。

GATE · 负载升高时尾延迟可控；无 OOM
PHASE 3 / TURBO

迁移与弹性

补 CPU offload、NCCL migration、placement controller 与 autoscaling；用真实 session trace 回放。

GATE · 成本–SLO Pareto 优于固定满池基线

08 / RISKS

容易踩错的四个判断

01

平均 FPS ≠ 不会卡

流式体验由最慢 chunk 和抖动决定；必须报告 P99 / max TPC 与 stall rate。

02

量化 ≠ 必然提速

没有硬件匹配 kernel 时，Q/DQ、路由和通信可能吞掉收益；先看 kernel trace。

03

迁移 ≠ 越多越好

只有未来负载改善大于状态复制、同步与缓存冷却成本时，迁移才值得。

04

Demo ≠ 通用后端

TurboServe demo 与 LingBot-World inference code 之间仍有明确 adapter 工程缺口。
